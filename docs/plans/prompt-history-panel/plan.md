# Implementation Plan: Prompt History Panel

## Overview

A frontend-only feature. A new optional dockview panel, `prompt-history`, lists the active session's user prompts newest-first with per-row truncation, expand (40 % panel-height cap with in-box scrolling), send time, agent-work duration, and an arrow that navigates to the prompt in the transcript. Build order: pure duration domain → panel content + registries + "+" menu → cross-panel transcript navigation → E2E + locale parity. No backend, schema, or API changes: prompts come from the loaded transcript messages (`messages.bySession`) and turns from the `useSessionTurns(sessionId)` hydration hook (which selects `turns.bySession` internally and backfills sibling sessions on switch — see `Frontend > 1`).

## Backend

None. The messages and turns the panel needs are already fetched and stored by the session page (SSR hydration via `lib/ssr/session-page-state.ts` + WS updates in `lib/state/slices/session/turn-actions.ts`).

## Frontend

### 1. Duration domain — `apps/web/lib/prompt-history.ts` (new, + test)

TURN HYDRATION (prerequisite for correct durations): route initialization — SSR (`session-page-state.ts`) or the client fallback (`task-detail-route.tsx` calling `fetchSessionDataForTask`, which reuses the same hydration) — fetches `listSessionTurns(sessionId)` for the route's INITIAL session only. Switching to a sibling session fetches its messages through `useSessionMessages` but leaves `turns.bySession[sibling]` undefined, so a completed single-prompt sibling would render `durationSeconds: null`. Add (a) a slice action `replaceSessionTurns(sessionId, turns)` in `lib/state/slices/session/turn-actions.ts`, (b) a per-session HYDRATION MARKER `turns.hydratedBySession: Record<string, boolean>` — set by route hydration (the turns merge in `lib/state/hydration/hydrator.ts`) and by `replaceSessionTurns`, and NEVER by the live WS `addTurn` (the `session.turn.started` handler at `apps/web/lib/ws/handlers/turns.ts` calls `addTurn`, whose reducer CREATES `turns.bySession[sessionId]` — so array existence is NOT evidence of hydration), and (c) a `useSessionTurns(sessionId): Turn[]` hydration hook that fetches `listSessionTurns` from `lib/api/domains/session-api.ts` when the MARKER for the session is absent (even when a live partial array exists), sets the marker on success (including EMPTY successful snapshots — a successful zero-turn response still means hydrated), internally selects `turns.bySession[sessionId]`, and returns the current list. The panel content consumes the HOOK's return value (not a raw store read), so sibling hydration cannot be skipped. Regression: a `session.turn.started` event lands before the hook's first check → array exists but marker absent → the snapshot fetch STILL fires and older completed turns are present afterwards; no refetch after the marker is set.
- MARKER SET ONLY ON ACTUAL MERGE: `mergeSessionMap` (`lib/state/hydration/merge-strategies.ts`) SKIPS an already-present active session unless `forceMergeSessionId` matches — so the hydrator must set `hydratedBySession[sessionId]` ONLY for sessions whose snapshot was actually merged (the forced/initial session, or newly inserted ones), and keep the marker ABSENT when the merge was skipped (protected active session). A blanket "mark every incoming key" marks a discarded snapshot as hydrated and suppresses the required fetch. The hydrator either uses `mergeSessionMap`'s accepted-session reporting or derives the accepted set itself. Regression: active session present pre-hydration, snapshot arrives without `forceMergeSessionId` → skipped → marker stays absent → `useSessionTurns` still fetches.
- INITIAL-STATE PATH IS PART OF THE CONTRACT (ONE CONTRACT, threaded through every boundary): `FetchedSessionData.initialState` is `ReturnType<typeof taskToState>` and `StateHydrator` accepts `Partial<AppState>` (`lib/ssr/session-page-state.ts`, `components/state-hydrator.tsx`) — there is no `HydrationState`-typed route payload, so the "optional marker at the HydrationState boundary" alternative is dropped. Instead `buildSessionState` EXPLICITLY includes the marker: `hydratedBySession: { [sessionId]: true }` when a session was hydrated (the route DID actually merge that session's turns), `{}` when none — the full `TurnsState` then flows through `Partial<AppState>` unchanged. `mergeInitialState` (`lib/state/default-state.ts`) DEEP-merges `turns.hydratedBySession` (default `{}` wins for keys the payload lacks), and `hydrateState`/the hydrator initializes `draft.turns.hydratedBySession ??= {}` before any marker write. Regressions: a boot payload with turns leaves a DEFINED marker map (never `undefined`); the route-initial session arrives marked (it was actually merged), a sibling does NOT.
- MERGE, NOT BLIND REPLACEMENT: turns are live WS state — a fetch begun while `turns.bySession[s]` is undefined can resolve AFTER `addTurn`/`completeTurn` events, and replacing the list would erase a newly received turn or its `completed_at`. `replaceSessionTurns` must upsert per fetched turn with EXACTLY the existing `addTurn` reducer semantics (`turn-actions.ts`: `Object.assign(existing, turn, { completed_at: existing.completed_at ?? turn.completed_at })`): `completed_at` is forward-preserved (the no-downgrade invariant is scoped TO `completed_at` — the field the duration feature reads); `metadata` follows the existing reducer's OVERWRITE behavior, which this contract does not change or claim to preserve; absent turns are appended; `activeBySession` untouched. A deferred snapshot can therefore never erase a completion, but it CAN overwrite a turn's `metadata` — accepted and documented, matching live behavior. Tests: fetch starts while turns absent → `addTurn`/`completeTurn` land before the response → the response applies → the `completed_at` survives and the duration renders; a deferred snapshot with older `metadata` overwrites it (documenting the existing reducer semantics).
- STALE-SESSION GUARD + TURNS-OWNED SEQUENCE: the per-session monotonic fetch-sequence pattern in `use-session-messages.ts` is NOT directly reusable — its counter and `lastAppliedFetchSeq` map are module-global and keyed only by session, shared with message fetches, so a newer MESSAGE fetch for the same session could advance the applied sequence and discard a valid TURN response. The hook must OWN its sequence namespace: either its own module-level counter/map keyed by a resource-qualified key (`turns:<sessionId>`) or a hook-local map — copy the pattern, do not import the shared helpers. It ALSO adds a hook-local ACTIVE-SESSION GENERATION check before merge — a MONOTONIC counter incremented on EVERY active-session transition, captured per request, compared before merge (an ID-only check is insufficient: on A→B→A with A's request still in flight, the ID matches again and the stale snapshot merges). Merge requires BOTH the generation captured at request time to equal the current generation AND the turns-owned sequence to be the latest. Tests: A fetch in flight → switch to B → A's response arrives → discarded, B's derived state unaffected; DEFERRED A→B→A — A's response arrives after returning to A → generation mismatch (it advanced on both transitions) → discarded; a message fetch committing after a turns fetch started does NOT discard the turns response (cross-resource isolation).

Pure, unit-testable derivation used by the panel:

```ts
export type PromptHistoryEntry = {
  messageId: string;
  sessionId: string;
  content: string;
  sentAt: string;          // Message.created_at
  durationSeconds: number | null; // null = no duration shown (see spec rules)
  isLastPrompt: boolean;
};

export function buildPromptHistoryEntries(
  messages: Message[],   // session transcript messages, any order
  turns: Turn[],         // turns.bySession[sessionId]
): PromptHistoryEntry[] // newest-first
```

Contract (spec "Duration rules" + robustness rules):

- Prompts = `author_type === "user"`. A prompt with unparseable `created_at` is excluded FIRST; the prompt list used for both ordering and next-prompt bounds is the filtered, sorted list. Sort ascending by `created_at`, ties broken by `id` ascending, then reverse for newest-first output.
- All associations are session-scoped: when matching a turn by `turn_id`, require `turn.session_id === message.session_id`; the "next prompt" bound is the immediately following entry of the same session in the filtered list — an unparseable user message can never become a next-prompt candidate, so a valid prompt followed by an invalid user message is bounded by the next valid prompt. Inputs need not be pre-filtered to one session.
- For each prompt: `start = created_at`; end candidates = the matched turn's `completed_at` (only when parseable) and the next same-session filtered prompt's `created_at`; `end = min` over present candidates; `durationSeconds = floor(max(0, end − start) / 1000)`; `null` when no end exists or when the entry is the last prompt of its session and its turn is not completed.
- Formatting lives next to it as `formatPromptDuration(seconds, units)` — a PURE numeric helper whose unit labels are INJECTED BARE LOCALIZED LABELS: `units = { s: string; m: string; h: string }` resolved at the call site from catalog keys via RUNTIME `t()` (never module-scope `t`); the helper APPENDS the numeric count itself (`${count}${units.s}` → `5s`), producing `0s` / `Xm Ys` / `Xh Ym Zs` shapes, clamping negatives to `0s`. This is NEW user-facing copy, so hardcoded English labels in the helper would violate the i18n contract (the ratchet does not reliably scan plain `.ts` helpers); the pre-existing `formatDuration` copies in `agent-status.tsx`/`use-session-turn.ts` are not an exemption. New keys are count-free BARE labels — `task:durationUnitSeconds: "s"`, `durationUnitMinutes: "m"`, `durationUnitHours: "h"` — with NO `{{count}}` interpolation, so the `check-inline-plurals` gate (`i18n:check`) is satisfied without `_one`/`_other` siblings; en + pseudo keys are owned by Task 02's catalog work. Tests assert en composition (`5m 23s`) with INJECTED labels; the pseudo-locale catalog-path assertion lives in Task 02's component test (the keys are created in Wave 2; Task 01 runs in Wave 1 before the catalogs exist).

### 2. Panel content + registries + "+" menu

- `apps/web/components/task/prompt-history-panel-content.tsx` (new): reads `useAppStore(state => state.tasks.activeSessionId)`, `useSessionMessages(sessionId)`, and `const turns = useSessionTurns(sessionId)` — the HOOK is the sole turns source (it selects `turns.bySession` internally and hydrates sibling sessions; a raw store read would skip hydration); derives entries via `buildPromptHistoryEntries`; renders rows newest-first. FOLLOWS THE ACTIVE SESSION (mirror `todos-panel-content.tsx`, which reads the same `tasks.activeSessionId` reactively): the panel always shows the task's active session's prompts and never merges sessions — a task with multiple agent transcripts shows one session at a time. Session switches (`setActiveSession` from session tabs, the session dropdown, or auto handoff via `adoptActiveSession`) re-derive the whole list: `useSessionMessages` refetches the sibling on switch (`sessionChanged`), and `useSessionTurns` hydrates the sibling's turns lazily via the `hydratedBySession` marker, so the new session's rows render immediately and its durations appear when its turns arrive (until then `durationSeconds: null`). A null active session yields the empty state. Row layout: arrow button (`IconCornerUpLeft`-style transcript-jump icon), truncated text (`flex-1 min-w-0 truncate`), compact relative time, duration (`formatPromptDuration`), expand chevron (`IconChevronDown`/`IconChevronUp`, `aria-expanded`). WAVE BOUNDARY (Task 02 runs before the `scrollTranscriptToMessage` action exists in Task 03): the component takes an OPTIONAL `onNavigateToPrompt?: (messageId: string) => void` prop and the row arrow invokes it with the row's `messageId`; Task 03 wires the dockview renderers to pass a callback bound to `scrollTranscriptToMessage(sessionId, messageId, resolvedTitle)` (title resolution `session?.name || panelTitle("chat")` lives in Task 03's wiring, where the action exists).
- PASSTHROUGH DEGRADED STATE (the menu guard alone cannot cover restored/already-open tabs, since the panel is reusable and persisted in layouts; `ChatContent` switches only the chat panel to `PassthroughToolbar` and there is no layout-side passthrough filtering): when the active session is passthrough (`taskSessions.items[sessionId]?.is_passthrough`), the content renders a passthrough empty state with NO rows and NO arrow controls — the transcript the arrow would jump to does not exist in a passthrough session. Component test: passthrough session → empty state, zero arrows, zero rows.
- **Chevron visibility** measures the collapsed single-line text element with `scrollWidth > clientWidth` (horizontal overflow), re-measured via a `ResizeObserver` on that element (width changes, e.g. panel resize). Expanded rows switch to wrapping text (`whitespace-normal`, no `truncate`) inside a `maxHeight`-capped box with `overflow-y-auto`.
- EXPANSION STATE IS KEYED BY `messageId`, NOT ROW INDEX: the list is live and newest-first, so a newly arriving prompt shifts every older row's index — an index-keyed `expandedByIndex` leaves the WRONG prompt expanded. Test IDs stay index-based (they are DOM-lookup handles only). Regression: expand an older prompt, prepend a newer prompt, assert the SAME message (by id) remains expanded.
- **40 % cap** measures the panel's own root element through a component `ref` (e.g. the `PanelRoot` wrapper). `PanelRoot` does not emit `data-panel-kind` by default (`components/task/panel-primitives.tsx`), so do not rely on `closest("[data-panel-kind]")`; the ref is the contract. A `ResizeObserver` on that root re-measures on resize; when no measurable container exists (isolated render), fall back to `40vh`. Expanded `maxHeight = round(root.clientHeight * 0.4)` px.
- Time display: `formatRelative` from `@/lib/i18n/formats` (compact catalog-backed ladder: `just now`, `5m ago`, `3h ago`, `2d ago`) inside `<time dateTime title>` with the absolute time in `title` (pattern from `components/task/chat/messages/message-actions.tsx`). Do not use `formatRelativeTime` — it renders full Intl phrases ("5 minutes ago") that do not fit the row.

### 3. Cross-panel transcript navigation

- `apps/web/lib/state/dockview-store.ts`: add state + actions:
  ```ts
  scrollTarget: { sessionId: string; messageId: string; token: number; hostPanelId: string } | null;
  scrollTranscriptToMessage: (sessionId: string, messageId: string, title: string) => void;
  clearScrollTarget: (token: number) => void; // consumer-side compare-and-clear
  clearScrollTargetForSession: (sessionId: string) => void; // teardown-side session compare
  ```
  A monotonic `token` (module-level counter incremented per request) gives every target an identity; `hostPanelId` is the RESOLVED host panel id (`session:<sessionId>` or `chat`) recorded by the action.
- EXACT-OWNER CONSUMPTION (two active hosts): `usePanelActive` is active-per-Dockview-GROUP (`hooks/use-panel-active.ts` reads the panel's `api.isActive`, which is "active tab in its own group") — so a persisted/split layout can leave the canonical `chat` panel and a `session:<id>` panel in DIFFERENT groups, both active at once; focusing one does not deactivate the other, and BOTH `TaskChatPanel` instances would pass the `isVisible` gate and race to consume/clear. `TaskChatPanel` therefore receives an OPTIONAL HOSTING `panelId?: string | null` prop: the two dockview `ChatContent` callers (`dockview-panel-content.tsx`, `dockview-shared.tsx`) pass their real panel id; the NON-dockview callers (`preview-session-tabs.tsx`, `task-center-panel.tsx`, `mobile/session-mobile-layout.tsx`) pass nothing. Consumption requires a DEFINED `ownPanelId` AND `scrollTarget.hostPanelId === ownPanelId` BEFORE scrolling or clearing — session match alone is not enough, and a host without a panel id (mobile/preview/center) can NEVER consume a dockview target. Regressions: canonical `chat` and `session:<id>` in different groups, both active, one target → only the owner instance consumes; the non-owner never scrolls and never clears; a non-dockview host (no `panelId`) never consumes a dockview target even when its `isVisible` is true.
- `apps/web/lib/state/dockview-panel-actions.ts`: implement `scrollTranscriptToMessage(sessionId, messageId, title)` — the CALLER (prompt-history panel content, which runs in React context) resolves the title as `session?.name || panelTitle("chat")` from `useAppStore` and passes it in, following the `addTerminalPanel(..., title)` precedent: the dockview store has no AppState access (the app store is context-created in `components/state-provider.tsx`, after the dockview store module initializes). Truthy check: an empty-string `name` must fall back too; NOTE: `TaskSession` has `name?: string`, not `title`; the precedence mirrors `resolveSessionTabTitle` in `components/task/session-tab-title.ts`, and the chat panel re-resolves its tab title reactively via `useChatSessionTitle`, so this is only the initial tab label. `addSessionPanel(api, centerGroupId, sessionId, title)` requires a non-undefined title.
- HOST-NEUTRAL CHAT-TARGET RESOLUTION (a bare `addSessionPanel` violates the Office layout, which is explicitly single-session — `office-dockview-layout.tsx` starts with a canonical `chat` panel that `dockview-shared.tsx`'s `ChatContent` already renders the active session into; adding `session:<id>` there would open a second chat tab instead of focusing the existing one, contradicting the spec's "opened if absent, focused if present"): resolve the target panel in this order — (1) an existing `session:<sessionId>` panel → focus it; (2) otherwise an existing canonical `chat` panel → focus it (its `ChatContent` resolves `paramSessionId ?? storeSessionId`, and the target session IS the active session, so the canonical panel already renders it); (3) only when no chat target exists at all → `addSessionPanel` to create `session:<sessionId>`. Then `set({ scrollTarget: { sessionId, messageId, token: nextToken(), hostPanelId: resolvedPanelId } })` — `hostPanelId` is the panel that was focused/created (`session:<sessionId>` in cases 1 and 3, `chat` in case 2); it is REQUIRED for exact-owner consumption and must be present in every record and test fixture. Tests cover all three resolutions AND assert `hostPanelId`, including the Office single-session case (no `session:<id>` exists, canonical `chat` exists → focuses `chat`, never adds a tab).
- WIRING is a required, tested change: `buildExtraPanelActions(get)` currently receives only `get` and its `StoreSet` type admits only `{ selectedDiff }` (`dockview-panel-actions.ts`). Change the store composition to `...buildExtraPanelActions(set, get)` (`dockview-store.ts`'s creator already has `set` in scope, like `buildPanelActions(set, get)`) and widen BOTH local types: `StoreSet` to admit `scrollTarget: { sessionId: string; messageId: string; token: number; hostPanelId: string } | null` (the SAME shape as the store's declared type — including `hostPanelId`) AND `StoreGet` to expose `scrollTarget` (the compare-and-clear reads it). EXISTING tests break under the new signature: `apps/web/lib/state/dockview-panel-actions-extra.test.ts` (callers at multiple lines) and its `makeStore` helper in `apps/web/lib/state/dockview-panel-actions.test-utils.ts` must be updated to pass `set` and to include `scrollTarget` in the test `StoreShape` — add both files to Files likely touched and to the Task 03 verification command.
- **Lifecycle policy (teardown-safe, implementable):** the target is retained until the intended panel consumes it — or until its session panel is removed. `scrollTranscriptToMessage` activates the target panel in the same tick, so consumption normally happens immediately in that panel's effect; the target only survives across layout work when the panel is detached but still registered. When the `session:<sessionId>` panel is removed (`api.onDidRemovePanel` in `components/task/dockview-layout-setup.ts` already hosts panel-removal cleanup), the teardown calls the store's `clearScrollTargetForSession(sessionId)` action — the IMPLEMENTABLE, declared API for teardown: it compares `scrollTarget.sessionId` to the argument (session match only, no token comparison: the removed panel carries no token, and the target always holds the LATEST intent — superseded requests are overwritten, so any removal of the target's session panel outside consumption means the user navigated away and the intent is stale) and clears when they match. It is wired BEFORE the callback's existing `if (isRestoringLayout) return;` guard so restore-time removals clear too (fail closed: a layout rebuild may drop a pending arrow-click intent, but a remounted panel can never perform an unexpected stale scroll). Consequences: a remounted same-session panel never consumes a stale target; removing a DIFFERENT session's panel never touches the target; an implementer never needs a direct `useDockviewStore.setState` bypass.
- SESSION-SWAP INVALIDATION (Office canonical chat): `onDidRemovePanel` alone cannot invalidate targets in the Office workbench — no `session:<id>` panel is ever created there, and the canonical `chat` panel stays mounted while its `ChatContent` swaps the resolved session (`paramSessionId ?? storeSessionId` → active session). A delayed target for session A (retained by the delayed-DOM contract) would otherwise survive the chat switching to session B and consume when the user returns to A. Fix: `TaskChatPanel`'s effect tracks its `resolvedSessionId`; when it CHANGES (only the session-swapping canonical `chat` host ever sees this — `session:<id>` instances have fixed props), it calls `clearScrollTargetForSession(previousSessionId)` (the action's session compare keeps it safe). Regression: canonical chat resolves A → target A set with delayed DOM (not consumed) → chat resolves B → target A cleared → chat resolves A again → no scroll.
- CANONICAL-HOST UNMOUNT OWNERSHIP: the same canonical host can be removed/rebuilt during a layout restore or closed without a session switch, leaving an unconsumed target that a same-session remount later consumes as a stale scroll (the `session:<id>` removal hook never fires for it). Fix: `TaskChatPanel`'s effect ALSO registers an unmount cleanup that calls `clearScrollTargetForSession(lastResolvedSessionId)` — the last session the host resolved to (for `session:<id>` instances this duplicates the panel-removal clear harmlessly; for the canonical host it closes the gap). Regression: canonical chat resolves A → target A unconsumed → panel removed (restore/close) → target cleared → remount resolves A → no scroll.
- REMOVAL-PATH CLEAR COVERS RESTORE (unmount cleanup is NOT guaranteed): during a layout restore (`fromJSON`), the portal slot DETACHES but deliberately does NOT release the persistent portal (`lib/layout/panel-portal-host.tsx` "Detach only — do NOT release"), and `onDidRemovePanel` in `dockview-layout-setup.ts` returns before `panelPortalManager.release` whenever `isRestoringLayout` is true — so a canonical `chat` removed during restore keeps its `TaskChatPanel` MOUNTED and its unmount cleanup never runs. The removal listener must ALSO clear canonical-chat targets on an always-running path BEFORE the `isRestoringLayout` guard: when the removed panel is the canonical `chat` (`panel.id === "chat"`) and a target exists, call `clearScrollTargetForSession(appStore.getState().tasks.activeSessionId)` (the canonical host always resolves the active session; `setupPortalCleanup` already receives the app store). The teardown test must exercise the ACTUAL persistent-portal restore lifecycle (slot detached, portal not released, host stays mounted) and assert the removal-path clear is what prevents the remounted host from consuming — not a mocked React unmount.
- `apps/web/components/task/task-chat-panel.tsx`: TWO SEPARATE EFFECTS (React runs an effect's cleanup before EVERY dependency-change rerun, so a single effect that both consumes on `isVisible` and clears-on-unmount/session-change would clear the retained target on an inactive→active transition before consuming it): (1) a LIFECYCLE effect keyed ONLY by `resolvedSessionId` — on session change it calls `clearScrollTargetForSession(previousSessionId)`; its cleanup (unmount or session change) also clears by the LAST resolved session (canonical-host unmount ownership); (2) a CONSUMPTION effect keyed by `scrollTarget`, `resolvedSessionId`, `isVisible`, and the message-list readiness — when `scrollTarget` is non-null, `scrollTarget.sessionId === resolvedSessionId`, and the hosting panel is active via the ALREADY-THREADED `isVisible` prop (symbols, not line numbers: `ChatContent` in `dockview-panel-content.tsx` and its Office counterpart in `dockview-shared.tsx` both pass `usePanelActive(panelId)` into `TaskChatPanel`'s `isVisible` prop), capture `const token = scrollTarget.token`, call `messageListRef.current?.scrollToMessage(scrollTarget.messageId, { align: "start" })`, and clear ONLY on success: `MessageListHandle.scrollToMessage` currently returns `void` and no-ops when the message element is not yet rendered. Change the handle to report success (`scrollToMessage(...) => boolean`) AND to resolve the row WITHIN the owning message-list root (`scrollRef.current.querySelector('[id="msg-<id>"]')` with `CSS.escape(messageId)` or an id-safe attribute selector) instead of ``document.getElementById(`msg-${messageId}`)`` — with the canonical `chat` and `session:<id>` panels mounted simultaneously, duplicate `msg-<id>` rows exist in the DOM and a global lookup can resolve the HIDDEN canonical duplicate, leaving the visible transcript unmoved even though the consumer instance gating passed.
