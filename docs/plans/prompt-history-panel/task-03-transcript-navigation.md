# Task 03: Transcript navigation

## Acceptance

- `scrollTranscriptToMessage(sessionId, messageId, title)` — the CALLER (the prompt-history panel content component, which runs in React context) resolves the title as `session?.name || panelTitle("chat")` from `useAppStore` and passes it in, following the existing `addTerminalPanel(..., title)` precedent: the dockview store has no AppState access (the app store is context-created in `components/state-provider.tsx`, after the dockview store module initializes). A TRUTHY check so an empty-string `name` falls back; NOTE: `TaskSession` (`apps/web/lib/types/http.ts`) has `name?: string`, not `title`; the precedence mirrors `resolveSessionTabTitle` (`components/task/session-tab-title.ts`) and the chat panel re-resolves its tab title reactively via `useChatSessionTitle`, so this only supplies the initial tab label. `addSessionPanel(api, centerGroupId, sessionId, title)` requires a non-undefined title.
- HOST-NEUTRAL CHAT-TARGET RESOLUTION: a bare `addSessionPanel` is WRONG for the Office workbench — `office-dockview-layout.tsx` is explicitly single-session and starts with a canonical `chat` panel whose `ChatContent` (in `dockview-shared.tsx`) already renders the active session; adding `session:<id>` there opens a SECOND chat tab instead of focusing the existing one, contradicting the spec's "opened if absent, focused if present". Resolve in this order: (1) existing `session:<sessionId>` panel → focus it; (2) else existing canonical `chat` panel → focus it (it renders the active session via `paramSessionId ?? storeSessionId`, and the target session IS the active session); (3) else (no chat target at all) → `addSessionPanel`. Then record `scrollTarget = { sessionId, messageId, token, hostPanelId: resolvedPanelId }` with a monotonic token — `hostPanelId` is the panel that was focused/created (`session:<sessionId>` in cases 1 and 3, `chat` in case 2) and is REQUIRED in every record and fixture.
- WIRING (the current builder cannot do this): `buildExtraPanelActions(get)` receives only `get` and its `StoreSet` type only admits `{ selectedDiff }` (`dockview-panel-actions.ts`). Change the store composition to `...buildExtraPanelActions(set, get)` (`dockview-store.ts`'s creator already has `set` in scope, like `buildPanelActions(set, get)`) and widen BOTH local types: `StoreSet` to admit `scrollTarget: { sessionId: string; messageId: string; token: number; hostPanelId: string } | null` (the SAME shape as the store's declared type — including `hostPanelId`) AND `StoreGet` to expose `scrollTarget` (the compare-and-clear reads it). EXISTING tests break under the new signature: `apps/web/lib/state/dockview-panel-actions-extra.test.ts` (callers at multiple lines) and its `makeStore` helper in `apps/web/lib/state/dockview-panel-actions.test-utils.ts` must pass `set` and include `scrollTarget` in the test `StoreShape` — update both and run them in this task's verification.
- The chat panel consumes a target only when ALL of: `scrollTarget` non-null, `scrollTarget.sessionId === resolvedSessionId`, `scrollTarget.hostPanelId === ownPanelId` (EXACT OWNER — see below), and the hosting panel is active via the ALREADY-THREADED `isVisible` prop — `TaskChatPanel` receives `isVisible` from `ChatContent` in `dockview-panel-content.tsx` and its Office counterpart in `dockview-shared.tsx` (both pass `usePanelActive(panelId)` per hosting panel). Do NOT add a new ``usePanelActive(`session:${sessionId}`)`` call inside `TaskChatPanel`: with the canonical `chat` placeholder and a `session:<id>` panel mounted simultaneously (a real transient layout state), both instances would observe the same signal and the hidden canonical instance could consume and clear the target before the visible one scrolls. Gating on each instance's own `isVisible` plus the session match prevents the hidden-instance case, but NOT two-active-hosts: `usePanelActive` is active-per-Dockview-GROUP (`hooks/use-panel-active.ts` reads the panel's `api.isActive`, i.e. "active tab in its own group"), so a saved/split layout can leave the canonical `chat` and a `session:<id>` panel in DIFFERENT groups, both active, and both instances would pass the `isVisible` gate and race. Therefore `scrollTarget` carries `hostPanelId` (the panel the action resolved: `session:<sessionId>` or `chat`), `TaskChatPanel` receives an OPTIONAL HOSTING `panelId?: string | null` prop (the two dockview `ChatContent` callers pass their real panel id; the NON-dockview callers — `preview-session-tabs.tsx`, `task-center-panel.tsx`, `mobile/session-mobile-layout.tsx` — pass nothing), and consumption requires a DEFINED `ownPanelId` AND `scrollTarget.hostPanelId === ownPanelId` BEFORE scrolling or clearing — session match alone is insufficient, and a host without a `panelId` can NEVER consume a dockview target.
- Success-reporting, root-scoped consumption: `MessageListHandle.scrollToMessage` currently returns `void` and resolves the row via ``document.getElementById(`msg-${messageId}`)`` (`message-list-native-scroll.ts` `useScrollToMessage` early-returns when that global lookup misses). Global lookup is wrong for this feature: with the canonical `chat` and `session:<id>` panels mounted simultaneously, DUPLICATE `msg-<id>` rows exist, and a global lookup can resolve the hidden canonical duplicate — the consumer-instance gate passes but the visible transcript never moves. Change the handle to (a) resolve within the OWNING message-list root — `scrollRef.current.querySelector('[id="msg-<id>"]')` using `CSS.escape(messageId)` or an id-safe attribute selector — and (b) return `boolean` (true only when it actually scrolled; false when the row is absent in this list's root). The effect calls `scrollToMessage(messageId, { align: "start" })` and clears with compare-and-clear — `clearScrollTarget(token)` only when the scroll succeeded AND the stored token still equals the consumed token — so a stale consumer can never clear a newer intent and a target is never dropped just because the row had not rendered yet. When the scroll reports false, the target stays; the effect re-runs as `messages`/`isVisible` change (delayed DOM, pagination, activation) and retries until it succeeds. The consumption effect must depend on `isVisible` so a target set while the panel is detached/inactive is consumed the moment the panel becomes active, with no new request.
- Targets for other sessions are ignored and not cleared by this panel. A superseded target (newer request) is not cleared by a delayed older consumer.
- SESSION-SWAP INVALIDATION (Office canonical chat): `onDidRemovePanel` teardown never fires for the Office layout because no `session:<id>` panel is created there — the canonical `chat` panel stays mounted while `ChatContent` swaps the resolved session. `TaskChatPanel`'s effect tracks its `resolvedSessionId`; when it CHANGES (only the session-swapping canonical `chat` host ever sees this; `session:<id>` instances have fixed props), the panel calls `clearScrollTargetForSession(previousSessionId)`. A delayed target for session A therefore cannot survive a canonical-chat switch to B and consume on return to A. Regression: canonical chat resolves A → target A set with delayed DOM (unconsumed) → resolved session changes to B → target A cleared → resolve back to A → no scroll.
- CANONICAL-HOST UNMOUNT OWNERSHIP: the canonical host can also be removed/rebuilt during a layout restore or closed without any session switch, leaving an unconsumed target that a same-session remount later consumes as a stale scroll (the `session:<id>` removal hook never fires for it). `TaskChatPanel`'s LIFECYCLE effect registers an unmount cleanup that calls `clearScrollTargetForSession(lastResolvedSessionId)` — the last session the host resolved to (for `session:<id>` instances this duplicates the panel-removal clear harmlessly). Regression: canonical chat resolves A → target A unconsumed → panel removed (restore/close) → unmount cleanup clears → remount resolves A → no scroll.
- REMOVAL-PATH CLEAR COVERS RESTORE (unmount cleanup is NOT guaranteed): during `fromJSON` restore the portal slot DETACHES but deliberately does NOT release the persistent portal (`lib/layout/panel-portal-host.tsx`), and `onDidRemovePanel` in `dockview-layout-setup.ts` returns before `panelPortalManager.release` while `isRestoringLayout` — so a canonical `chat` removed during restore keeps its `TaskChatPanel` MOUNTED and the unmount cleanup never runs. The removal listener ALSO clears canonical-chat targets on an always-running path BEFORE the `isRestoringLayout` guard: when the removed panel is `panel.id === "chat"` and a target exists, call `clearScrollTargetForSession(appStore.getState().tasks.activeSessionId)` (the canonical host always resolves the active session; `setupPortalCleanup` already receives the app store). The teardown test must exercise the ACTUAL persistent-portal restore lifecycle (slot detached, portal not released, host stays mounted) and assert the removal-path clear prevents the remounted host from consuming — not a mocked React unmount.
- TWO SEPARATE EFFECTS ARE MANDATORY (React runs an effect's cleanup before every dependency-change rerun): (1) the LIFECYCLE effect is keyed ONLY by `resolvedSessionId` — its rerun clears the PREVIOUS session, and its cleanup (unmount or session change) clears by the LAST resolved session; it must NOT depend on `isVisible`, so an inactive→active transition never triggers its cleanup; (2) the CONSUMPTION effect is keyed by `scrollTarget`, `resolvedSessionId`, `isVisible`, and message-list readiness, with no cleanup — it consumes on activation and clears only on a successful scroll. A single effect doing both would clear the retained target on an inactive→active transition before consuming it, violating the activation test.
- Teardown policy (implementable, via a declared API): the target is retained until the intended panel consumes it; when the `session:<sessionId>` panel is removed (`api.onDidRemovePanel` in `components/task/dockview-layout-setup.ts`), the teardown calls the store action `clearScrollTargetForSession(sessionId)` — session match ONLY, no token comparison (a token compare is not implementable: the removed panel carries no token, and the target always holds the LATEST intent, superseded requests being overwritten, so any removal of the target's session panel outside consumption means the user navigated away and the intent is stale). The action is declared on the store (`clearScrollTargetForSession` next to `clearScrollTarget(token)`) and implemented in `buildExtraPanelActions(set, get)` via `set`; the teardown never needs a direct `useDockviewStore.setState` bypass. The call MUST run BEFORE the callback's existing `if (isRestoringLayout) return;` guard (fail closed: a layout rebuild may drop a pending arrow-click intent, but a remounted panel can never perform an unexpected stale scroll). A remounted same-session panel (e.g. after a task switch and back) therefore never consumes a stale target; removing a DIFFERENT session's panel never touches the target.
- Clicking a prompt-history row arrow produces exactly this behavior. WIRE-UP OWNERSHIP (Task 03): the component already exposes the `onNavigateToPrompt?: (messageId: string) => void` seam (Task 02); Task 03 updates the two dockview renderers (`dockview-panel-content.tsx`, `dockview-shared.tsx`) to pass a callback bound to `scrollTranscriptToMessage(sessionId, messageId, resolvedTitle)`, resolving the title as `session?.name || panelTitle("chat")` (custom / EMPTY-string / absent `name` cases tested here, where the action exists). The renderer wiring is COVERED BY TESTS in this task: `dockview-panel-content.todos.test.tsx` (desktop) and `dockview-shared.test.tsx` (Office) assert, with `PromptHistoryPanelContent` mocked, that each renderer passes the bound callback with the correct resolved title for all three `name` cases — an omitted callback or wrong title fails those tests.

## Risks

- Multiple `TaskChatPanel` instances exist for multi-session tasks; without per-panel active gating an inactive instance consumes a target meant for the visible transcript. Without compare-and-clear a delayed consumer clears a newer request. Cover both with the deterministic tests: target A then session switch (stale A not consumed by the new session); request B superseding undelivered A (A's delayed consume does not clear B); target for another mounted session ignored and left uncleared; target set while the panel is inactive → consumed on activation (`isVisible` flips); canonical `chat` and `session:<id>` mounted simultaneously → only the session-hosted instance consumes; teardown — target set for session A, panel A removed (`onDidRemovePanel`) → target cleared, and a remounted A does not scroll; the removal with `isRestoringLayout` true still clears.
- The active-panel gate must be the reactive per-panel `isVisible` prop (`usePanelActive(panelId)` in the host), not a snapshot of `api.activePanel` and NOT a `session:<id>`-keyed signal inside `TaskChatPanel`: with the canonical `chat` placeholder and `session:<id>` mounted together, both instances would observe the same signal and the hidden canonical instance could consume and clear the target before the visible one scrolls. Each instance gates on its own hosting panel's active state plus the session match.
- `scrollToMessage` can no-op before the row renders (message loading, pagination, layout timing); clearing unconditionally would drop the target without scrolling. The success-report contract (handle returns boolean, clear only on true, retry on re-render) is what makes the retention policy real — pin it with the delayed-DOM regression test AND a native-level test of the real `useScrollToMessage` (the mocked-handle test alone lets a buggy native implementation pass while clearing incorrectly).
- The row lookup MUST be root-scoped: with canonical `chat` + `session:<id>` mounted together, duplicate `msg-<id>` rows exist and a `document.getElementById` lookup can scroll the hidden duplicate while the visible transcript stays put — consumer-instance gating alone does not save it. The duplicate-row native regression is what pins this.
- The teardown clear is ownership-sensitive but token-less by necessity: the removed panel carries no token and the target always holds the latest intent, so the clear is session-match only and runs before the `isRestoringLayout` guard. The negative test (other-session removal leaves the target intact) is what stops a cleanup that clears on ANY session removal. Do not re-introduce a token compare into teardown: it is unimplementable and its test would be vacuous.
- The teardown clear must be placed before the `isRestoringLayout` early-return in `onDidRemovePanel` (or in a separate always-running listener) or restore-time removals skip it.
- `addSessionPanel` requires a title argument; the CALLER supplies `session.name || panelTitle("chat")` (truthy check — empty-string `name` falls back too; never `session.title`, which does not exist on `TaskSession`). The dockview store action cannot reach AppState (`useAppStore` is context-only); wiring `buildExtraPanelActions(set, get)` with a widened `StoreSet` is a required, tested change, not an assumption.
- Keep `scrollToLastPrompt`/`scrollToStart` flows untouched; this adds a parallel entry point.
- The chat-target resolution is host-sensitive: in the Office single-session layout only the canonical `chat` panel exists and already renders the active session — focusing it must NOT add a `session:<id>` tab; in the desktop multi-session workbench an existing `session:<id>` wins. The three-way resolution test pins both.
- Office targets need session-swap invalidation, not just panel-removal teardown: the canonical chat host never unmounts, so the resolved-session-change clear (`clearScrollTargetForSession(previousSessionId)`) is what stops a delayed target for A consuming after a switch to B and back. The regression test must hold the target in the delayed-DOM state across the swap.
