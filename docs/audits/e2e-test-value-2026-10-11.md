# E2E test value and overlap audit

Status: Initial audit; proven consolidations implemented in the [cleanup ledger](e2e-test-value-cleanup-2026-10-11.md)
Reviewed: 2026-10-11
Source revision: `e8c1761cb5b7006b905c0aa995925372ce8664e1`

The suite contains obsolete scaffolds, repeated smoke checks, and tests whose assertions do not prove their stated behavior. Start with eight obsolete skipped definitions and six duplicate checks. Then repair false passes and consolidate repeated agent launches while carrying every distinct assertion into the surviving tests.

The immediately removable smoke checks are inexpensive. Larger runtime gains require work in task creation, clarification, and timed lifecycle tests. Removing useful transport, security, or mobile coverage merely because it resembles another test would weaken the suite.

The inventory covers all 1,382 spec files and 249,083 lines under `apps/web/e2e/tests`. Playwright discovery succeeded with no collection errors and listed 4,113 configured test instances across those spec files: Chromium 2,854, mobile Chrome 1,060, containers 152, auth 37, routing 9, and Kubernetes compatibility 1. These include skipped and opt-in cases; they are not a count of executed CI tests. Suite-wide static screening was followed by focused reading of candidates, shared helpers, relevant production owners, existing tests, and contract/history evidence. This is not a semantic verdict on every individual test.

Paths below are repository-relative. Line numbers identify the audited revision. [The CSV inventory](e2e-test-value-inventory.csv) records every spec and screening signals. A flag in the CSV is a discovery clue, not a deletion decision.

**Disposition:** D means delete obsolete code; C means consolidate into a named keeper; F means repair assertions or setup; R means retain a distinct contract. The findings below preserve the original source snapshot and recommendations. The cleanup ledger records implemented decisions, verification and remaining work, including cases whose eventual keeper differs from this initial recommendation. Unresolved equivalence means retain.

## Obsolete definitions

Their `setExecutionPolicy` helper at line 5 always throws because the old API no longer exists. The modern browser keeper is `office/workflow-quorum-transitions.spec.ts`, which drives the actual move endpoint and checks guarded approve/reject transitions, role attribution, and re-entry. Do not remove the four active status/comment tests in the same legacy file: their HTTP contracts still exist. Rename or move those only after matching backend coverage. The file's latest change was PR #3392; its remaining terminal-step setup protects a separate approval gate.

2. **D: Default-project onboarding expectation.** Remove `office/projects.spec.ts:17`, “onboarding creates a default project.” Its own comment explains that projects are intentionally created on demand and `officeSeed.projectId` is empty. It waits for a contract reversal rather than testing current behavior. Keep the active Projects page check and project creation/assignment coverage.

3. **D: Two permanently skipped real-agent resume scaffolds.** `session/session-resume-real.spec.ts:26` and `:44` unconditionally skip even when `KANDEV_E2E_REAL_AGENTS=1` is set. Neither contains executable verification. Remove the empty suite and keep any desired live-agent coverage requirement in the backlog. Mock resume tests do not prove live provider conversation continuity; deleting this scaffold does not resolve that gap. Its latest change was PR #2412, a managed-runner routing change.

4. **D: Empty branch-fetch error scaffold.** Remove `setup-timeouts.spec.ts:10`, “GitHub branch fetch network failure shows error.” Its body is empty and its comment names a removed `github-url-error` selector. Keep the active health-indicator test. A future per-chip branch failure test must assert the current disabled pill and tooltip; the dead scaffold provides no present protection.

These eight definitions are already skipped, so deleting them improves maintenance and reported inventory rather than execution time.

## Duplicate checks and consolidations

5. **C: Preferences page smoke.** `office/config-sync.spec.ts:35` repeats `office/dashboard.spec.ts:60`: same route and same Preferences title assertion. Keep the dashboard check, or move that assertion into a functional Preferences scenario, and remove the Config Sync copy. No export or import behavior is exercised by this check.

6. **C: Inbox smoke and API availability.** `office/inbox.spec.ts:15` is subsumed by `office/realtime-inbox.spec.ts:5`, which checks both the Inbox title and Mine tab. Keep the latter. The API tests at `inbox.spec.ts:5` and `realtime-inbox.spec.ts:16` make the same request and only assert a defined response; retain one until a stronger endpoint keeper exists. “Starts empty” does not check emptiness, and “returns count” does not check a count. The surviving file's “Real-time inbox updates” describe block also performs no mutation or event-driven update: rename it to smoke coverage or add a real live-update scenario. The initial-approvals check at `inbox.spec.ts:10` is another availability check, not an empty-state proof.

7. **C: Activity API smoke.** `office/dashboard.spec.ts:12`, “activity feed is defined,” repeats `office/activity-page.spec.ts:12`, “activity API returns data.” Both call `listActivity` and assert only defined. Keep one endpoint check beside the Activity page, preferably strengthened with a seeded event and its identity, and remove the dashboard duplicate.

8. **C: Archive popover geometry.** `task/archive-confirmation-preference.spec.ts:6` and `task/confirmation-text-hierarchy.spec.ts:88` share the same title and assertions: stable sidebar row height before/open/after, width greater than 256px, containment on both axes, no horizontal document overflow, and Cancel closing the popover. Keep the text-hierarchy case: it also waits for finite animations and checks description wrapping. It uses the same 900px width and a shorter, more constrained viewport height. Preserve the geometry attachment if useful, and retain the other preference/warning tests; those assert distinct behavior.

9. **C: Git commit persistence after refresh.** `git/git-changes-panel.spec.ts:1613`, “commits persist after page refresh,” repeats the flow at `:1677`, “multiple commits persist after page refresh.” Keep the three-commit scenario, including every subject and SHA assertion before and after refresh. Both use the same standard profile, repository, Changes panel, and reload path. Retain the adjacent realtime commit-update case: event delivery and reload hydration are different risks. The multiple-commit setup also stages only its own files, avoiding the single-commit case's `stageAll()` exposure to shared-repository leftovers.

Items 5–9 remove six duplicate test definitions while leaving equivalent assertions in existing keepers. This is the small first batch, separate from the deeper consolidations below.

10. **C: Task creation smoke and repeated launch.** In `task/create-task.spec.ts`, fold `:442` “opens create task dialog,” `:550` “can fill in task title and description,” `:567` “start agent: creates task, starts session, navigates to session,” and `:762` “create and start agent: session completes with task environment created” into one launch journey. Either launch case can be the keeper, but it must contain the union: dialog opening, input values, enabled Start action, dialog closure, task URL, visible sidebar/terminal/files/chat, sidebar title, initial user message, mock response, idle state, Turn Finished grouping, Review step, exactly one session, and ready environment linked to the task. These are not currently interchangeable without moving assertions. Preserve the plan-mode variants, workflow memory/workspace isolation, credential compatibility, and agent selection tests. The API case at `:804` additionally checks `session.task_environment_id`; retain or migrate that boundary proof rather than silently losing it.

11. **C: Clarification carousel startup overhead.** `chat/clarification.spec.ts:754`, `:830`, `:854`, `:882`, `:903`, `:925`, and `:1398` each start an agent to check a small part of the same three-question flow. Consolidate those seven cases into one journey, preserving: initial three-step/one-card structure, active and unanswered state, progress count, Back disabled on the first question, Submit disabled while incomplete, option-driven advance, answered markers, Back restoring the selected answer, direct step navigation, Submit enabled only after all answers, and submission unblocking the agent. Check incomplete submission before filling the missing answers. Keep shared-context layout, markdown rendering, keyboard focus/shortcut scope, stale-question races, deferred answers, escape behavior, and failure handling as distinct regressions. A long file alone does not justify dropping them.

12. **C: PR-specific warning captures.** `settings/pr3473-qa-visual-capture.spec.ts:9` and `settings/mobile-pr3473-qa-visual-capture.spec.ts:10` run in the default suite. Their warning interactions overlap `settings/no-silent-model-fallback.spec.ts` and its mobile counterpart. Move the exact saved start-model label assertion into those keepers before gating or removing the PR capture scenarios. Preserve desktop tooltip visibility/layering and mobile tap-open drawer containment; the two interaction forms are independent. Keep `session/model-mismatch-warning.spec.ts` because actual executor fallback and persisted launch warnings differ from a host-probe advisory.

13. **C: Repeated recovery settings API checks.** `office/recovery.spec.ts:4`, `:15`, `:27`, and `office/dashboard.spec.ts:67` repeatedly read or write `recovery_lookback_hours`. Consolidate into one HTTP contract scenario covering schema, a non-default persisted value, and writing 24 back. The existing “reset to default” case explicitly writes 24; it does not test a reset operation or default restoration when the field is omitted. Restore the original value in `finally`, as the dashboard test already does. API-only recovery tests leave settings in the shared Office workspace; the fixture resets the CEO but does not reset all workspace settings.

## False passes and fallback behavior

14. **F: Observation helpers perform recovery.** `e2e/pages/session-page.ts:183` (`waitForLoad`) periodically reloads the page. `:244` (`waitForChatIdle`) also reloads and clicks the recovery Resume button. They eventually assert readiness, but can hide a lost hydration/state event or failed automatic resume. Separate passive waits from explicitly requested manual recovery. Tests claiming automatic recovery, live updates, or navigation continuity must assert those outcomes before any extra reload or Resume click. Keep ordinary retrying observations and explicit user recovery scenarios. Do not mechanically remove all catches: the problem here is intervention changing the outcome being observed.

15. **F: Auto-start has no independent launch oracle.** `session/auto-start-session.spec.ts:5` only calls the two helpers above. It can succeed after their intervention, and it never verifies the intended initial prompt or exact session count. Assert the initial no-session condition, automatic launch, exactly one resulting session, the expected mock response and user prompt, and idle state using passive waits. Keep the contract; remove the fallback assistance from this proof.

16. **F: Approval test never calls the approval endpoint.** `office/agent-governance.spec.ts:112`, “decide approval endpoint returns updated approval on approve,” manually patches agent status from pending to idle. The rejection case at `:141` patches pending to stopped. Neither creates an approval or submits a decision. Delete their approval-coverage claim; either remove them as redundant status checks or replace them with a real agent-authenticated approval flow. Backend keepers exist at `internal/office/approvals/service_test.go:170` and `:198`; security tests at `approvals/handler_security_test.go:148`, `:169`, `:190`, and `:212` independently cover worker/self/cross-workspace restrictions and JWT identity. The current E2E header's assertion that runtime JWTs are unavailable is stale: `office/workflow-quorum-transitions.spec.ts` already mints them through supported E2E helpers. Preserve HTTP auth wiring if consolidating into a real flow.

17. **F: Missing arrays become valid empty arrays.** `office/agent-governance.spec.ts:105` uses `resp.approvals ?? []`, and `:161` uses `inbox.items ?? []`; both can pass with missing response fields. The latter promises a pending approval item but never checks for one. `office/recovery.spec.ts:44` and `:52` similarly turn missing `runs` into an empty array, then iterate zero entries. Seed a real record, require the actual response field, assert its identity and lifecycle, and then validate shape. For APIs that deliberately encode empty collections as null, preserve that documented contract instead of imposing a blanket array rule.

18. **F: Config Sync barely checks export or import.** `office/config-sync.spec.ts:13`, “export config includes workspace settings,” accepts `{}` because its JSON string has positive length. The tests at `:5` and `:20` check only object/defined; `:26` exports then imports unchanged state and checks a defined result. These should move to meaningful HTTP/service contracts or be replaced with a sentinel value that travels through the real export/diff/import path. Existing backend proof is substantially stronger: `internal/office/config/service_test.go:105` checks every exported field; `config/handler_test.go:122` verifies the HTTP envelope and persisted seeded entities; `config/sync_test.go` verifies diffs, import/pruning, idempotence, writes, errors, and round trips. The modern `office/office-config-sync-provider.spec.ts` is worth retaining: it checks reconciliation results, actual rows, idempotence and rendered status. That provider path is distinct from filesystem-to-database sync and is not a replacement for its contract.

19. **F: Workflow column tests do not check columns.** `workflow/workflow-steps.spec.ts:5` and `:33` assert that cards are visible somewhere on the board. They pass if both tasks appear in the wrong columns. Consolidate into one test using `KanbanPage.taskCardInColumn(title, stepId)` or an equivalent scoped locator, checking each intended column and absence from the previous one. Required seeded steps should fail setup if missing, rather than skip. Keep rejected moves, sidebar feedback, and WIP behavior as separate contracts.

20. **F: Project picker can pass without assignment.** `office/property-pickers.spec.ts:125` returns successfully if no project option exists. Its “onboarding creates one” comment contradicts current onboarding. Create a project explicitly, select that exact project, check the persisted task link and rendered label, clear it, and verify persistence after clearing. This is an assertion repair, not obsolete UI coverage.

21. **F: Reviewer and approver setup failures become CEO fallback.** `office/property-pickers.spec.ts:258` and `:302` swallow `createAgent` failures and select the shared CEO instead. This hides failures in setup and changes the identity under test. Seed a specific agent and let creation failure fail. The reviewer case checks added initials but stops after clicking Remove; the approver case has no final add/remove outcome assertion. Verify the assigned ID, visible chip, persisted removal and chip absence. Retain distinct reviewer and approver paths even if common setup is shared.

22. **F: Empty-state titles assert availability only.** `office/costs.spec.ts:6` promises zero cost and `:11` promises empty budgets, but both merely require defined responses. Likewise the Inbox “initially empty” checks do not assert emptiness. Use isolated seeded state and exact totals/collections if the empty state is a real requirement; otherwise consolidate and accurately name a minimal endpoint smoke. Keep the costs live-refetch test at `:23`, while strengthening it with the changed rendered breakdown when appropriate. A network refetch alone does not prove that the correct value reached the user.

23. **F: Missing normal fixture prerequisites become skips.** Conditional skips in `workflow/workflow-steps.spec.ts`, branch-selection and GitHub URL tests can turn a broken baseline workflow/executor/branch fixture into a green run with less coverage. Required mock prerequisites should be deterministic and fail setup. Preserve skips for deliberately opt-in live agents, missing local Docker, and documentation capture; those express actual execution boundaries. Changing every skip would incorrectly pull paid or platform-specific integration work into the default suite.

24. **F: Shared state changes need explicit restoration.** Office uses worker-scoped onboarding/API fixtures. Its `testPage` fixture resets task/session state, while API-only tests need not request `testPage`; the unconditional beforeEach only resets the CEO name/status. Recovery settings, governance flags, and entities can therefore outlive an API-only case. Give mutation cases an isolated owner or `finally` cleanup. Do not preserve weak assertions merely because they tolerate other tests' leftovers. Consolidating settings transitions should make cleanup unconditional on assertion success.

25. **F: Queue tests do not prove the queued payload ran.** `chat/message-queue.spec.ts:91`, `:134`, and `:347` end by checking an idle composer after showing a queue chip. Losing the queued message can still lead to idle. Assert the exact queued user message and its corresponding mock response or persisted delivery before checking idle. Retain keyboard and button entry paths, and task-page versus Quick Chat wiring; those are different triggers and hosts. The plan-mode case at `:808` additionally protects system-context leakage and should keep that assertion.

## Tests that belong outside ordinary browser execution

26. **C: Authentication screenshot generator.** `auth/auth-screenshots.spec.ts` explicitly describes itself as a manual screenshot generator, yet has no capture opt-in gate. Its seven cases match the default auth project, restart the backend into a dedicated database, and include unverified render-settling dwells. Gate it with `CAPTURE_DOCS_MEDIA=1`, matching `settings/executors-docs-screenshots.spec.ts` and `plugins/plugins-docs-screenshots.spec.ts`. Preserve useful auth assertions in `auth/auth-lifecycle.spec.ts` and the relevant account/user tests before excluding capture-only flows. “Member segregated view” takes screenshots without asserting exclusion of the private workspace; it must not be treated as a security isolation keeper.

27. **C: Fixture lifecycle unit tests in the E2E project.** `system/backend-fixture-lifecycle.spec.ts` contains eight useful Node helper tests using fake ChildProcess/EventEmitter objects, filesystem operations, and injected cleanup callbacks. They do not exercise application UI. Move them to a lightweight harness test target or the unit runner after separating Playwright-bound imports as needed. Preserve spawn/exit failure, cleanup ordering, ownership of the exact temp directory, and SSH shutdown proof. Their sampled test bodies total only 0.253 seconds, so this is routing/ownership cleanup rather than an important runtime win.

28. **C: Harness recovery and navigation setup checks.** `session/session-page-recovery.spec.ts` builds a fake DOM with `setContent` and listeners to exercise recovery-helper behavior. Keep its disabled-button and duplicate-click protection, but use a lightweight browser fixture rather than starting a real backend. `task/task-navigation-responsiveness.spec.ts:28` tests real git fixture setup preserving a dirty shared checkout; it belongs in a harness integration target, while the actual navigation responsiveness cases remain browser E2E. These are valid tests of the harness, not product tests to discard.

29. **C, conditional: Ordinary API CRUD smoke.** Examples in `office/routines.spec.ts` and `office/execution-stages.spec.ts` exercise HTTP creation/listing/status validation without a browser. Prefer backend HTTP integration coverage for the CRUD matrix and one meaningful UI journey. Keep the current E2E cases until an equivalent keeper covers HTTP route wiring, validation, persistence and errors; service-unit proof alone does not establish all of those boundaries. This recommendation does not apply indiscriminately to CLI, authenticated runtime, or real executor tests.

## Valuable similarities to retain

34. **R: Mobile, provider, platform and mode distinctions.** Retain mobile tests when they exercise taps, drawers, focus, viewport containment, pointer scope or different navigation. Shared setup can reduce maintenance without deleting those checks. Jira and Linear share concepts but have separate credentials/routes. Cursor auth and plugin settings persist different keys. Regular-mode workspace deletion deliberately restarts with Office disabled and tests a different deletion route. Docker, SSH, remote Docker and Kubernetes specs can be API-only while still exercising real ownership, transport, process and secret-handling boundaries. CLI agentctl tests cross the real binary-to-HTTP boundary. Agent MCP configuration tests in `settings/config-management.spec.ts` test tool dispatch, not ordinary CRUD. Long runtime continuity/delivery tests protect identity and accounting across restarts; similarity to simple resume is not equivalence.

35. **R pending resolution: Skipped real regressions.** `session/maximize-sidebar-switch.spec.ts:64` protects client-side sidebar switching into a maximized layout, unlike a full-page navigation test. Its flake needs repair or an explicit unresolved regression record. `office/agentctl-cli.spec.ts:615` names a CLI/backend workflow payload mismatch; `:671` names a blocked approval setup. Do not silently declare these obsolete. Existing skips for paid/external agents or absent host tools likewise need to preserve their purpose. Empty TODO scaffolds can go, but a disabled executable regression needs a clear contract disposition.

36. **R: Unique data and purposeful source checks.** The random UUID/name suffixes inspected isolate repositories, files, network names or test identities; they are not evidence of arbitrary random scenario selection. Preserve isolation. Assertions hidden in helpers, Node assert, or multiline expect.poll are not assertion-free tests. Source inspection can protect required keys, bytes or architecture boundaries, and must be judged by its oracle. Optional popover reopening to perform the same user action differs from swallowing a failed API setup and selecting another identity. `fixtures/test-base.ts:40` restricts backend recovery to fetch transport errors during idempotent setup operations; keep that recovery distinct from helper intervention inside a product-behavior assertion.

## Cleanup order and verification

1. Remove the eight dead definitions and six duplicate checks in items 1–9. Run each keeper with its affected siblings; verify discovery counts and CI file routing. Removing skipped placeholders must not be presented as measured runtime improvement.
2. Repair items 14–25, beginning with passive recovery observation, actual approval decisions, deterministic project/participant setup, response-field assertions and scoped board columns. A test that passes after its claimed behavior is deliberately broken is not a keeper. Use sequential, reversible mutations of the relevant production owner to prove repaired assertions fail for the intended reason.
3. Consolidate task creation and the clarification carousel, carrying the complete assertion unions described above. Move any distinct API association proof before removing its old case. Run both keepers and affected siblings before and after the consolidation.
4. Gate media capture and route harness-only tests into targets that actually run in CI. Preserve auth, browser helper and real git cleanup contracts. Regenerate explicit duration-aware shard manifests/timing profiles where the routing requires it.
5. Optimize the LSP frontend timer first. Consider backend lifecycle lane changes only after verifying their representative end-to-end contract remains required. Compare repeated CI samples and the slowest shard, not just total test seconds.

For local Playwright verification, run from `apps/web` through the guarded runner, one worker per shard, without overlapping full suites. For example, `pnpm e2e:raw --project=chromium tests/task/archive-confirmation-preference.spec.ts tests/task/confirmation-text-hierarchy.spec.ts` verifies the archive keeper pair. Use the auth/mobile/containers projects for their own coverage and existing opt-in prerequisites. Do not combine a paid/live agent run with ordinary audit verification.

Validation for this audit: package installation and successful Playwright `--list --reporter=json`; source/contract/history comparison and existing CI artifact analysis. No browser execution, baseline rerun, production mutation, deletion, or timing experiment was performed. Recommendations involving a new keeper, a clock, or a test-target move remain conditional on that focused proof.
