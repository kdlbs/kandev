# ADR-2026-10-11-honest-delivery-loss-recovery: Preserve missing delivery history during native restoration

**Status:** accepted
**Date:** 2026-10-11
**Area:** protocol

## Context

An authenticated journal can survive a host crash with an acknowledged cursor
ahead of the backend's surviving receipt. Pruned events cannot be replayed.
Current recovery requires contiguous cursor coverage and therefore cannot
initialize the original native conversation while supported reads cannot
supply that interval. In the motivating incident, offline forensic recovery
found all five original events in unused bbolt pages. Restoring validated replay
recovered them through ordinary projection on the original generation. Such
page survival is not guaranteed; it neither proves irreversible event loss
nor establishes a bootstrap cursor bug.

Before this fix, the SQLite writer used WAL with synchronous NORMAL. SQLite documents that a
committed transaction in this mode can roll back after power loss, whereas FULL
adds a WAL synchronization at commit. A journal that durably deletes events
after such an acknowledgment can outlive their backend receipt. This is a
supported failure mechanism, not proof of ordering for a particular crash.

## Decision

Use FULL synchronous durability for backend SQLite writers before permitting
journal acknowledgments. Preserve projection-before-acknowledgment, batching,
and explicit failure handling. No per-request downgrade or operator toggle
weakens this boundary.

Record historical intervals unavailable through supported reads separately from receipt and
projection cursors. When the original owner is proven dead, the native
conversation and every unresolved submission are authenticated, and the old
stream is fully acknowledged with no retained suffix, a checkpointed recovery
may restore the same native conversation on a fresh harness/delivery generation.
Old cursor values and unknown outcomes remain honest. Restoration is not proof
that the missing event contents, tool outcomes, or prompt completion are known.
Complete validated original-event replay takes precedence over this fallback.
When original events remain available, ordinary receipt/projection takes
precedence without a loss successor or unavailable-output notice. Automated raw-page
forensics is not part of the recovery contract.

Reuse the existing SQL restore checkpoint to allocate the successor under the
pinned recovery identity. Guarded retained inspection verifies the exact gap
and dead owner; successful native retirement seals the empty predecessor. It does not relax ordinary
`RolloverStream` requirements. Admission of a new instruction waits for native
verification and committed recovery. Existing automatic recovery and Resume
share this transition; no prompt is generated by recovery itself.

## Consequences

Acknowledgment has the same persistence boundary as the receipt it releases.
SQLite writes incur additional synchronization cost; delivery batching limits
the number of commits but does not guarantee a latency bound. Existing lost
history remains unrecoverable and visible even after the composer is usable.

The existing checkpoint carries additive gap evidence with SQL and journal
persistence, positive mixed-version proof,
exact original-process death proof, and convergence tests for every store
boundary. A surviving or unverifiable owner remains blocked. A retained suffix
is preserved and is not covered by this initial recovery exception.

## Alternatives considered

- Raise the old SQL cursor to the journal ACK: falsely claims receipt and
  projection of unavailable events and conceals possible tool or terminal loss.
- Resume the old stream from its high-water mark without recording loss:
  silently skips unavailable history and reproduces the same gap on restart.
- Permanently block every pruned gap: preserves honesty but strands a verified
  saved conversation even when safe prompt-free restoration is possible.
- Delete the journal or create a new native conversation: loses evidence and
  violates conversation continuity.
- Keep NORMAL and checkpoint before each ACK: adds a second persistence barrier
  whose connection ownership, concurrent writes, and failure rules must be
  maintained beside transaction commits. FULL supplies the simpler boundary.
