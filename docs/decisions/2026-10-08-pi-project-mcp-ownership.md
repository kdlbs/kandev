# ADR-2026-10-08-pi-project-mcp-ownership: Fence shared Pi project MCP ownership

**Status:** accepted
**Date:** 2026-10-08
**Area:** backend

## Context

ADR 0020 made `<workspace>/.pi/mcp.json` the project-local injection point for
Pi because `pi-acp` does not reliably pass session MCP definitions through to
the Pi process. The file is shared by executions that use the same workspace.

The current lifecycle path records a file created by an old execution and
removes that path unconditionally. A successor can materialize a new file with
its own agentctl port before the old execution is cleaned up. The old cleanup
then deletes the successor's configuration. Conversely, an existing user file
must not become Kandev-owned merely because Kandev merged its server entry.

The same boundary must cover launch, workspace promotion, resume/recovery,
backend restart, failed launch rollback, and concurrent cleanup without
writing a user-level Pi configuration.

## Decision

Keep Pi's project-local `<workspace>/.pi/mcp.json` contract and its existing
`streamable-http` and `eager` generated Kandev entry. Add lifecycle ownership at
the shared project-file boundary:

1. Serialize materialization and teardown decisions for each project MCP
   resource with an in-process mutex and an OS advisory lock in Kandev's
   private temporary directory. The lock is derived from the canonical path,
   is not written into the workspace, and covers overlapping backend processes
   during restart.
2. Track claims per execution and the current generated generation using only
   the normalized path and a SHA-256 fingerprint. A successor claims the
   resource before its materialization is visible to cleanup.
3. Treat an existing merge file as user-owned unless its current bytes match a
   known Kandev generation from a related execution. Known Kandev files can be
   advanced to the successor generation; user or unknown files are merged but
   never tracked for deletion.
4. On teardown, release only the ending execution's claim. Remove a file only
   when no claim remains, Kandev ownership is known, and the current bytes
   still match the generated fingerprint. User edits, malformed/unknown files,
   symlinks, and successor claims fail closed and remain untouched.
5. Persist the non-secret claim records through the existing
   `executors_running.metadata` projection and hydrate them during recovery.
   Failed or incomplete recovery cannot establish ownership and therefore
   cannot delete the file.
6. Use the same release operation for pre-registration launch rollback and
   duplicate-execution rollback. Do not disable cleanup globally and do not
   add a user-level Pi config entry.

## Consequences

Old execution cleanup cannot delete a successor's current project MCP file,
including when cleanup follows materialization before the successor is added to
the execution store. Pure Kandev-owned files can still be reclaimed after the
last claim ends. User files retain their existing servers and unrelated fields
and are never deleted by Kandev teardown.

The lifecycle manager keeps a small in-memory resource index and performs a
fingerprint read before owned deletion. Unknown or user-modified files may be
left behind after a crash or incomplete recovery; this is an intentional
fail-closed trade-off that protects user configuration. Ownership metadata is
non-secret but includes a normalized workspace path, so it remains internal to
the durable execution record.

## Alternatives Considered

- **Only compare the cleanup file contents or port:** Rejected. It does not
  protect a pending successor whose generated bytes happen to match, and it
  does not represent shared claims or restart recovery.
- **Disable project-file cleanup for every execution:** Rejected. It leaks
  Kandev-created files and does not distinguish user-owned content.
- **Write a Kandev sidecar into `.pi` or modify `~/.pi/agent/mcp.json`:**
  Rejected. A sidecar pollutes the user workspace and adds another stale-file
  lifecycle; user-level configuration violates the project-local injection
  contract and can cross task/session boundaries.
- **Use a fixed delay or retry cleanup:** Rejected. Timing cannot establish
  ownership and would leave the same race under load or restart.
