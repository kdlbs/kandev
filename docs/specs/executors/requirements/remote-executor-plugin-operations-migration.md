# Remote executor plugins: operations, launch policy, and preparation requirements

## Overview

What an operator needs to run a worker-pool provider for a long time: a bounded view of its health and a typed way to
act on it, a launch-policy requirement that agentctl enforces, a workspace preparation contract that new strategies
can use without another core change. Each is an opt-in
[capability](remote-executor-plugin-capability-versioning.md).

## Terminology

- **Provider status:** A bounded, non-secret read of a provider's nodes and capacity.
- **Maintenance action:** A typed operator action from a closed set, applied by the provider and recorded by the host.
- **Launch policy:** A generic requirement that agent processes start under a sandbox or wrapper policy.
- **Preparation hints:** Non-secret, uninterpreted key-value intent that the host passes to a provider that prepares the workspace.

## Requirements

### REQ-EXECUTORS-PLUGIN-OPS-001: Provider status, inventory, events, logs, and maintenance

**Intent:** Operators see provider health in Kandev and act on it through one audited route.

#### Acceptance criteria

- **AC-EXECUTORS-PLUGIN-OPS-001.1:** When a provider requires `provider_operations`, an administrator read shall return provider status with at most 200 nodes, each with an opaque non-secret ID, a state (`ready`, `draining`, `quarantined`, `down`, `unknown`), capacity by resource class, and a reason code. An installation can declare several providers; every provider-operations read and maintenance route shall take a `provider_key` selector, which may be omitted only when the installation declares one provider, and an unknown key shall be `not_found`. Nodes shall be ordered by node ID in byte order. The response shall be at most 64 KiB, and an oversize response shall be rejected, never truncated silently.
- **AC-EXECUTORS-PLUGIN-OPS-001.2:** An inventory read shall page provider-known environments, ordered by provider ID in byte order (an opaque provider-issued cursor of at most 256 bytes, default and maximum page size 100; an empty cursor starts the read and an absent next cursor ends it) with each environment's provider ID, host environment reference, and state. The host shall match an entry to a host record by the triple of installation, `provider_key` and provider ID, so equal opaque IDs from two providers never match each other's records, shall mark entries it does not know as `unrecognized` and shall change no host record from this read.
- **AC-EXECUTORS-PLUGIN-OPS-001.3:** The provider shall publish events through a host callback with a kind from a closed set (`node_quarantined`, `node_recovered`, `capacity_low`, `capacity_restored`, `placement_stalled`, `provider_degraded`, `provider_recovered`, `maintenance_completed`), a severity (`info`, `warning`, or `critical`), an opaque subject ID, a message code matching `[a-z0-9_.]{1,64}` with at most 8 parameters (keys `[a-z0-9._-]{1,32}`, values at most 64 bytes, no secret), and a dedupe key of at most 128 bytes. The host shall render the kind as localized text under `executors:pluginEvent.<kind>`, shall show the code only as a parameter, and shall treat an unknown code as the kind's generic text.
- **AC-EXECUTORS-PLUGIN-OPS-001.4:** The host shall validate an event first, then drop a duplicate (same installation, kind, and dedupe key within five minutes; an empty dedupe key is never a duplicate, and a dropped duplicate consumes no rate-limit token), then apply a limit of 30 per minute per installation (a token bucket of burst 30 refilled one token every two seconds, held in memory and reset by a backend restart, as is the dedupe map), and deliver the rest through the existing notification service to the users who own a notification provider and are instance administrators (the same check as the administrator routes; the default user when authentication is not enforced), because a plugin installation is instance-wide and has no workspace audience. Delivery uses a new notification event type `executor.plugin_event`, added to the notification service's closed event lists and not added to any default subscription or back-filled for existing providers, so an administrator opts a provider in under the notification settings, and a provider that is not subscribed receives nothing. The title and body are built by the host from a fixed English text per kind (as other notification messages are) with the message code and parameters appended as `key=value` pairs and never any provider text; the payload carries the kind, severity, subject, code, and parameters, and the web client localizes it under `executors:pluginEvent.<kind>`. An event with no administrator recipient (including a recipient lookup that fails under enforced authentication) or with no subscribed provider shall be dropped and counted with the outcome `dropped_no_recipient` or `dropped_no_subscriber`, and shall never reach another account. An event shall never carry a secret, a log line, or free text.
- **AC-EXECUTORS-PLUGIN-OPS-001.5:** A log read shall return at most 500 lines and 64 KiB for one environment or node, shall pass the host's secret redaction, and shall be limited to administrators.
- **AC-EXECUTORS-PLUGIN-OPS-001.6:** When a provider requires `provider_maintenance`, a typed action (`quarantine_node`, `readmit_node`, `drain_node`, `undrain_node`) with a subject ID, a reason code matching `[a-z0-9_.]{1,64}`, and an idempotency key matching `[A-Za-z0-9._:-]{1,128}` (an empty or malformed key or code is rejected as `invalid_request` before any provider call) shall be accepted only on a generic administrator route, only for the named installation, and shall return `applied`, `noop`, or `refused` with a reason.
- **AC-EXECUTORS-PLUGIN-OPS-001.7:** The host shall write a structured audit log line for each maintenance request, before the call (`requested`) and after it (outcome), naming actor, installation, action, subject, and outcome. A request that repeats an idempotency key of the same installation within 24 hours with the same body shall return the recorded outcome without a second provider call; with a different body it shall be rejected as `conflict` immediately, including while the first call is in flight. After 24 hours or a backend restart the key is forgotten and the request is a new one, which the provider treats idempotently by the key. A second request with the same installation and key that arrives while the first is in flight shall wait for it and return its outcome with no second provider call. Only `applied`, `noop`, and `refused` outcomes are recorded; a provider timeout (30 seconds), transport error, or `unavailable` or any other provider error (not `applied`, `noop`, `refused`) is not recorded, is returned to the caller as `unavailable` with the audit outcome `unknown`, and a replay of the same key and body calls the provider again.
- **AC-EXECUTORS-PLUGIN-OPS-001.8:** A provider that is disabled, unavailable, or at a different negotiated version shall return `unavailable` from these reads, and the host shall keep working without them.

### REQ-EXECUTORS-PLUGIN-LAUNCHPOLICY-001: Launch policy requirement

**Intent:** A profile can require that agent processes start under a sandbox policy, and a launch that cannot enforce it fails closed.

#### Acceptance criteria

- **AC-EXECUTORS-PLUGIN-LAUNCHPOLICY-001.1:** When a provider requires `launch_policy`, the profile `config` shall accept the keys `launch_policy` (`none`, `preferred`, or `required`; an absent or empty value is `none`) and `policy_id` (an opaque ID of at most 64 characters matching `[A-Za-z0-9._-]+`, required for `preferred` and `required`, and rejected when the policy is `none`), and shall validate them when the profile is saved and again before allocation.
- **AC-EXECUTORS-PLUGIN-LAUNCHPOLICY-001.2:** Before allocation the host shall reject `required` when the provider does not report support for the policy ID with the code `launch_policy_unsupported` and no allocation, and shall reject any policy other than `none` on a provider that does not require `launch_policy` with the same code. A `preferred` policy the provider does not support is not rejected and is recorded as `unwrapped`.
- **AC-EXECUTORS-PLUGIN-LAUNCHPOLICY-001.3:** The workspace descriptor shall carry `applied_launch_policy` (`none` or `applied`) and the applied policy ID. Policies are ordered `none`, `preferred`, `required`. The host shall reject a descriptor weaker than the profile: for `required`, anything but `applied` with the profile's policy ID. A profile of `none` or `preferred` accepts any descriptor.
- **AC-EXECUTORS-PLUGIN-LAUNCHPOLICY-001.4:** For `required`, agentctl shall refuse to start an agent process without the wrapper and shall report the failure, never falling back to an unwrapped start; a wrapper that is missing, not executable, whose specification does not parse, or that fails to execute before the agent process starts counts as unavailable for this rule (for `required` the session fails with `launch_policy_unenforced`, for `preferred` the start is unwrapped and reported `unwrapped`); the session shall fail with `launch_policy_unenforced`, and the environment shall be retained, not destroyed. For `preferred` it shall try the wrapper on every agent start, start unwrapped when none is available, and report on each start whether it did; the host shall record the latest outcome in the envelope.
- **AC-EXECUTORS-PLUGIN-LAUNCHPOLICY-001.5:** Wrapper discovery, placement, and node-local files shall stay in the provider and its worker; the provider gives agentctl the wrapper specification through the instance environment, and the host and agentctl shall handle only the policy ID and the outcome. The host shall not interpret node-policy files and this cycle adds none to the host or agentctl.

### REQ-EXECUTORS-PLUGIN-PREPARATION-001: Extensible workspace preparation

**Intent:** A new preparation strategy (mirror, sparse checkout, pull-request checkout) is provider-only work.

#### Acceptance criteria

- **AC-EXECUTORS-PLUGIN-PREPARATION-001.1:** When a provider requires `preparation_hints`, each repository intent entry shall carry a `checkout` of kind `branch`, `ref`, or `pull_request` with a value, optional `sparse_paths` (at most 64), and `hints`. The host shall build them from the profile `config` keys `checkout_kind` (default `branch`), `sparse_paths` (a newline-separated list; each line is trimmed of leading and trailing ASCII whitespace including a trailing carriage return, blank lines are skipped, and a duplicate after trimming is rejected; empty means the whole tree), and `hint.<key>` entries, applied to every repository of the launch, with no per-repository override. For kind `branch` the value is the task's branch for that repository, or its base branch when the task names none; for `ref` the value is the profile key `checkout_value`; for `pull_request` it is the number of the pull request linked to the task for that repository, and a repository without a linked pull request is rejected like a missing value. A profile of kind `ref` or `pull_request` for a task that names a branch, a missing value, a duplicate sparse path or hint key, an absolute or `..` sparse path, or a sparse path over 512 bytes shall be rejected at launch as `invalid_config` with a named reason and no allocation.
- **AC-EXECUTORS-PLUGIN-PREPARATION-001.2:** `hints` shall hold at most 16 entries, keys `[a-z0-9._-]{1,64}`, values at most 256 bytes, no secret. The host shall pass them through uninterpreted and shall include them in the operation input digest.
- **AC-EXECUTORS-PLUGIN-PREPARATION-001.3:** The provider shall return for each repository its ID, path, branch, head commit, applied checkout kind, and an opaque strategy label matching `[A-Za-z0-9._:-]{1,64}`. The host shall verify the set, the path containment in the workspace, and the commit format, and shall record the label of the first repository in position order, without interpreting it, and shall verify (length and charset only) and audit-log the others.
- **AC-EXECUTORS-PLUGIN-PREPARATION-001.4:** The host shall not change for a new strategy label or a new hint key. A provider that returns a repository the intent did not name shall be rejected under REQ-EXECUTORS-NATIVE-WORKER-003.
- **AC-EXECUTORS-PLUGIN-PREPARATION-001.5:** Credentials shall stay executor-owned, as in REQ-EXECUTORS-NATIVE-WORKER-003.

## Out of scope

- Converting or renaming records between authorities.
- Autoscaling, per-person quotas, fleet-management UI beyond the status read, and hostile-workload isolation.
- A per-node repository mirror itself; only the contract in REQ-EXECUTORS-PLUGIN-PREPARATION-001.
- **Profile migration from a built-in executor to a plugin (plan item M8; formerly REQ-EXECUTORS-PLUGIN-MIGRATION-001 and work order 15).** Cut by the owner on 2026-10-28 (Spec Review round 6, option b) and deferred to follow-up card `a8546b99-a348-461e-b39f-23993e118b73` ("Spec: executor profile migration (M8)"). Deferring it means the profile save API and the launch gate may change in a later contract change; this cycle adds neither a migration operation, the `executor_profile_migrations` table, a `migrated_to` profile key, an `authority` field on environment records, the `executor_migrating` failure code, nor the `after_migration_step` crash barrier. The cut text covered: enumeration of built-in environments by state, one authority per record, a freeze/drain/switch/rollback operation stored one row per source profile with a revision guard, a freeze gate at the two launch entries, resumability, retained plugin environments after rollback, and start outcomes per step. The card's starting defect list is: the drain waits only for `STARTING` sessions while a workspace-only `PrepareTaskSession` launch (`StartAgent=false`, session `CREATED`) passes the gate and can create a built-in record after the drain listed environments, and the drain candidate predicate (executor type versus profile) is unstated; the revision check before each destroy has no atomic "destroy started" boundary, there is no runner claim, per-environment progress or cleanup-failure retry rule, and no target-validity policy after start; `migrated_to` is written by whom, whether user saves preserve it, honoured only while the row is `done`, and the outcome when the target is deleted (the owner left this decision to the card); a replayed start versus `conflict` in `done`, and a target that is not `plugin_remote` or a source that is itself a plugin profile. Closed decisions to carry: a start is `conflict` when `done` or on a different target mid-run, a `rolled_back` row is reused for a new operation, rollback is also allowed from `done`, retained plugin environments leave only through ordinary archive, delete, or reset, and the freeze gate belongs before runtime allocation in `launchPreparedSession` and `ResumeSessionWithOptions`. The resume entry that the card's gate must also cover is `attachRetainedPluginExecutor` (see the admission requirements).
