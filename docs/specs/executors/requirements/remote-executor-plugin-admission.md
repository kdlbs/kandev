# Remote executor plugins: admission and placement requirements

## Overview

Two launch-path behaviors that a worker-pool provider needs and the plugin path lacks today: a non-secret admission
context checked atomically before allocation, and placement that can wait in a queue beyond the current launch deadline.
Each is an opt-in [capability](remote-executor-plugin-capability-versioning.md). A provider declaring none keeps today's
behavior, including the rejection of unsupported workspace sharing (AC-EXECUTORS-PLUGIN-002.2). Shared
environments were cut from this cycle; see Out of scope.

## Terminology

- **Admission context:** Non-secret opaque identifiers and a priority describing who is launching.
- **Admission hook:** Host-side code that allows or denies, and names the scope to reserve capacity in, before any allocation. The default hook allows everything with no scope.
- **Pending placement:** A recorded state where the provider accepted the request but has not placed it.

## Requirements

### REQ-EXECUTORS-PLUGIN-ADMISSION-001: Identity and admission context

**Intent:** Quota and placement decisions see who is launching, and are enforced at every path that starts or resumes work.

#### Acceptance criteria

- **AC-EXECUTORS-PLUGIN-ADMISSION-001.1:** When a provider requires `admission_context`, provision and recovery requests shall carry task ID, session ID, workflow step ID, user ID, workspace (team) ID, project ID, and priority (`low`, `normal`, `high`). All identifiers shall be host-generated opaque IDs. No name, email address, label, resource class, or secret shall be sent; labels and resource classes are cut from this cycle (see Out of scope).
- **AC-EXECUTORS-PLUGIN-ADMISSION-001.2:** Withdrawn. The admission context carries no labels, and the host reads no `labels` or `resource_class` profile key for admission; a provider that declares such a key keeps it as an ordinary provider-owned property (see Out of scope, card 11c92feb-2b4c-4d05-8318-9aff24e2fa10).
- **AC-EXECUTORS-PLUGIN-ADMISSION-001.3:** The host shall run its admission hook before any provider allocation call on first launch and on a resume of a retained environment (the continuation of a pending placement keeps its reservation and is not an admission, AC-EXECUTORS-PLUGIN-PLACEMENT-001.11). Both entries shall call one shared gate function named `admitLaunch` (capability gate, `profile_too_large` measure, hook). A first launch reaches it from `validateLaunch`, which keeps rejecting `WorkspaceReuseRequired` and shared workspaces exactly as today (AC-EXECUTORS-PLUGIN-002.2). A resume reaches it from `attachRetainedPluginExecutor`, which on main runs before `validateLaunch` and is the only path that sees `WorkspaceReuseRequired` for a retained environment; it calls `admitLaunch` directly and never `validateLaunch`. At first launch the gate steps read the current manifest. At a resume they read the negotiated set recorded in the envelope: the capability gate checks that recorded set against the host registry, `profile_too_large` runs only when the recorded set is non-empty (AC-EXECUTORS-PLUGIN-PROFILE-001.8), and "a provider requiring `admission_context`" means that the recorded set contains it, so an environment allocated before this capability existed (empty recorded set, no identity snapshot) never calls the hook. A test shall enumerate the callers of both entries and fail when a launch or resume path reaches the provider without `admitLaunch`. The hook shall allow (with an optional scope and limit) or deny with a stable reason, and shall name the admission scope and its limit. The hook shall be called outside any database transaction with a fixed 5-second deadline; a deadline overrun is a failure under AC-EXECUTORS-PLUGIN-ADMISSION-001.6. Recovery of an admitted environment is not an admission.
- **AC-EXECUTORS-PLUGIN-ADMISSION-001.4:** An allow decision with a scope shall record a reservation in the same write that creates the operation, after that write has counted the live reservations of the scope under a lock whose key the host derives from the validated scope. Two launches competing for the last unit of one scope shall not both be admitted, on SQLite and on PostgreSQL, and the loser shall receive `admission_denied` with the reason `scope_full`. An allow decision with an empty scope (the default hook) records no reservation. A decision with a scope and a limit of zero or less is a denial with the reason `scope_full`. When that write fails for a store reason (not a lost race), the launch shall fail with `admission_unavailable`, nothing shall be allocated, no reservation shall exist, and no `Release` shall be sent to the hook.
- **AC-EXECUTORS-PLUGIN-ADMISSION-001.5:** A reservation shall be released exactly once, and only when absence is confirmed: on destroy confirmation (including a terminal launch failure, after the recovery destroy confirms), and on a provider `cancelled` or a refusal that allocated nothing. While a cancel is uncertain (AC-EXECUTORS-PLUGIN-PLACEMENT-001.4) or a destroy is unconfirmed, the reservation stays held.
- **AC-EXECUTORS-PLUGIN-ADMISSION-001.6:** A hook decision is valid only when it is exactly one of allow or deny, a deny carries a reason matching `[a-z0-9_.]{1,64}`, an allow carries either an empty scope or a scope matching `[a-z0-9._:/-]{1,128}` with an integer limit, and no error accompanies it. When the hook is unavailable, overruns its deadline, returns an error, or returns a decision that is not valid, a first launch for a provider requiring `admission_context` shall be denied with `admission_unavailable`; a resume follows AC-EXECUTORS-PLUGIN-ADMISSION-001.11 instead. A provider not requiring it shall not call the hook, and the host shall run no admission step for it.
- **AC-EXECUTORS-PLUGIN-ADMISSION-001.7:** Withdrawn. The provider response carries no applied resource class and the host persists none (see Out of scope).
- **AC-EXECUTORS-PLUGIN-ADMISSION-001.8:** A resume of a retained environment (stopped or live) shall keep the reservation it already holds and shall not take a second one.
- **AC-EXECUTORS-PLUGIN-ADMISSION-001.9:** A resume shall never take, count against, or write to the scope lock or the reservation count, because it keeps the reservation it already holds. A new launch counts the live reservations of the scope including those of environments being resumed or running, so the outcome of a resume racing a new launch for one scope shall be the same in either order: the resume goes ahead under AC-EXECUTORS-PLUGIN-ADMISSION-001.11 and never loses its reservation, and a new launch that no longer fits is refused as `admission_denied` with the reason `scope_full`.
- **AC-EXECUTORS-PLUGIN-ADMISSION-001.10:** The admission context shall be built from these sources only. The priority is the task priority mapped `critical` and `high` to `high`, `medium` to `normal`, `low` to `low`, and unset to `normal`. The project ID is the task's project ID, and the workflow step ID is the task's current step; either is the empty string when the task has none. No field of the context is omitted; an absent value is the empty string.

- **AC-EXECUTORS-PLUGIN-ADMISSION-001.11:** A resume shall keep the reservation the environment already holds and shall take no new one, and shall not count or lock the scope. For a provider whose recorded negotiated set contains `admission_context` the resume shall call the hook once, after the capability gate, with the identity snapshot recorded at admission (AC-EXECUTORS-PLUGIN-ADMISSION-001.12), and the outcome shall be: the hook allows (any scope), so the resume goes ahead with the recorded scope; the hook denies, so the resume is refused with `admission_denied` carrying the hook's reason, the environment and its reservation unchanged; the hook is unavailable, overruns its deadline, returns an error, or returns an invalid decision, so the resume goes ahead (the opposite of a first launch, because refusing would strand a running workload on a policy outage). An environment that holds no reservation (admitted with an empty scope) shall resume by the same rules: a deny refuses it and an allow with a scope records no reservation. The hook is called outside any transaction, so after it returns the resume proceeds only under the existing environment generation fence (ADR 2026-09-04): an environment reset, destroyed, or re-keyed meanwhile fails the fenced attach with the existing stale-generation error and nothing reaches the provider.
- **AC-EXECUTORS-PLUGIN-ADMISSION-001.12:** The host shall record, in the environment envelope at admission, the identifiers and values of the context (task, session, workflow step, user, workspace, project, priority), and recovery and resume requests shall carry that snapshot, so a restart or a later edit of the task never changes the identity, step, or priority a provider sees.
- **AC-EXECUTORS-PLUGIN-ADMISSION-001.13:** Withdrawn. There is no resource class list, no `default_resource_class`, and no `unknown_resource_class` refusal (see Out of scope).

Requirements PLACEMENT-001 and PLACEMENT-002 (queued and pending placement, refused provision) are in [placement](remote-executor-plugin-placement.md); they keep their IDs.

## Out of scope

- Resizing a live environment, preemption, and cross-provider failover.
- Autoscaling or provisioning machines.
- Per-person quotas as a feature: the hook is the seam and quota policy lives in whoever implements it.
- **Resource classes, labels, and provider-reported admission values (plan items N2, N3, N4 and the class parts of N7 of Spec Review round 7).** Cut by the owner on 2026-10-28 (option c2) because the admission hook ships as a seam with a default allow-all, so no first-release consumer needs them. Cut: the requested and applied resource class, the provider's `resource_classes` and `default_resource_class`, the class-aware allow-with-a-lower-class decision and the resume class comparison, the `unknown_resource_class` refusal, the `labels` context field and its encoding, and every provider value that the cut text read "from profile validation" (the placement deadline is now the fixed host value of AC-EXECUTORS-PLUGIN-PLACEMENT-001.2; launch policy IDs are declared in the manifest, AC-EXECUTORS-PLUGIN-LAUNCHPOLICY-001.2). **Consequence: adding them later is a second contract change** (new admission context fields, a response field for the applied class, an envelope field in the host budget, a carrier from profile validation to launch, which does not exist on main because the launch path never calls `ValidateExecutorProfile` and the validation result is only field errors, and a string-valued encoding for labels because profile config is `map[string]string`). The follow-up is card 11c92feb-2b4c-4d05-8318-9aff24e2fa10 ("Spec: admission resource classes and labels (cut N2-N4)"). Its starting defect list: which class value a resume compares (requested, applied, or a persisted admitted class), where provider-reported values are captured and stored, the labels encoding and the host-owned key list of PROFILE-001.7, an empty `resource_classes` list, a recorded class that has left the list at resume, and the class-validity check at profile save.
- **Workspace reuse and shared environments (plan item M1; formerly REQ-EXECUTORS-PLUGIN-SHARED-001 and the `workspace_sharing` capability).** Several owners attaching to one provider environment, with an owner set, a share epoch, holder and owner rows, per-owner agentctl instances, an owner cap, and destroy only on the last release. Why it was cut: Spec Review round 5 (the cap) found 17 open defects, about two thirds of them in this cluster, and the rules for owner release, `closing` retention, reclaim paths, and reservations contradicted each other; the Nomad plugin does not need cross-task sharing for its first release. The owner knowingly reversed an earlier decision to keep M1 in this cycle (decided 2026-10-28, option c2). **Consequence: adding M1 later is a second contract change** (a new capability, new envelope fields and owner rows, new failure codes, and amendments to ADMISSION-001.5 and the destroy and cleanup paths), not a drop-in. Until then workspace reuse and shared-workspace launches stay rejected exactly as today (AC-EXECUTORS-PLUGIN-002.2). The follow-up is card 99beef6d-530e-4afd-949b-1424fc9245df ("Spec: shared executor environments (M1) for plugins"). **That card must decide K5 first, before any design work: the reuse candidate set versus `WorkspaceReuseRequired` on main** (on main it selects attach-only preparation of the request's own already-ready task environment; the cut text instead pooled any matching ready holder across tasks of one principal). Its starting defect list: K1 owner-row deletion versus `closing` retention and the cleanup sweep; K2 owner and re-keyed holder rows reclaimed by the existing archive, startup, and reaper paths (ADR 0025); K3 deleting a non-holder or `releasing` owner's task releasing its reservation early; K4 reservation written with the operation versus in the owner row, and how many times the hook runs per request; K5 reuse candidate set; K7 `attaching` owner recovery (startup or periodic, `ListInstances` failure, ready-write fencing, replayed attach, duplicate-attach dedup); K9 holder-task delete check versus the multi-step durable delete job; K13 `owner_phase` naming; K15 two callers releasing the same owner; K16 stale-fence attach `conflict` versus PLACEMENT-001.9; K17 `max_owners` absent or non-positive and what proves absence on a failed `ListInstances`. The removed text is in git history (commit 4c6dcdf29c and earlier) of the former `remote-executor-plugin-shared-admission-placement.md` requirements and design.
