# Remote executor plugins: queued and pending placement requirements

## Overview

Continuation of [admission and placement](remote-executor-plugin-admission.md)
(moved here for the file size limit, IDs unchanged): placement that can wait in a queue beyond the current launch deadline, and
a refusal that releases the record. The terms of that document apply. Both are opt-in [capabilities](remote-executor-plugin-capability-versioning.md).

## Requirements

### REQ-EXECUTORS-PLUGIN-PLACEMENT-001: Queued and pending placement

**Intent:** A launch waiting for capacity is visible, cancellable, and bounded, and capacity refusal differs from placement failure.

#### Acceptance criteria

- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.1:** When a provider requires `pending_placement`, a provision response can report `queued` or `placing` with a closed reason code, an optional queue position, a progress phase, and a poll interval. The host shall persist the pending state and the operation before replying.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.2:** The host shall poll the provider within the clamped interval (2 to 60 seconds), shall record each phase change, and shall end polling at the placement deadline or when the record leaves `placement_pending`, whichever is first. The deadline is the fixed host value of 600 seconds added to the host clock time at which the first pending response was persisted, stored as UTC `deadline_at` in the pending state; a provider response cannot extend it, and a clock step is not compensated. A provider-reported deadline is cut from this cycle (see the Out of scope of the admission requirements). The deadline is evaluated at commit: the guarded write of every transition compares the host clock with `deadline_at` inside the write, so a completion committed at or before `deadline_at` is accepted and a completion whose write is attempted after it ends as `placement_timeout`, whatever time the provider produced it.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.3:** The task and session shall show a pending-placement status with the reason code and progress phase, and the existing stop action shall cancel a queued launch. While the operation is cancelling, the session shall stay `STARTING` with the label `cancelling` and shall move to its stopped state only when the provider says `cancelled` or a destroy confirms absence. Every new user-facing string shall be localized.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.4:** A cancel of a queued launch shall mark the operation cancelling under the claim and ask the provider to cancel. The outcome shall be `cancelled` (nothing allocated) or `already_placed`, and `already_placed` shall continue with the normal destroy. When the cancel call fails or times out, the operation shall stay cancelling and the host shall retry with backoff until the placement deadline, then run the existing recovery destroy by operation; it shall report cancelled only after the provider says `cancelled` or a destroy confirms absence.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.5:** When placement completes while a cancel is in flight, exactly one shall commit first. If the cancel commits first, a later completion is treated as `already_placed`, destroy runs to confirmation, the launch outcome is `placement_cancelled`, and the session ends in its existing stopped state with no allocation left. The completion commit is the guarded write that moves the record from `placement_pending` to `creating`; it is not readiness. If the completion commits first, the continuation of AC-EXECUTORS-PLUGIN-PLACEMENT-001.11 owns the launch. The agent start is itself a guarded transition of the session from `STARTING` to `RUNNING` (a compare-and-set on the session state). A Stop that commits before it makes the start a no-op: the environment is published ready without an agent start, the stop is processed as an ordinary Stop (the environment is preserved, as today), and the task shall not report the launch as cancelled. A Stop after the start has begun is an ordinary Stop of a running agent.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.6:** The host shall report failures as `capacity_refused` (the provider will not queue this request; this is the refusal reason of REQ-EXECUTORS-PLUGIN-PLACEMENT-002, one outcome), `placement_failed` (the provider tried and failed), or `placement_timeout`, and shall not merge them into a generic error.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.7:** After a backend or plugin restart the host shall resume polling the persisted operation and shall neither allocate a second environment nor lose the pending state. Startup recovery shall skip every record in the phase `placement_pending`, `cancelling`, `placement_failed`, or `placement_timeout` and leave it to the poller registry, which is the only owner of those records (it never attaches them, AC-EXECUTORS-PLUGIN-PLACEMENT-001.17); the authenticated-handshake recovery of AC-EXECUTORS-NATIVE-WORKER-007.2 applies only to a record that has reached `creating`. The operation claim named in this document is the existing environment recovery claim (`recoveryclaim`, keyed by the task environment and carrying the operation ID): a poll read holds no claim, and each transition (complete, cancel, fail, timeout) takes it. A continuation after a restart publishes through the guarded publication of AC-EXECUTORS-NATIVE-WORKER-007.3 under that claim.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.8:** A provider not requiring `pending_placement` shall keep the current synchronous launch and deadline, and a pending response from it shall be rejected as `conflict`.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.9:** Every host-originated launch failure code a user can meet (`capability_mismatch`, `missing_capability`, `unavailable` from the capability echo, `profile_too_large`, `invalid_config` with its named reason, `admission_denied`, `admission_unavailable`, `launch_policy_unsupported`, `launch_policy_unenforced`, `secret_reference_missing`, `secret_in_state`, `bootstrap_consumed`, `repository_inventory_mismatch`, `state_too_large`, `api_unreachable`, the three placement outcomes, each refusal reason, and `placement_cancel_pending`) shall appear in the task and session view as localized text that names the next step, shown with an icon and text and never by colour alone. The reasons of `admission_denied` and `invalid_config` are a closed set for display: `scope_full` and the named `invalid_config` reasons of this document set each have their own key under `executors:pluginFailure.<code>.<reason>`, and any other reason, including any hook-supplied reason, shows the generic text under `executors:pluginFailure.<code>` and never the raw reason string. The code `conflict` from a provider call is resolved by the host under AC-EXECUTORS-PLUGIN-PLACEMENT-001.15 and shall not reach the user.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.10:** The reason codes are the closed set `no_capacity`, `quota_wait`, `node_unavailable`, `maintenance`, and `other`; the progress phases are the closed set `queued`, `reserving`, `provisioning`, `starting_worker`, and `preparing_workspace`. A value outside a set shall be recorded as `other` (reason) or shown with the text under `executors:pluginPlacement.unknown` (phase), and a provider-supplied string shall never be displayed. A queue position is 1-based, and an absent or zero position means unknown. An absent or zero poll interval is 5 seconds before clamping. A response carrying more than one of a resource, a refusal, and a pending state, or none of them, shall be rejected as `conflict`.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.11:** When a poll reports that placement is complete and no cancel committed first, the host shall continue the launch from the persisted operation through the same post-provision path as a synchronous launch (bootstrap handshake, instance creation, and the agent start with the prompt already stored for the session) without a user action. This continuation is the delayed launch of REQ-EXECUTORS-PLUGIN-ADMISSION-001: it re-runs the capability gate against the negotiated set recorded at admission (a mismatch ends as `capability_mismatch` with a destroy), and it keeps the reservation taken at the original launch without a second admission. Until the environment is ready the session shall be `STARTING` with the pending-placement label (a session the user stopped meanwhile keeps its stopped state, AC-EXECUTORS-PLUGIN-PLACEMENT-001.5), and a failure shall give the session the failure code. The bootstrap nonce shall be valid until the placement deadline plus 600 seconds on that same host clock, and a completion whose write is attempted after `deadline_at` shall end as `placement_timeout` with a destroy (AC-EXECUTORS-PLUGIN-PLACEMENT-001.2).
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.12:** One poll loop per operation shall exist in a backend process, held in a registry keyed by operation ID and created again from the persisted state after a restart. A poll that returns a transport error or `unavailable` shall be retried at the next interval until the deadline. `rate_limited` shall retry at the next interval (a longer provider hint is honored up to the clamp). `not_found`, `denied`, `invalid_config`, `unsupported`, `expired`, `conflict`, and `cleanup_pending` end as `placement_failed`, each followed by the recovery destroy by operation, since only destroy confirms absence. A cancel retry shall wait 2 seconds, doubling to a cap of 30 seconds. After a restart the backoff restarts at 2 seconds, and a `next_poll_at` in the past means one poll immediately, not one per missed interval. A transition that cannot take the operation claim because another actor holds it shall not block: the poller retries it at the next poll interval and the cancel path at the next backoff step.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.13:** An archive, reset, or delete of a task whose record is `placement_pending` or `cancelling`, and a Stop of such a task, shall all call one request-cancel function. It finds the loop for the operation ID in the poller registry (the registry holds the in-flight marker after the claim is released, and recreates the loop from the record after a restart). For a record in `placement_pending` it takes the operation claim, waiting at most 5 seconds, and in one guarded write sets `cancelling` (and `cleanup_requested` for archive, reset, and delete, AC-EXECUTORS-NATIVE-WORKER-007.9), then starts the cancel path of AC-EXECUTORS-PLUGIN-PLACEMENT-001.4 (`already_placed` continues to destroy). For a record already `cancelling` it writes nothing and issues no second cancel RPC, so there is one cancel RPC in flight per operation ID in a backend process. When the claim cannot be taken within 5 seconds, Stop, archive, and reset return accepted after setting a cancel-requested flag on the registry entry, which the loop consumes at its next iteration (at most 60 seconds, or one backoff step of at most 30 seconds); the flag is in memory and a restart clears it, so the user repeats the action; delete in that case is refused as below. Each cancel attempt, each retry, and each terminal transition takes the claim for its own write and releases it afterwards; no claim is held while waiting between retries. The poller registry remains the only actor on these records: the cleanup sweep never calls the provider for them and only reads `cleanup_requested` to see that the cancel is still owed. A reset is complete when absence is confirmed: no other reset step runs before then and no second environment is created, and the next start launches a fresh one. A start for the task is refused with `placement_cancel_pending` while the record is `cancelling`, `placement_failed`, or `placement_timeout`, from the moment it enters the phase until it settles absent. A delete is refused with `placement_cancel_pending` in the same phases, and for a `placement_pending` record after starting the cancel; the refusal changes nothing except that it started the cancel, and a repeated delete is the same refusal until the provider says `cancelled` or a destroy confirms absence, because deleting the task would cascade away the record that the cancel and destroy depend on.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.14:** Every terminal transition of a pending operation shall re-read the record under the operation claim and apply only the transitions allowed from its current phase, each as a guarded write of the record revision. From `placement_pending`: a completion accepted under AC-EXECUTORS-PLUGIN-PLACEMENT-001.2 moves to `creating`; a failure poll result moves to `placement_failed`; the deadline, or a completion attempted after it, moves to `placement_timeout`; a cancel moves to `cancelling`; a refusal with no recorded checkpoint and no provider state settles under AC-EXECUTORS-PLUGIN-PLACEMENT-002.2 (absent, reservation released once, refusal reason shown); a refusal with a checkpoint or state is `conflict` and moves to `placement_failed` with the recovery destroy (AC-EXECUTORS-PLUGIN-PLACEMENT-002.3). From `cancelling`: `cancelled` settles the record absent; a completion or `already_placed` sets `destroy_started` in the same guarded write and continues to destroy, and a writer that finds `destroy_started` already set is dropped, so one destroy owner exists; a refusal with no checkpoint and no state is the cancel outcome `cancelled` (settled absent as `placement_cancelled`, reservation released once, no refusal reason shown); any other poll result (a failure, or a refusal with a checkpoint or state) is dropped without a write, because polling ends when the record leaves `placement_pending` and only a poll already in flight can still deliver one, and the destroy of the cancel path covers a late placement. The deadline reached in `cancelling` changes no phase: it switches the cancel retries to the recovery destroy by operation (AC-EXECUTORS-PLUGIN-PLACEMENT-001.17). From `placement_failed` and `placement_timeout`: only the destroy confirmation, which settles absent. A transition not allowed from the current phase (a late poll failure after `cancelling`, or a late completion after settlement) shall be dropped without a write and without a second destroy. When two transitions race, the loser re-reads the record, finds a phase or `destroy_started` that does not allow it, and is dropped.

- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.15:** The host shall resolve a provider `conflict` as follows and shall never show it: on provision, a pending response from a provider not requiring `pending_placement`, an invalid response shape, or a `conflict` error returned by the call runs the recovery destroy by operation (AC-EXECUTORS-PLUGIN-PLACEMENT-001.17) and ends as `placement_failed` for a provider requiring `pending_placement` and as the ordinary launch failure otherwise (AC-EXECUTORS-PLUGIN-PLACEMENT-002.4); on a poll, as AC-EXECUTORS-PLUGIN-PLACEMENT-001.12; on a cancel, it is read as an unknown outcome, the operation stays `cancelling`, and the retries of AC-EXECUTORS-PLUGIN-PLACEMENT-001.4 converge by the recovery destroy; on a refusal, as AC-EXECUTORS-PLUGIN-PLACEMENT-002.3.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.16:** When the recovery destroy of a `cancelling` record is still unconfirmed after the placement deadline, the destroy shall keep retrying with the backoff of AC-EXECUTORS-PLUGIN-PLACEMENT-001.12 until absence is confirmed, the session shall end `FAILED` with the failure code `placement_cancel_pending` and its localized text (the one deliberate exception to AC-EXECUTORS-PLUGIN-PLACEMENT-001.3, so no session stays `STARTING` forever), and when the destroy confirms, the record shall settle absent, the session code shall be replaced by the outcome `placement_cancelled`, and the session shall move to its stopped state. The session of a `placement_failed` or `placement_timeout` record is `FAILED` with that code from the transition and keeps it; `placement_cancel_pending` is never written over it and is for those records only the refusal code of start and delete (AC-EXECUTORS-PLUGIN-PLACEMENT-001.13). After a restart the poller registry recreates the loop for `placement_pending` and `cancelling` records and a destroy-retry loop (same registry, same single-flight, backoff restarted at 2 seconds) for `placement_failed` and `placement_timeout` records. An archive or reset shall be accepted and return success after it starts the cancel path, the task view shows the `cancelling` label until absence is confirmed, and neither deletes the record.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.17:** The recovery destroy by operation shall be: call `RecoverExecutorOperation` for the operation; `found` destroys the returned resource through the existing destroy path and settles the record absent on confirmation; `absent` settles the record absent (the existing `settleAbsentPluginExecutor`) and releases the reservation once; `unknown`, a transport error, or an unavailable provider retains the record and retries in the registry loop with the backoff of AC-EXECUTORS-PLUGIN-PLACEMENT-001.12 until it can say, without waiting for a restart. It shall never attach a found resource as a live environment and never publish ready. The ordinary startup recovery of main cannot serve these phases: `recoverPluginExecutor` attaches a `found` resource as a live environment, retains an `unknown` outcome with a log line and no retry, and destroys only a `cleanup_pending` record that holds a resource handle or an `allocating` record of a terminal task.

### REQ-EXECUTORS-PLUGIN-PLACEMENT-002: Refused provision releases the record

**Intent:** A provision the provider refused, with nothing allocated, does not leave a record that only recovery can release.

#### Acceptance criteria

- **AC-EXECUTORS-PLUGIN-PLACEMENT-002.1:** When a provider requires `provision_refusal`, a provision response can carry `refused` with `nothing_allocated`, and a reason from `capacity_refused`, `admission_refused`, `policy_refused`, or `invalid_request`. A provider requiring `pending_placement` shall also require `provision_refusal`, so a pending-placement provider's refusal always settles through this path.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-002.2:** The host shall accept the refusal only when no checkpoint and no provider state for the operation was recorded. It shall then, in one write, record the refusal, settle the environment absent, and release the admission reservation, without running recovery.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-002.3:** A refusal for an operation that has a recorded checkpoint or state shall be rejected as `conflict`, and recovery shall run as for any failed provision.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-002.4:** A lost reply, a timeout, or a response error shall never be read as a refusal. Only recovery or destroy can say that a resource is absent.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-002.5:** The task shall show the refusal reason as a distinct outcome, and a provider not requiring the capability shall keep today's behavior.

## Out of scope

- Resizing a live environment, preemption, and cross-provider failover.
- Autoscaling or provisioning machines.
