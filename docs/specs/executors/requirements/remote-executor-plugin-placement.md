# Remote executor plugins: queued and pending placement requirements

## Overview

Continuation of [admission and placement](remote-executor-plugin-admission.md)
(moved here for the file size limit, IDs unchanged): placement that can wait in a queue beyond the current launch deadline, and
a refusal that releases the record. The terms of that document apply. Both are opt-in [capabilities](remote-executor-plugin-capability-versioning.md).

## Requirements

### REQ-EXECUTORS-PLUGIN-PLACEMENT-001: Queued and pending placement

**Intent:** A launch waiting for capacity is visible, cancellable, and bounded, and capacity refusal differs from placement failure.

#### Acceptance criteria

- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.1:** When a provider requires `pending_placement`, a provision response can report `queued` or `placing` with a closed reason code, an optional queue position, a progress phase, and a poll interval. The host shall persist the pending state and the operation before replying.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.2:** The host shall poll the provider within the clamped interval (2 to 60 seconds), shall record each phase change, and shall end polling at the placement deadline. The deadline is the `placement_deadline_seconds` that the provider reports in profile validation (60 to 86400, default 600) and is read from the profile snapshot recorded at allocation. The deadline time is the host clock time at which the first pending response was persisted plus that many seconds, stored as UTC in the pending state; a provider response cannot extend it, and a clock step is not compensated. An absent or zero value is 600 seconds, and a value outside 60 to 86400 or not an integer fails profile validation with `invalid_config`.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.3:** The task and session shall show a pending-placement status with the reason code and progress phase, and the existing stop action shall cancel a queued launch. While the operation is cancelling, the session shall stay `STARTING` with the label `cancelling` and shall move to its stopped state only when the provider says `cancelled` or a destroy confirms absence. Every new user-facing string shall be localized.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.4:** A cancel of a queued launch shall mark the operation cancelling under the claim and ask the provider to cancel. The outcome shall be `cancelled` (nothing allocated) or `already_placed`, and `already_placed` shall continue with the normal destroy. When the cancel call fails or times out, the operation shall stay cancelling and the host shall retry with backoff until the placement deadline, then run the existing recovery destroy by operation; it shall report cancelled only after the provider says `cancelled` or a destroy confirms absence.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.5:** When placement completes while a cancel is in flight, exactly one shall commit first. If the cancel commits first, a later completion is treated as `already_placed`, destroy runs to confirmation, the launch outcome is `placement_cancelled`, and the session ends in its existing stopped state with no allocation left. The completion commit is the guarded write that moves the record from `placement_pending` to `creating`; it is not readiness. If the completion commits first, the continuation of AC-EXECUTORS-PLUGIN-PLACEMENT-001.11 owns the launch, and before it starts the agent it shall re-read the session: a session that is no longer `STARTING` because the user stopped it gets the environment published ready without an agent start, the stop is processed as an ordinary Stop (the environment is preserved, as today), and the task shall not report the launch as cancelled.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.6:** The host shall report failures as `capacity_refused` (the provider will not queue this request; this is the refusal reason of REQ-EXECUTORS-PLUGIN-PLACEMENT-002, one outcome), `placement_failed` (the provider tried and failed), or `placement_timeout`, and shall not merge them into a generic error.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.7:** After a backend or plugin restart the host shall resume polling the persisted operation and shall neither allocate a second environment nor lose the pending state. Startup recovery shall skip every record in the phase `placement_pending` or `cancelling` and leave it to the poller registry, which is the only owner of those records; the authenticated-handshake recovery of AC-EXECUTORS-NATIVE-WORKER-007.2 applies only to a record that has reached `creating`. The operation claim named in this document is the existing environment recovery claim (`recoveryclaim`, keyed by the task environment and carrying the operation ID): a poll read holds no claim, and each transition (complete, cancel, fail, timeout) takes it. A continuation after a restart publishes through the guarded publication of AC-EXECUTORS-NATIVE-WORKER-007.3 under that claim.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.8:** A provider not requiring `pending_placement` shall keep the current synchronous launch and deadline, and a pending response from it shall be rejected as `conflict`.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.9:** Every host-originated launch failure code a user can meet (`capability_mismatch`, `missing_capability`, `admission_denied` with its reasons including `scope_full`, `admission_unavailable`, `launch_policy_unsupported`, `launch_policy_unenforced`, `secret_reference_missing`, `secret_in_state`, `bootstrap_consumed`, `repository_inventory_mismatch`, `state_too_large`, `api_unreachable`, the three placement outcomes, each refusal reason, and `placement_cancel_pending`) shall appear in the task and session view as localized text that names the next step, shown with an icon and text and never by colour alone. The code `conflict` from a provider call is resolved by the host under AC-EXECUTORS-PLUGIN-PLACEMENT-001.15 and shall not reach the user, except that a resume refused because its admitted class changed (AC-EXECUTORS-PLUGIN-ADMISSION-001.8) shall appear as localized text saying the resume was refused because the resource class changed.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.10:** The reason codes are the closed set `no_capacity`, `quota_wait`, `node_unavailable`, `maintenance`, and `other`; the progress phases are the closed set `queued`, `reserving`, `provisioning`, `starting_worker`, and `preparing_workspace`. A value outside a set shall be recorded as `other` (reason) or shown with the text under `executors:pluginPlacement.unknown` (phase), and a provider-supplied string shall never be displayed. A queue position is 1-based, and an absent or zero position means unknown. An absent or zero poll interval is 5 seconds before clamping. A response carrying more than one of a resource, a refusal, and a pending state, or none of them, shall be rejected as `conflict`.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.11:** When a poll reports that placement is complete and no cancel committed first, the host shall continue the launch from the persisted operation through the same post-provision path as a synchronous launch (bootstrap handshake, instance creation, and the agent start with the prompt already stored for the session) without a user action. This continuation is the delayed launch of REQ-EXECUTORS-PLUGIN-ADMISSION-001: it re-runs the capability gate against the negotiated set recorded at admission (a mismatch ends as `capability_mismatch` with a destroy), and it keeps the reservation taken at the original launch without a second admission. Until the environment is ready the session shall be `STARTING` with the pending-placement label, and a failure shall give the session the failure code. The bootstrap nonce shall be valid until the placement deadline plus 600 seconds on that same host clock, and a placement reported after the deadline shall end as `placement_timeout` with a destroy.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.12:** One poll loop per operation shall exist in a backend process, held in a registry keyed by operation ID and created again from the persisted state after a restart. A poll that returns a transport error or `unavailable` shall be retried at the next interval until the deadline. `rate_limited` shall retry at the next interval (a longer provider hint is honored up to the clamp). `not_found`, `denied`, `invalid_config`, `unsupported`, `expired`, `conflict`, and `cleanup_pending` end as `placement_failed`, each followed by the recovery destroy by operation, since only destroy confirms absence. A cancel retry shall wait 2 seconds, doubling to a cap of 30 seconds.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.13:** An archive, reset, or delete of a task whose record is `placement_pending` or `cancelling` shall start the cancel path of AC-EXECUTORS-PLUGIN-PLACEMENT-001.4 if none is running (`already_placed` continues to destroy), and shall record `cleanup_requested` (AC-EXECUTORS-NATIVE-WORKER-007.9) on the record. The poller registry of AC-EXECUTORS-PLUGIN-PLACEMENT-001.7 remains the only actor on these records: the cleanup sweep never calls the provider for them, and it only reads `cleanup_requested` to see that the cancel is still owed (the poller of an operation that has no loop, such as after a restart, is recreated from the record). Each cancel attempt, each retry, and each terminal transition takes the operation claim for its own write and releases it afterwards; no claim is held while waiting between retries, so an archive, reset, or second delete of the same task is never blocked by a pending retry and finds the operation already `cancelling`. There shall be one cancel RPC in flight per operation ID in a backend process: Stop, archive, reset, delete, and the sweep all call one request-cancel function that finds the loop in the poller registry (which holds the in-flight marker after the claim is released) and returns without a second RPC, and after a restart the registry is recreated from the `cancelling` record. A delete shall be refused with `placement_cancel_pending` until the provider says `cancelled` or a destroy confirms absence; the refusal changes nothing except that it started the cancel, and a repeated delete is the same refusal until then, because deleting the task would cascade away the record that the cancel and destroy depend on.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.14:** Every terminal transition of a pending operation (completion, cancel reply, poll failure, deadline, cleanup) shall re-read the record under the operation claim and apply only the transitions allowed from its current phase: from `placement_pending`, completion moves to `creating`, failure or deadline moves to `placement_failed` or `placement_timeout`, and cancel moves to `cancelling`; from `cancelling`, `cancelled` settles the record absent, and a completion or `already_placed` continues to destroy; a transition not allowed from the current phase (for example a late poll failure after `cancelling`, or a late completion after settlement) shall be dropped without a write and without a second destroy. Two more rows complete the table. A poll response carrying a refusal with no recorded checkpoint or provider state settles from `placement_pending` through AC-EXECUTORS-PLUGIN-PLACEMENT-002.2 (absent, reservation released once, refusal reason shown); from `cancelling` it is the cancel outcome `cancelled` (settled absent as `placement_cancelled`, reservation released once, no refusal reason shown); with a checkpoint or state it is `conflict` and ends as `placement_failed` with the recovery destroy. The deadline reached in `cancelling` changes no phase: it switches the cancel retries to the recovery destroy by operation. When two transitions race, the loser re-reads the record, finds a phase that does not allow it, and is dropped.

- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.15:** The host shall resolve a provider `conflict` as follows and shall never show it: on provision, a pending response from a provider not requiring `pending_placement` or an invalid response shape runs the recovery destroy by operation and ends as `placement_failed`; on a poll, as AC-EXECUTORS-PLUGIN-PLACEMENT-001.12; on a cancel, it is read as an unknown outcome, the operation stays `cancelling`, and the retries of AC-EXECUTORS-PLUGIN-PLACEMENT-001.4 converge by the recovery destroy; on a refusal, as AC-EXECUTORS-PLUGIN-PLACEMENT-002.3.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-001.16:** When the recovery destroy of a `cancelling`, `placement_failed`, or `placement_timeout` record is still unconfirmed after the placement deadline, the destroy shall keep retrying with the backoff of AC-EXECUTORS-PLUGIN-PLACEMENT-001.12 until absence is confirmed, the session shall end `FAILED` with the failure code `placement_cancel_pending` and its localized text (the one deliberate exception to AC-EXECUTORS-PLUGIN-PLACEMENT-001.3, so no session stays `STARTING` forever), a start or delete for that task shall be refused with `placement_cancel_pending`, and the record shall settle absent when the destroy confirms. After a restart the poller registry recreates the loop for `placement_pending` and `cancelling` records only; startup recovery shall run the recovery destroy for `placement_failed` and `placement_timeout` records through the ordinary path. An archive or reset shall be accepted and return success after it starts the cancel path, the task view shows the `cancelling` label until absence is confirmed, and neither deletes the record.

### REQ-EXECUTORS-PLUGIN-PLACEMENT-002: Refused provision releases the record

**Intent:** A provision the provider refused, with nothing allocated, does not leave a record that only recovery can release.

#### Acceptance criteria

- **AC-EXECUTORS-PLUGIN-PLACEMENT-002.1:** When a provider requires `provision_refusal`, a provision response can carry `refused` with `nothing_allocated`, and a reason from `capacity_refused`, `admission_refused`, `policy_refused`, or `invalid_request`. A provider requiring `pending_placement` shall also require `provision_refusal`, so a pending-placement provider's refusal always settles through this path.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-002.2:** The host shall accept the refusal only when no checkpoint and no provider state for the operation was recorded. It shall then, in one write, record the refusal, settle the environment absent, and release the admission reservation, without running recovery.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-002.3:** A refusal for an operation that has a recorded checkpoint or state shall be rejected as `conflict`, and recovery shall run as for any failed provision.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-002.4:** A lost reply, a timeout, or a response error shall never be read as a refusal. Only recovery or destroy can say that a resource is absent.
- **AC-EXECUTORS-PLUGIN-PLACEMENT-002.5:** The task shall show the refusal reason as a distinct outcome, and a provider not requiring the capability shall keep today's behavior.

## Out of scope

- Resizing a live environment, preemption, and cross-provider failover.
- Autoscaling or provisioning machines.
