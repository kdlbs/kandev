# Provider Error Recovery Requirements

## Overview

A provider can also abandon a partially streamed response and retry it inside
the same prompt. That retry must replace the abandoned attempt without leaving
duplicate transcript rows or stale recovery context.

## Terminology

- **Provider response attempt:** One provider generation attempt inside a
  Kandev prompt. A provider can retry this attempt without ending the prompt.
- **Response-attempt retry boundary:** Structured, current-prompt evidence that
  the provider abandoned its active response attempt and will generate a
  replacement.

## Requirements

### REQ-PLATFORM-PROVIDER-ERROR-RECOVERY-001: Provider Error Recovery

**Intent:** Agent CLIs and providers report equivalent failures through different ACP frames, HTTP metadata, process exits, and diagnostic strings. Capacity, network, subscription, and quota failures need different recovery behavior, but orchestration code must not branch on provider names or raw prose.

#### Acceptance criteria

- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.1:** Agent adapters collect bounded evidence from structured ACP errors, ordered ACP updates, managed stderr, process exits, and structured HTTP metadata.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.2:** Evidence is correlated to the active invocation, prompt generation, and lifecycle phase before it can authorize recovery.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.3:** A shared deterministic classifier maps evidence to a stable semantic code, policy class, confidence, scope, classifier rule ID, and validated timing hints.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.4:** Provider-specific signatures live in adapter extractors and a central fixture-driven catalogue. Kanban, Office, lifecycle, and UI code do not inspect provider names or raw error strings to choose behavior.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.5:** Structured metadata and exact signatures outrank broad text patterns. Collision tests enforce deterministic priority.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.6:** Adding a known provider message normally adds a sanitized fixture and catalogue rule. It does not add an orchestration or UI branch.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.7:** Classification is deterministic in this version. Calling a model to classify an error or extract timing data is deferred.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.8:** Original-prompt replay, reset waiting, and fallback require current-invocation, pre-result, effect-safe evidence. Native restoration follows the separate [interruption contract](provider-interruption-continuation.md). Live capacity continuation follows the [runtime continuity contract](transient-turn-runtime-continuity.md).
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.9:** While an eligible interactive transient retry is pending, desktop and mobile task chat shall show the retry reason, provider, attempt count, countdown, and Cancel action only while the backend owns that retry.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.10:** When an interactive transient retry succeeds, is exhausted, reaches a terminal state, is stopped, or is cancelled, the system shall attempt to durably retire every outstanding retry notice for the session so that a successful cleanup prevents the notice from reappearing after the session becomes idle, the task changes, the page reloads, or another viewer observes the session. If listing or deletion fails, the system shall log and swallow the failure so a later authorized cleanup can retry the remaining notices.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.11:** After authorization, cancelling an interactive transient retry shall attempt to retire outstanding retry notices even when the retry loop has already ended. Usable Chat follows the [runtime continuity contract](transient-turn-runtime-continuity.md); otherwise, cancelling an active loop exposes Resume and Start fresh. Listing or deletion failures follow AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.10. A denied or foreign task-session pair shall not expose whether retry state or retry notices exist.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.12:** A current Cursor frame beginning, after trimming, with case-insensitive `Error: RetriableError:` and a non-empty suffix of at most 256 UTF-8 bytes shall be suppressed when no later progress occurs, then yield one structured failure after the barrier. `[unavailable] PING timed out` and `Connection stalled` are valid. Cancellation, deadline, and retry-escalation signatures remain ordinary output. Prose before the prefix, empty/partial markers, stale evidence, and non-Cursor output stay ordinary output.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.13:** When Cursor resumes generation before the prompt settles, Kandev shall treat the earlier matching frame as internal retry telemetry. Kandev shall not start a retry from the superseded frame. A later matching terminal frame for the same prompt can become new failure evidence.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.14:** A bounded terminal Cursor `RetriableError` shall retain its observed category. An explicit HTTP/2 stream reset shall classify as `agent_transport_lost`; `[unavailable]` as `provider_unavailable`; an explicit connection-stalled diagnostic as `network_unavailable`; and `[resource_exhausted]` as `provider_resource_exhausted`. An unknown suffix shall remain unclassified and shall not authorize automatic recovery. Both layers share Unicode trim and byte bounds. A stream reset labelled `[canceled]` stays eligible; context cancellation, deadline, and retry escalation retain the veto.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.15:** Terminal Cursor `RetriableError` replay requires current-turn evidence of no output or tools and retains the provider, retry owner, budget, and backoff. Output or tools forbid replay. Native continuation follows the separate interruption contract; missing evidence remains manual.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.16:** Kandev shall retain current-prompt ACP diagnostics in the transcript. Pre-result recovery requires a matching structured `session/prompt` error, the same high-confidence fallback-eligible code, and no later output or tools. Mismatch, stale identity, low confidence, output, or tools shall keep ordinary-output treatment and prohibit original-prompt recovery. Live capacity continuation requires its separate typed evidence.

- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.17:** The catalogue shall carry a raw ACP replay fixture for every required cell of the replay matrix. The gateway enumeration is `claude-direct`, `teamclaude`, `openrouter`, `litellm`. The case enumeration is `matched`, `mismatched`, `later-output`, `queued`, `prose-matched`, `prose-tool`, `prose-output`. The first four cases are required for every gateway. The three `prose-` cases are required only for a gateway the matrix declares classifying, because a prose case asserts nothing when the terminal envelope does not classify. A required cell with no fixture shall fail the fixture test, and a test shall not skip a required cell. Two fixtures sharing a case shall not carry equivalent frames, compared as canonically re-encoded values rather than as raw file bytes.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.18:** Each replay fixture shall declare its gateway, its correlation case, the agent identity it replays through, whether its gateway is classifying, its capture mode as either `recorded` from a live ACP session or `reconstructed` from a cited published contract, and the replay identity the recovery-evidence layer requires: a corpus-unique session identifier, an execution identifier, and a non-zero prompt generation. The replayed payload shall contain no credential, bearer token, account or organization identifier, URL, or absolute host path. The system design shall enumerate the forbidden identifier shapes, and that enumeration shall be the enforced definition rather than an illustrative sample. Provenance fields shall carry no credential, no account or organization identifier, and no private host, and may cite a public documentation URL. Replaying a fixture shall be deterministic and shall not depend on wall-clock timing.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.19:** Replaying a fixture shall produce the fixture's declared ordered event sequence, its declared classified diagnostic code, and its declared recovery disposition. The event sequence and the diagnostic code shall be observed at the ACP transport layer, where every token before the terminal failure is observed on the adapter's event stream and the terminal failure token is observed as the sanitized provider projection built from the error the prompt call returned. Every preceding token shall be on the event stream before the prompt call returns. The recovery disposition shall be observed at the recovery-evidence layer. Both layers shall consume the same fixture file, and a fixture shall not be satisfied by one layer alone. For the queued-diagnostic case, the diagnostic message chunk shall reach the event stream before the terminal failure event regardless of update-worker scheduling.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.20:** The provider-diagnostic candidate marker shall be decided once, at the ACP conversion boundary, and carried unchanged on every streaming, lifecycle, and evidence hop. Carried means the field survives on the in-flight event value that each hop receives. Message accumulation and flush shall neither read, act on, nor persist the marker, and no message-level column shall be added for it. A consumer shall not re-derive the marker from message text. An event that reaches a consumer without the marker shall be treated as ordinary model output.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.21:** A marked diagnostic chunk shall stay visible in the transcript, shall not advance turn progress, and shall not clear a recorded diagnostic for its own generation. An unmarked non-empty assistant or thought chunk in the same generation shall clear the recorded diagnostic and restore the ordinary output fence. Tool activity in the same generation shall not clear the recorded diagnostic; it shall instead fail the attempt through the effect fence, so an attempt with tool activity is never pre-result safe.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.22:** A provider diagnostic projected from a terminal ACP prompt error shall carry only allowlisted structured metadata: the JSON-RPC error code, the adapter-declared error kind, the negotiated provider identity, and the session model identity. The session model identity shall be carried only when the adapter has settled a model for that session, meaning it has emitted a session configuration or model event carrying a non-empty current model identity; otherwise the field shall be omitted. Raw JSON-RPC error data shall never cross the boundary. A malformed, oversized, or unrecognized field shall be dropped and shall not invalidate the projection, and the presence or absence of this metadata shall not affect whether a projection is valid. A model settled after a projection is built shall not be added to it retroactively. This metadata shall not by itself authorize recovery in this version.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.23:** A recorded diagnostic shall authorize pre-result recovery only when its normalized text is contained in the normalized message of the terminal provider failure, in addition to both classifying to the same high-confidence, fallback-eligible semantic code. Normalization shall trim leading and trailing whitespace and collapse internal whitespace runs to a single space, and comparison shall be case-sensitive. An empty normalized diagnostic shall never satisfy containment. The normalized diagnostic text shall be retained with the recorded diagnostic code, shall be cleared whenever that code is cleared, and shall not be overwritten by a later diagnostic in the same generation. A diagnostic that classifies to the terminal code but whose normalized text is not contained in the terminal message shall keep the output fence and expose manual recovery.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.24:** A terminal ACP prompt error whose transient signature exists only in `RequestError.Data` shall expose manual recovery on every occurrence, including repeated failures in one session, without a transient retry notice or automatic retry. A preceding diagnostic shall not change this outcome under criteria `.16`, `.22`, and `.23`. The `/transport-lost` E2E mock shall retain the SDK envelope, `Message` equal to `Internal error` and peer-disconnect detail only in `Data`, and assert manual recovery. Its obsolete retry-cancellation sub-test shall be retired. Documentation shall not claim that this surface enters the retry ladder. The catalogue retains other-surface unit coverage; automatic transport-loss E2E coverage on this data-only surface is intentionally absent.

- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.25:** During one interactive transient retry loop, desktop and mobile chat shall show at most one current retry banner. Each subsequent attempt shall update that banner's reason, provider, attempt count, deadline, and Cancel action. Reloading the session shall retain the latest persisted attempt. Existing duplicate retry notices shall consolidate on the next successful retry-notice write. Unrelated messages and other sessions shall remain unchanged. Storage failures shall remain non-fatal and shall not trigger creation of an additional notice when an existing notice cannot be read or updated.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.26:** When a supported adapter receives exact structured evidence that the active provider abandoned the current response attempt and will retry it internally, Kandev shall accept a response-attempt retry boundary within that prompt generation. One prompt generation may contain multiple sequential boundaries; each boundary applies only to assistant and thinking records created after the preceding boundary or commit boundary. Malformed evidence, a false retry flag, an unsupported adapter, a zero or stale prompt generation, and terminal provider errors shall not create that boundary or remove transcript content.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.27:** After Kandev accepts a response-attempt retry boundary, it shall durably remove assistant and thinking messages created by the abandoned attempt. Connected desktop and mobile chats shall remove those messages before later replacement output, and a reload or another viewer shall see only the replacement response.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.28:** Response-attempt cleanup shall preserve messages, tool activity, permission state, and turns committed before the active provider attempt. A repeated retry boundary with no new output shall be a no-op, and abandoned assistant text that has not crossed a history boundary shall not enter later fallback resume context. The boundary shall not erase prompt-level output or effect evidence used to decide whether a separate Kandev-owned replay is safe.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.29:** The primary launch prompt shall use credential-only, unbounded redaction on every attempt, including attempt 0. Provider output and `FailureReason` shall use the diagnostic tier.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.30:** Cursor terminal failure presentation, persisted diagnostics, and technical details shall retain the bounded sanitized provider condition. A resource-exhaustion or availability diagnostic shall not be replaced by a fabricated HTTP/2, TCP, or network-failure explanation. Sanitization shall remove sensitive content without inventing a cause; if diagnostic detail cannot be retained, Kandev shall use a neutral provider-error explanation.
- **AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.31:** The explicit bounded Cursor `RetriableError: [resource_exhausted]` envelope shall permit a short same-provider retry as transient `provider_resource_exhausted`. The category alone shall not assert an account quota, billing failure, rate-reset deadline, or provider-switch permission. Explicit hard quota/authentication evidence, user cancellation, unknown diagnostics, and stale evidence shall retain their existing recovery policy.

## Out of scope

- Classifier rules keyed on the structured error kind or JSON-RPC code. The metadata is transported and observable in this version; making it outrank the message-text catalogue is a separate contract change, because it would let a gateway authorize dynamic recovery through a field no fixture yet constrains.
- Automatic retry from a generic ACP `RequestError.Data`-only signature. The sanitized message boundary in `.22` takes precedence: the classifier sees `Message`, so this surface remains manual. The transport-loss catalogue rule still applies when its signature reaches supported message or stderr surfaces; that does not make those surfaces replay-safe. A future restoration of data-only classification requires a reviewed classification-only channel, a fixture for the data-only signature, and a negative fixture proving that raw detail never reaches display, logs, or persistence.
- New catalogue signatures for the OpenRouter and LiteLLM error envelopes. Neither gateway has a message-text rule today, so both are declared non-classifying and their `matched` and `queued` fixtures assert an unclassified disposition and manual recovery. A follow-up needs: a real captured envelope per gateway, a rule added beside `acp.gateway_server_failure.v1`, the paired negative-case prose test that catalogue convention requires, and a flip of the gateway's classifying declaration, which then makes its three `prose-` cells required.
- Tightening the existing overloaded signature. The reported false positive reaches the fence through `anthropic.overloaded.529.v1`, whose pattern matches a numeric code adjacent to the word overloaded on one line; the anchored gateway signature already rejects equivalent prose. Narrowing that pattern would change stderr classification everywhere it is used, so this version closes the hole at correlation instead, through AC-PLATFORM-PROVIDER-ERROR-RECOVERY-001.23.
- Live gateway calls during test execution. Fixtures are committed artifacts; the capture path is a developer-run script.
- Rendering the diagnostic candidate marker in the web or desktop UI. The marker is backend recovery evidence; the diagnostic text itself already renders as ordinary transcript content.
- Changes to retry policy values, attempt limits, backoff, or candidate ordering.
- Gateway usage adapters beyond the existing TeamClaude client (`docs/plans/teamclaude-proxy-usage/` tasks 02 through 04).
