# Managed Git isolation rollout requirements

## Overview

[Managed Git repository-code isolation](managed-git-repository-code-isolation.md) stops hooks and other repository-supplied code from running in Kandev-managed Git unless a repository opts in. That changes what existing users' commits do, so it ships behind the runtime flag `features.managedGitIsolation`: off in every profile (`prod`, `dev`, and `e2e`); tests and contributors enable it explicitly through its environment variable. This document owns the flag, its off and on behavior, and the migration rule for existing repositories.

"Flag on" and "flag off" refer to the **running value**: the value the backend process resolved at startup (AC-AGENTS-GITISOLATION-004.4). A stored override or profile change is not the running value until the backend restarts. A **mode** is the on or off isolation state of one agentctl process. **Baseline** is the behavior of Kandev-managed Git on `main` at the commit this change is based on, recorded in the work order.

### REQ-AGENTS-GITISOLATION-004: Rollout behind a runtime flag

**Intent:** The isolation changes what existing users' Git commits do (hooks stop running). It ships off in every profile, is enabled explicitly where it is exercised, and can be switched back off without a code change.

#### Acceptance criteria

- **AC-AGENTS-GITISOLATION-004.1:** The system shall register the runtime flag `features.managedGitIsolation` (environment variable `KANDEV_FEATURES_MANAGED_GIT_ISOLATION`) as restart-required and mutable from Settings → System → Feature Toggles, with the value `false` in the `prod`, `dev`, and `e2e` profiles. A test or contributor that needs the isolation sets `KANDEV_FEATURES_MANAGED_GIT_ISOLATION=true`. The value the backend resolves at startup follows the standard precedence: explicit environment variable, then stored override, then profile default.
- **AC-AGENTS-GITISOLATION-004.2:** While the flag is off, the system shall start every managed Git process of the backend, and of every agentctl instance in off mode, with the same executable, argument vector, environment, and hook, file-system-monitor, filter, text-conversion, merge-driver, and transport behavior as the baseline, including the pins that exist there. It shall start no extra Git process for driver enumeration, shall not check the `managed-git-policy.v1` capability (AC-AGENTS-GITISOLATION-001.12 does not apply), shall not read the hooks setting to build agentctl create requests, and shall send no `git_hooks` or `git_isolation` value to agentctl. A golden fixture committed with the tests shall record, captured from the baseline, the argument vector, environment, and Git process count of one representative command for each of the interactive, lifecycle, and background helpers and the gitinit helper, and the off-mode output shall equal it.
- **AC-AGENTS-GITISOLATION-004.3:** While the flag is on, the system shall apply REQ-AGENTS-GITISOLATION-001 through 003 unchanged to the backend's managed Git and to every agentctl instance in on mode. An instance created while the flag was off follows AC-AGENTS-GITISOLATION-004.2 until it is reset.
- **AC-AGENTS-GITISOLATION-004.4:** The system shall resolve the flag once per backend process at startup; the value shall not change for the life of that process, and the repository "Run Git hooks" switch (AC-AGENTS-GITISOLATION-004.5) shall use this running value, while Settings → System → Feature Toggles shows the stored value with its existing restart-pending indication. Each agentctl process holds one mode, set by the first create admitted while it has no live instance (published or still being created) and unchanged for as long as any instance, published or still being created, remains. When the last one is gone, whether by stop, reset, or a creation that did not publish and finished its cleanup, the process returns to off mode, as it was before its first create; the next admitted create adopts its own mode. An overlapping same-mode create that was admitted keeps the mode when the create that adopted it fails. The mode is the one the lifecycle Manager sends on the create call (the same moment and rule as AC-AGENTS-GITISOLATION-002.6); a request that carries none is off. Before its first admitted create, and whenever it has no live instance, an agentctl process runs its own managed Git in off mode. Changing the flag therefore applies to the backend after restart, and to an agentctl process once its instances are gone, for example through **Reset Environment** of its only instance.
- **AC-AGENTS-GITISOLATION-004.5:** While the flag is off, the "Run Git hooks" switch (AC-AGENTS-GITISOLATION-003.1) shall be rendered disabled, showing the stored value, followed by explanation text that is linked to the switch as its accessible description. The text shall say that the setting has no effect until managed Git isolation is turned on and Kandev is restarted, in Settings → System → Feature Toggles or through the `KANDEV_FEATURES_MANAGED_GIT_ISOLATION` environment variable, and it shall be the same whether or not a stored override already says on or the value comes from the environment. While the flag is on the switch is enabled. As a disabled control the switch is exempt from keyboard reachability in AC-AGENTS-GITISOLATION-003.2 while the flag is off; its label, stored state, and explanation shall remain exposed to assistive technology. The repository settings API shall still accept, store, and return the hooks setting, with the same semantics as AC-AGENTS-GITISOLATION-002.7, and the setting shall have no effect on Git.
- **AC-AGENTS-GITISOLATION-004.6:** When the backend first runs with the flag on, the system shall not change any stored hooks setting. Every repository that existed earlier reads its stored value, which is off (AC-AGENTS-GITISOLATION-002.1) unless the API stored on while the flag was off, in which case it takes effect on enable. Hooks that ran before therefore stop running, for the backend's managed Git and for instances in on mode, in every repository stored off until its owner turns "Run Git hooks" on; instances still in off mode keep running hooks until reset (AC-AGENTS-GITISOLATION-004.4). The system shall provide no bulk or automatic grandfathering of existing repositories. When the flag is later turned off again, stored values are kept, and the backend and instances created after that restart return to the behavior in AC-AGENTS-GITISOLATION-004.2, except that an agentctl process that still has a live on-mode instance refuses an off-mode create until it has no live instance (AC-AGENTS-GITISOLATION-004.8).
- **AC-AGENTS-GITISOLATION-004.7:** The public Git operations guide shall state that the isolation is controlled by `features.managedGitIsolation`, that it is off by default in released builds, how to enable it, and the consequence in AC-AGENTS-GITISOLATION-004.6. AC-AGENTS-GITISOLATION-003.4 describes the behavior with the flag on.
- **AC-AGENTS-GITISOLATION-004.8:** If a create request's mode differs from the mode of an agentctl process that has a live instance, including an instance created for a host-utility probe, agentctl shall refuse the create before it reserves a port or an instance, with an error whose text names both modes and says that the instances of that agentctl process must be stopped first and that agentctl itself must be restarted if none can be stopped. The launch or **Reset Environment** that sent the request shall fail with that text in the surface that shows other launch errors, and a repeat shall succeed once the agentctl process has no live instance, whether by stopping or resetting its instances or by restarting agentctl. Mode adoption, the live-instance check, and the reservation shall be one atomic step, so of two concurrent creates with different modes against an empty agentctl process exactly one is admitted and the other is refused. The mode shall be written only together with registering the create's provisional bundle, after every other check and reservation of the admission has succeeded, so a create that is refused, rejected, cancelled, or fails to collect its environment or allocate a port shall leave the process mode as it was, and a process with no live instance is never left in on mode. A create that is admitted and then fails before publication releases the mode only when it was the last live instance, and only once its provisional bundle has been removed after cleanup, which can complete after the failed create's response is sent; a create of the other mode sent in that window is refused by the rule above with the same text, and a repeat succeeds once cleanup has completed. A provisional bundle whose cleanup failed stays live, because it still holds its port and possibly a process: nothing retries it while the process runs (its cleanup runs once after the failed create and once more at agentctl shutdown), other-mode creates keep being refused until it is removed, and the remedy is to restart that agentctl process, which no stop or reset of another instance can replace. Restarting agentctl means restarting Kandev for the local agentctl, except that with agent survival or on a remote executor it means stopping that agentctl process or recreating that executor environment, because a Kandev restart leaves it running. The same remedy applies to a published instance whose stop failed and stays in the stopping state: a retried stop or reset removes it, and a restart if that fails again; and to a host-utility probe instance orphaned by a backend exit that the user has no control to stop, which is also removed by the idle reaper after its idle timeout. A create whose instance ID is in use is rejected, is not an idempotent success, and changes nothing: a published ID keeps the existing "already exists" error and a provisional ID, including one whose create is still in flight, keeps the existing "is still cleaning up" error; a caller that lost the response to a create looks the instance up by ID instead of repeating the create.
- **AC-AGENTS-GITISOLATION-004.9:** While the flag is on, the lifecycle client shall check the `managed-git-policy.v1` capability before every create request it sends, including those for host-utility probe instances, and shall set `git_isolation` on the request; while the flag is off it shall do neither. agentctl shall advertise the capability whether or not the flag is on.

## Out of scope

- **Promoting the flag to on in `prod` and removing it:** a later release decision, made with the runtime-feature-flags procedure.
- **Per-repository migration tooling:** no import of repository hooks usage, and no notice listing repositories whose hooks stopped running.
