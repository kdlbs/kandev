# Dynamic Agent Routing Requirements

## Overview

Users often name profiles by the capability they want rather than a provider brand. A task can use a profile named Frontier for planning and one named Balanced for execution. The dynamic profile selects Claude, Codex, OpenCode, or another provider from an ordered list of complete agent profiles.

## Requirements

### REQ-AGENTS-DYNAMIC-AGENT-ROUTING-001: Dynamic Agent Routing

**Intent:** Select a concrete agent profile from an ordered list under one capability name.

#### Acceptance criteria

- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.1:** Kandev always registers one built-in virtual agent family with canonical ID `dynamic` and display name Dynamic. It cannot be disabled or uninstalled, does not expose a CLI command, and is not probed as a concrete inference agent. Profiles created under it have kind `dynamic`.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.2:** Agent settings can create a dynamic profile with a user-defined name, description, icon, and availability scope.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.3:** A dynamic profile references existing concrete agent profiles. It never copies or merges their credentials, environment, model, ACP options, flags, permissions, passthrough behavior, or MCP configuration.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.4:** A dynamic profile's candidate list can reference only concrete, launchable profiles. It cannot reference itself, another dynamic profile, or a rich Office identity in the first version. An Office identity's separate `execution_agent_profile_id` binding can reference a concrete or dynamic profile.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.5:** The profile name is the only capability label. Users can create profiles such as Frontier, Balanced, Economy, Review, or Security Review. Kandev stores no class or tier field and assigns no semantics to those names.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.6:** Each profile has an ordered candidate list. A candidate identifies one concrete profile and stores separate transient-error and hard-error policies. Each class can wait for a trusted near reset, retry the same candidate with bounded exponential backoff, then either skip the candidate or stop.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.7:** A concrete profile with `AutoFallback=true` is not an eligible dynamic candidate. The conductor is the only owner of cross-candidate fallback. An explicit `FallbackModel` remains part of the concrete profile's start-model policy. It does not advance the dynamic candidate list, and turn attribution records the model that ran.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.8:** Dynamic profiles and their concrete candidates participate in the existing profile-in-use dependency dialog. A dependency lookup failure blocks the change. Otherwise, the user can cancel or explicitly confirm deletion or disabling. Confirmed changes keep durable bindings unchanged: stale selected profiles fail closed, while stale or disabled candidates become ineligible and another configured candidate can be selected.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.9:** When a standalone dynamic-profile save completes while other profiles change, every unrelated profile shall retain its latest accepted state, including additions, updates, and removals. Every unrelated valid picker option shall remain available with its accepted label, enabled state, and revision, including options whose owner is temporarily absent from Agent settings. Desktop and phone shall share this behavior. A failed save shall not publish a replacement profile collection.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.10:** A failure shall be charged only to the route generation and candidate that produced it. When the route has already recorded a successor while the predecessor execution still serves the session, a later failure of that predecessor execution shall not open the successor's circuit, advance the route, or change its generation or candidate.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.11:** A route action submitted for a session whose selected profile is not dynamic shall be rejected as a validation error that names the reason. It shall not change session or route state and shall not be reported as an internal failure.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.12:** When a resumed or prepared runtime for the route's claimed execution is ready and waiting for input, the claimed route generation shall become active, whether the process-start callback or the resume-ready path observes it first. A cancelled session, a different execution, or a stale generation shall leave the route unchanged. A failed durable activation shall return an error to the resume caller while preserving the ready runtime. After storage recovers, admission shall be able to complete that same generation without stopping or replacing the current ready execution. Reconciled admission shall succeed only after both the durable route and its persisted session projection are active for that generation and execution.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.13:** An explicit recovery action shall be able to resume a session whose route is still `starting` with no live runtime, re-claiming the same persisted candidate. A live launch owner, a passive resume without same-generation activation reconciliation, and every other non-active route state shall keep the existing route guard. When an explicit recovery action cannot resume, it shall return an error instead of a success response without an execution. A passive session open shall keep its waiting response.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.14:** The restart orphan-route sweep shall mark `action_required` a session parked in WAITING_FOR_INPUT whose route is still `starting` and whose `executors_running` row is absent. A live executor row, a read error, or a stale generation shall leave the session and its route unchanged.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.15:** Automatic queue delivery shall not reserve a queued message for a session whose route is `action_required` and whose `executors_running` row is absent. The message shall stay queued and visible with the session's route recovery actions, and a successful route action shall make it deliverable again. A session with a live executor row, and a session without a dynamic route, shall keep the existing delivery behavior.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.16:** When a queued dispatch fails because a WAITING_FOR_INPUT session whose route is still `starting` has no `executors_running` row, Kandev shall mark that route `action_required` with the orphaned-starting reason, keep the message queued, and stop automatic redelivery until a route action runs. It shall not change the session state. A session whose launch is still pending shall keep its existing retry.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.18:** When a dynamic session moves to a different concrete candidate, through automatic fallback, launch resolution, or a manual route action, the next candidate shall not launch with the model, permission mode, or ACP options reported by the previous candidate's provider. Explicit user runtime overrides and the mode declared by the current workflow step shall survive the switch. A retry of the same candidate shall keep its runtime settings. A mode or model event from the previous candidate's execution that arrives after the switch shall not restore its settings.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.23:** When a start would change the logical profile of a session whose durable route is already materialized for a different logical profile, Kandev shall refuse the start before writing the session and return a validation error. The session label, concrete profile, and route shall stay unchanged and no agent shall launch. A session without a materialized route keeps its first profile selection, and a route for the requested profile resumes normally. See the [guard package](../../../plans/materialized-route-profile-guard/plan.md).
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.19:** A qualifying classified failure that may not advance the route, because the attempt already produced output or effects, shall still open the shared circuit of the candidate that produced it, charged under the same generation and candidate rule as AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.10. The route's generation, candidate, and status and the failed turn's existing recovery surface shall stay unchanged and no successor shall launch; later selections shall skip the open circuit until it recovers. An unclassified failure, or a failure of a superseded generation or predecessor execution, shall open no circuit.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.20:** Shared resource circuits shall use the default backoff ladder: 1, 5, 15, and 30 minutes, then 1, 2, and 4 hours. The ladder shall stop increasing at 4 hours. Failures inside one open window shall count as one incident. A failed probe shall advance the count. A successful probe shall close the circuit and retain its count. Only a clean completed turn shall reset the count. A successful launch alone shall not reset it. A later provider reset time shall extend the deadline. Inferred reset times shall be capped at 24 hours; explicit provider reset times shall remain authoritative. Timed failures shall never replace an owner-release hold.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.21:** Failure counts and UTC deadlines shall survive restarts on SQLite and PostgreSQL, including closed circuits with retained counts. Disabling or re-enabling dynamic agents shall not erase circuit history. Loading that history while dynamic agents are disabled shall not schedule work or mutate a circuit. Existing circuit rows without a failure count shall begin at zero. An upgrade shall preserve existing deadlines and holds.


- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.24:** `features.dynamicAgentRouting` shall be the sole release toggle for dynamic selection and fixed-profile circuit admission, failure charging, and completion resets. It shall remain off in prod, dev, and e2e profiles and require a restart. When it is off, fixed-profile dispatch shall retain its existing behavior and shall not charge or reset shared circuit counts. Candidate policies remain independent routing data, not additional feature toggles.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.25:** The retired `features.dynamicCircuitBackoffEscalation` key and `KANDEV_FEATURES_DYNAMIC_CIRCUIT_BACKOFF_ESCALATION` environment variable shall have no active effect. Old true and false values shall neither enable dynamic agents nor change their default backoff. Saved overrides shall be retained as inert data. The retired identities shall not be reused.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.26:** Feature discovery and Settings > System > Feature Toggles shall expose only the dynamic-agent release toggle for this capability. Desktop and phone shall expose the same remaining control, including its restart and environment-lock behavior. They shall expose no separate circuit-backoff switch.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.29:** An explicit Retry route action for a FAILED session whose route generation is still `starting` shall mark that same generation `action_required` and then apply the retry, so the user can relaunch it. This applies only when the request carries the current generation, no runtime is live for the session, and the session has only the stopped standalone local or worktree history row of its own execution; that history row shall be preserved. A live runtime, an unknown liveness probe, an absent `executors_running` row, or any other executor row shall leave the session and its route unchanged and report `dynamic_route_pending`; a stale generation, another session state, and another route state keep the existing route-action behavior. The resulting manual relaunch may reopen the FAILED session for the retried prompt and reschedule its FAILED task; automatic relaunches and stale generations shall still refuse a terminal session.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.17:** When a workspace enables mid-turn provider failover and a Kanban/task dynamic attempt that already produced output or effects fails with `rate_limited`, `quota_limited`, `provider_unavailable`, `provider_overloaded`, or `model_capacity` whose classification allows fallback, Kandev shall perform the same atomic Try next route action a person can submit, at most once per failed route generation and only after the failed turn has settled. The successor shall receive the bounded continuation package built from durable task state; Kandev shall not resend the failed prompt or replay its tools, and shall not change candidate order. A failure of another attempt or prompt generation, a superseded generation, a repeated delivery, a moved route, or a completed turn before the handoff runs shall not advance the route. When the same classified code fails again on a candidate that already failed in the current chain of automatic handoffs, or no eligible candidate remains, Kandev shall not advance automatically and the session shall keep its existing recovery surface. Unclassified failures, other codes, pre-result-safe failures, Office sessions, and workspaces with the setting off shall keep their existing behavior.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.22:** Each workspace shall store a mid-turn provider failover setting that defaults to off for new and existing workspaces and survives the workspace HTTP, WebSocket, and boot-state round trips; an omitted update shall keep the saved value. Workspace settings shall show the toggle to a workspace manager only while dynamic agent routing is enabled.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.27:** When a workspace enables automatic failed-route retry and a classified `rate_limited`, `quota_limited`, `provider_unavailable`, `provider_overloaded`, or `model_capacity` failure leaves a Kanban/task dynamic route in `action_required` or in `waiting` with no eligible candidate, Kandev shall submit the same Retry route action a person can submit, once for that route generation, through the same route-action transaction and continuation package; it shall not resend the failed prompt or replay its tools. The retry shall run no earlier than one minute after the failure and no earlier than the earliest expiry of an open circuit of a candidate the retry could use, and shall record the route reason `auto_failed_route_retry`. Kandev shall submit at most the workspace's limit of automatic retries between successful turns, and shall not retry again when the same candidate fails with the same code as a failure it already retried. A repeated delivery of the failure, a backend restart, a moved or superseded route generation, a session that is not waiting for input, a held candidate, or a setting turned off before the retry runs shall not submit a second or a stale retry. A pending retry shall survive a backend restart. Every other failure, an Office session, a workspace with the setting off, and every declined or stopped case shall keep the existing recovery surface. A person's Retry on a route waiting with no eligible candidate shall reselect in candidate order. When mid-turn provider failover is also enabled, its automatic Try next shall run first and the automatic retry shall apply only after the route reaches one of these recovery states.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.28:** Each workspace shall store an automatic failed-route retry setting that defaults to off and a retry limit from 1 to 3 that defaults to 1, for new and existing workspaces, through the workspace HTTP, WebSocket, and boot-state round trips; an omitted update shall keep the saved value and a limit outside 1 to 3 shall be rejected as a validation error. Workspace settings shall show the toggle and the limit, independent of the mid-turn failover toggle, to a workspace manager while dynamic agent routing is enabled.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.31:** When a workspace-only execution created with a logical profile is promoted to an agent execution after a concrete profile is resolved, the execution shall be bound to and persist that concrete profile, even when no Office profile is supplied. An acting Office profile shall remain in its separate field. Startup, persistence, and restart shall read the concrete profile.
