# Managed Git isolation rollout system design

## Purpose and ownership

Agents owns the flag. It gates the policy described in the [managed Git isolation design](managed-git-repository-code-isolation.md); that document describes the flag-on behavior and this one describes how the mode reaches each process.

## Requirement mapping

| Requirement | Sections |
| --- | --- |
| REQ-AGENTS-GITISOLATION-004 | Flag and mode propagation, Migration rule, Test order (AC-004.1 to 004.9) |

## Flag and mode propagation

The flag is registered in `internal/runtimeflags/registry.go` as `features.managedGitIsolation` / `KANDEV_FEATURES_MANAGED_GIT_ISOLATION` (`Kind` feature, `RestartRequired` true, `Mutable` true, medium risk whose description says hooks stop running for repositories that have not opted in), with a `Features.ManagedGitIsolation` config field and `profiles.yaml` values `prod: "false"`, `dev: "false"`, `e2e: "false"`. Only the "Run Git hooks" Playwright specs set `KANDEV_FEATURES_MANAGED_GIT_ISOLATION=true`, through the backend environment of those specs; every other test runs with the flag off. The registry, profile, and frontend completeness tests cover it (AC-004.1).

Mode propagation (AC-004.1, AC-004.2, AC-004.4, AC-004.5, AC-004.8, AC-004.9):

- **Backend process.** `subproc.SetManagedGitIsolation(bool)` is called once, during startup before any component can start Git, from the resolved config. It stores an atomic value that is never written again, so there is no race between callers and no mid-process flip (AC-004.4). The default before the call is off, matching a process that never reads the flag. The repository card uses the running value; the Feature Toggles API and page report the stored override, which can differ until restart.
- **gitinit helper.** The helper is the Kandev binary run as a child; the starter passes the mode as an explicit helper argument (`__git-init-open-directory-isolated` instead of `__git-init-open-directory`), not an environment variable. The helper sets its own process mode from that argument before it calls `ManagedGitArgs`, so it does not depend on inherited state.
- **agentctl.** `ControlClient.CreateInstance` sets `git_isolation` on the create request, beside the `git_hooks` map, only when the backend mode is on; with the flag off it neither sets `git_isolation` nor derives `git_hooks` (`collectGitHooks` returns no map). A request without the field is off, which is what an older backend sends. One agentctl process has one mode, because instances share the process-level `subproc` value (AC-004.4). `instance.Manager` takes the mode in `admitCreate`, under the same `m.mu` critical section that checks for a duplicate ID and registers the provisional bundle, rather than in a separate earlier step:
  - the live set is the published `m.instances` plus `m.provisional`; if it is empty, the request's mode is adopted, otherwise a differing mode returns `ErrGitIsolationMismatch` before a port or bundle is reserved (AC-004.8). Two concurrent opposite-mode creates against an empty process serialize on `m.mu`, so the second sees the first's provisional bundle and is refused;
  - the duplicate-ID, shutdown, and context checks, the agent-environment collection, and the port allocation all run before the mode is written; the mismatch check precedes the port reservation, but the mode write happens in the same step as `m.provisional[id] = bundle`, after every failure point of `admitCreate`, so no admission failure leaves a non-off mode on an empty live set. The mode is a function of the live set, not a per-create undo: it is held while `m.instances` plus `m.provisional` is non-empty and cleared to off at each place that removes an entry (instance removal, and `cleanupProvisionalInstance` deleting its bundle), in the same `m.mu` critical section as the removal. A create that fails after adoption therefore leaves the mode alone while an overlapping same-mode create is live, and clears it when it was the last. The clearing happens when the bundle is removed, which `abandonWG` does after the failed create has already returned (`CreateInstance` defer), so a response can precede the release; a provisional bundle whose cleanup failed stays in `m.provisional`, keeps the mode held and the other mode refused, and is cleared only by restarting agentctl, because `cleanupProvisionalInstance` runs once from the abandon goroutine and once from `Shutdown`; a published instance whose stop failed likewise keeps the mode until a retried stop succeeds, and an orphaned host-utility probe instance until the idle reaper removes it or agentctl restarts;
  - ID collisions keep their two existing errors: a published ID gives "already exists", a provisional ID gives "is still cleaning up"; neither changes the mode;
  - the error text names the requested and the held mode and says the instances of that agentctl process must be stopped first and that agentctl must be restarted if none can be stopped (a Kandev restart for the local agentctl; stopping that agentctl process or recreating the environment under agent survival or a remote executor). The backend returns it unchanged through the launch path, so it reaches the user as an ordinary launch error. A `Reset Environment` stops its instance before it creates, so it adopts the current mode when that instance was the last one, and is refused when another live instance, including a host-utility probe instance, holds the other mode;
  - a surviving agentctl (agent survival, remote executors) keeps its mode across a backend restart, so a flag flip is visible to it only after its instances are gone.
- **Capability.** `ControlClient.CreateInstance` checks `managed-git-policy.v1` before every create request, only when the backend's mode is on (AC-004.9). Host-utility probe instances take the same path, so they are checked and carry `git_isolation` too; AC-001.12 describes the user-visible launch failure for an execution, and a probe fails with the same error. agentctl advertises the capability whenever it contains the code, independent of the flag.
- **Frontend.** The repository card reads the flag through the existing runtime-flag boot payload, which carries the running value (AC-004.4). While it is off the switch stays rendered, is natively disabled, shows the stored value, and has `aria-describedby` pointing at the explanation paragraph; a disabled switch leaves the tab order, so AC-004.5 exempts it from keyboard reachability and relies on the description for assistive technology. The explanation copy is one string that is true in every non-running state (stored on with a restart pending, stored off, environment-set), so the card needs no override or lock state; it names Settings → System → Feature Toggles and the environment variable and is translated in every locale, without an em dash. The REST handler and store keep accepting `run_git_hooks` regardless of the flag, so the stored value survives flag changes (AC-004.5, AC-004.6).

## Migration rule

Migration rule for existing repositories (AC-004.6): none beyond the column default. `repositories.run_git_hooks` is `DEFAULT 0`, so every existing row is off, and enabling the flag changes no stored value. This is chosen over grandfathering existing repositories as on for three reasons: the hooks setting is a per-repository decision by the repository's owner and an automatic "on" would be made by Kandev for them; the repositories that exist when the flag is enabled are the ones whose shared Git directory an agent may already have written to, so keeping hooks running there preserves the exposure this capability closes; and the flag's off state, which is the default in `prod`, is the compatibility window in which operators can see which repositories rely on hooks before deciding. Turning the flag off again restores today's behavior for every repository without touching stored values.

## Test order

Tests for the off path are written first (TDD). A golden fixture, captured from the baseline before the policy code is applied and committed beside the tests, holds the argument vector, environment, and Git process count of one representative command for each of the interactive, lifecycle, and background helpers and the gitinit helper. A subproc test asserts the off-mode output equals it, so an equality test cannot pass after both sides regress (AC-004.2). An agentctl test asserts an absent `git_isolation` leaves hooks, fsmonitor, and filters in plain-Git behavior; a Manager test asserts no `git_hooks` seed, provider call, or capability check with the mode off. The agentctl `instance` tests cover the mismatch refusal, two concurrent opposite-mode creates, two same-mode creates where the first fails and the mode stays held, a last-instance failure that clears the mode once its bundle is removed, a cleanup-failed bundle that keeps the other mode refused, a published and a provisional duplicate ID with their two texts, a port-allocation failure on an empty process that leaves the mode off, and a probe instance holding the other mode (AC-004.8). A web unit test asserts the disabled switch carries `aria-describedby` that resolves to the explanation (AC-004.5).
