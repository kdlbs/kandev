# Coordinator merge stewardship Requirements

## Overview

A coordinator helps land linked pull requests and merge requests (changes) on watched cards. The coordinator owns proposal authority and its presentation; the provider owns change state and the final merge decision. This amends the human-only rule in [proposal kinds](proposal-kinds.md) and [permissions](permissions.md), the own-task wake boundary of phase 3 ([wake](wake.md)) and, for merge only, the create-time-only automatic attempt of [pause](pause.md), when the merge flag is enabled. Moving a task to Done stays human.

## Terms

- **Change key:** provider, canonical host, repository ID and change number.
- **Condition readings:** each check is *met*, *unmet* or *unavailable*. Pipeline: GitHub combines every check run of every check suite for the head SHA with the combined commit status (suites with no runs are ignored; a required context that is configured but not yet reported counts as pending); GitLab uses the latest pipeline by creation time then ID descending. Any failed, errored, cancelled or timed-out check is *red* (unmet); any queued, running or pending one is *pending* (unmet, not red); none reported is *none* (unmet, shown "No checks"); skipped or neutral count as success; all success is *green* (met). Approvals: no approval rule is met; an unreadable rule is unavailable. Threads: zero unresolved is met. Mergeable: the provider's explicit mergeable value; computing or unknown is unavailable. Conflict: GitHub mergeable false or state dirty, GitLab has_conflicts true; it clears on GitHub explicit mergeable true or GitLab has_conflicts false. GitLab mergeable means `detailed_merge_status` is `mergeable`; other statuses map per the design. A rate-limited, partial or failed read is unavailable. The GitLab `locked` state means a merge is in progress.
- **Creation codes** (closed): `policy_denied`, `predecessor`, `change_unknown`, `method`, `head_mismatch`, `unavailable`.
- **Refusal reasons** (closed), in recheck order: `authority`, `paused`, `repository_unavailable`, `closed`, `merged_elsewhere`, `stale_head`, `pipeline`, `not_mergeable`, `draft`, `approvals`, `threads`, `predecessor`, `method`, `unavailable:<condition>` where condition is one of head, pipeline, mergeable, draft, approvals, threads, predecessor, method; `expired` (before dispatch), and after dispatch `provider_rejected`, `not_merged`, `unconfirmed`. `authority` covers the flag or policy no longer allowing the merge and an invalid execution principal.

## Requirements

### REQ-COORDINATOR-MERGE-001: Change visibility and wakes

**Intent:** Managers and coordinators see the same actionable change state.

#### Acceptance criteria

- **AC-COORDINATOR-MERGE-001.1:** When a watched card has linked changes, Queue and coordinator turn context shall show each change's provider, repository, number, target branch, head SHA, pipeline state (green, red, pending or No checks), mergeability and conflicts, unresolved thread count, required approval status, draft state and behind count. Unknown values shall be labelled unavailable, never presented as passing; a failed provider read shall retain the card, show unavailable with retry and shall not replace the last successful values, which stay visible with their observation time. A successful read younger than 60 seconds is reused for that change key; a failed read is never reused, Retry always re-reads, and concurrent reads of one change key share one provider call.
- **AC-COORDINATOR-MERGE-001.2:** When a watched card's change becomes red, develops a conflict, or gains unresolved threads, the system shall record a wake through phase 3, subject to its autonomy, watch, admission, retention and delivery rules. Wake kinds are `change_red`, `change_conflict` and `change_threads`. The first observation of a change is a baseline and never wakes. Red clears on green or on a different head SHA; conflict clears as in Terms or on a different head SHA; pending, none and unavailable never clear either; threads clear at zero unresolved and wake only when the count rises from zero, so a new thread on a change that already has unresolved ones does not wake. A failed or unavailable first read is no baseline; the first successful read is. A condition that clears and recurs, or a head change onto an already red or conflicting head, is a new episode that wakes. A repeated observation of one episode creates no further wake, and an observation started before the stored one is discarded. One transition records a wake for every autonomy-on coordinator whose Watches cover a task linked to the change. A wake the 200 cap refused is stored later by the backstop from the open episode (Pause and admission hold delivery only); a coordinator that gains autonomy or a watch later receives wakes for episodes still open, never for baselines.
- **AC-COORDINATOR-MERGE-001.3:** When no changes are linked, the card shall show no change state; multiple changes shall be ordered by provider, repository identity and change number ascending.

### REQ-COORDINATOR-MERGE-002: Repository policy

**Intent:** A manager chooses merge authority separately for each repository.

#### Acceptance criteria

- **AC-COORDINATOR-MERGE-002.1:** Each coordinator and workspace repository pair shall have policy `denied`, `requires_approval`, or `automatic`; missing settings default to `denied`. A manager can change it, and readers and coordinator principals cannot. The settings UI shall show each repository and its effective policy, including on phone, with loading, save failure and retry states. For each repository and each target branch of its watched changes (the default branch when none), ascending by branch name, it shall show whether the provider enforces required pipeline, approvals and resolved threads as enforced, not enforced or unknown, and, when an `automatic` principal is no longer authorized, show it inactive with a Replace execution manager control that sends `replace_principal` and a message on 409 `principal_valid`. It shall state that conditions not enforced by the provider can change between the last check and acceptance, that a repository whose changes report no checks cannot be merged, and that a repository requiring a provider merge queue is unsupported.
- **AC-COORDINATOR-MERGE-002.2:** A changed policy shall be revisioned and audited with actor, repository, before, after and revision. The save may list some or all repositories; an omitted map or omitted repository is unchanged. A save in which any listed repository differs from the stored policy shall carry the read policy revision; a mismatch shall be refused with 409 `revision_conflict` and a missing one with 400 `revision_required`, storing nothing, and the revision check precedes the no-change check. Saves that change no repository policy keep their existing behaviour and need no revision. An unchanged save shall create no revision or audit entry, and one save applies atomically. Other policy writes shall preserve these settings. Changing a repository to `automatic` records the selecting manager as its execution principal and the revision at which it took effect. A listed entry for an already `automatic` repository is unchanged unless it carries `replace_principal`; with it, when the stored principal is no longer an authorized manager the saver replaces it as an audited `principal_replaced` change that needs the revision, bumps it and keeps the `automatic` revision, and while the principal is valid the save is refused 409 `principal_valid`.
- **AC-COORDINATOR-MERGE-002.3:** `denied` shall prevent a merge proposal. `requires_approval` shall require a manager's approval. `automatic` shall be an explicit manager choice independent of raisable-class eligibility, subject to Pause, the coordinator-wide daily automatic limit and phase 3 containment and admission.
- **AC-COORDINATOR-MERGE-002.5:** When provider protection settings are read, the system shall record the repository, target branch, observation time and each protection as enforced, not enforced or unknown. A failed or unsupported read shall record unknown, never infer enforcement, and shall not by itself disable the manager-selected policy. Reads happen when settings open, on retry, and when a repository first leaves `denied`. GitHub counts classic branch protection and rulesets; a classic 404 is unknown unless admin access is confirmed. Settings shall offer a retry that refreshes every branch shown.
- **AC-COORDINATOR-MERGE-002.4:** A provider-rejected automatic merge or an automatic dispatch reconciled `not_merged` shall lower that repository's automatic policy to `requires_approval`, as shall a confirmed revert of an automatically executed merge. Lowering applies only when the stored policy is still `automatic` with the same `automatic` revision recorded at the dispatch, so it never overwrites a stricter or newer manager setting; it takes the lock, retries once on contention, is audited and shown in activity, and is recorded once per dispatch; a lowering that still fails stays pending on the dispatch, the backstop retries it each pass, and automatic proposals for that repository stay `pending` and unclaimed, evaluated again each pass, meanwhile. Preflight refusals, `stale_head`, `authority`, `closed`, `merged_elsewhere`, `unconfirmed`, `expired`, transport errors still uncertain and merges a manager approved shall not lower. A revert is confirmed when, within 7 days of the provider's merge time, a target-branch commit states `This reverts commit <recorded merge commit SHA>`; where the provider cannot list commits, revert status shall be unknown and nothing lowers.

### REQ-COORDINATOR-MERGE-003: Ordered, guarded merge

**Intent:** Merge only the reviewed change after its predecessors land.

#### Acceptance criteria

- **AC-COORDINATOR-MERGE-003.1:** A manager may declare or replace a card’s set of predecessor task IDs or provider change references in the coordinator UI; a reader or coordinator principal cannot change it. A save with duplicate or self references shall be refused without changes; dependencies are stored per coordinator and task with their own revision (first save expects revision 0), a save without the revision is refused with 400 `revision_required`, a stale save with 409 `revision_conflict`, and each change is audited with actor, card, before, after and revision. A merge proposal shall not be created while any predecessor is unresolved, unknown, inaccessible, ambiguous or unmerged. An empty set has no predecessors. A predecessor task with no or several linked changes, a closed unmerged change, one that was deleted or archived, or a change reference no longer linked to any task blocks until a manager removes it; a dependency cycle blocks every member. Execution reads the set under the coordinator lock at the recheck and dispatches only if its revision equals the one read; otherwise the recheck repeats. A task reference and a change reference naming one change are duplicates; a task naming its own change is a self reference; cycles are detected within one coordinator's set.
- **AC-COORDINATOR-MERGE-003.2:** A proposal shall identify one watched card, linked change, expected head SHA and merge method derived from repository settings; the creating coordinator’s policy and dependency set govern it. The coordinator creates it with `propose_merge_kandev` (task, optional change when the task has one, observed head SHA), offered only while some repository is not `denied`. Creation shall refuse with a creation code and an activity row, storing no proposal, in the order `change_unknown`, `policy_denied` (on the resolved change's repository), `predecessor`, `method`, `unavailable`, `head_mismatch` (observed head differs from a fresh read). After those checks, an open proposal for the same change key in the workspace, whatever the card or coordinator, is returned instead of creating another, shown with its owning coordinator; but a `pending` one whose head differs from the observed head is first settled `refused (stale_head)` and a new proposal is created, while an `approving` or `uncertain` one is returned unchanged. Unknown or unsupported identity, method, predecessor or state shall refuse the proposal without a provider mutation. The tool returns `{proposal_id, status, reason?, creation_code?}` after evaluating an automatic proposal but never dispatching, which a later pass performs; `status` and `reason` reflect that evaluation; on a creation refusal `proposal_id` is null and `status` is `refused`.
- **AC-COORDINATOR-MERGE-003.3:** Immediately before dispatch after approval or automatic execution the system shall recheck, uncached, in the refusal-reason order of Terms: authority; Pause (automatic execution only; a manager’s approval is not blocked by Pause); repository available; change not closed or merged elsewhere; current head equals expected head; pipeline green for that head; mergeable and conflict-free; not draft; required approvals met; no unresolved threads; all predecessors merged, checked in canonical provider, host, repository and change-number order; and method still allowed. It shall refuse at the first unmet or unavailable check, record the reason and make no merge request to the provider. The provider request shall include the expected head and merge method and shall not force, bypass checks, push, or enable deferred provider auto-merge. A `paused` result on an automatic attempt leaves the proposal `pending` as `manager_only` (AC-COORDINATOR-MERGE-003.8), not refused; any waiting reason of AC-COORDINATOR-MERGE-003.8 at an automatic attempt likewise returns the claim to `pending` with no dispatch and no daily-limit count. A manager’s approval refused by the recheck settles the proposal `refused` with that reason. A refused automatic attempt before dispatch does not count toward the daily limit; a dispatch does, including an uncertain one.
- **AC-COORDINATOR-MERGE-003.8:** An automatic merge proposal shall be evaluated when created and then on every backstop pass, using the recheck of AC-COORDINATOR-MERGE-003.3 without dispatch. While the first unmet condition is a waiting one (pipeline pending or none, `unavailable:*`, `draft`, `approvals`, `threads` or `predecessor`) it stays `pending` and records an activity row only when the reason changes; any other unmet condition settles it `refused` with that reason, so a red pipeline or a conflict is refused and the coordinator may propose a fixup. An automatic proposal records the `automatic` revision at creation; if the stored policy is no longer `automatic` at that revision it becomes `manager_only` (`policy_changed`). The execution principal is checked at claim and at the dispatch recheck only. Pause is checked at each pass; the daily limit, containment and admission only once all conditions are met, together with the dispatch-record insert under the coordinator lock. When any of them prevents the attempt, it stays `pending` for a manager as `manager_only` with a note naming the reason and is never evaluated automatically again. When all conditions are met and none prevents it, it is claimed automatically and dispatched. A head change settles it `refused (stale_head)`, and one still `pending` 7 days after creation, `manager_only` or not, settles `refused (expired)`. These settlements, a change merged or closed elsewhere (`merged_elsewhere`, `closed`) and a stored policy of `denied` (`authority`, taking precedence over `policy_changed`) apply to every pending merge proposal, `requires_approval` included, on each backstop pass and when a manager opens its detail or approves it, each with one uncached read.
- **AC-COORDINATOR-MERGE-003.7:** When the provider rejects the merge, the proposal shall end `refused (provider_rejected)` with the bounded provider reason, its dispatch settles, and an automatic attempt shall lower that repository to `requires_approval` under AC-COORDINATOR-MERGE-002.4. Conditions the provider does not enforce, including strict up-to-date rules, signed-commit rules and required merge queues, can change or apply between the last check and acceptance and surface as this rejection, except a response that the expected head no longer matches, which is `refused (stale_head)`, settles the dispatch, counts toward the daily limit and lowers nothing.
- **AC-COORDINATOR-MERGE-003.4:** Concurrent approvals and retries for one proposal shall produce at most one provider merge request. A changed head shall refuse as stale. An uncertain provider outcome shall be reconciled from provider state and shall not be blindly retried; a merged change shall be recorded as merged only when confirmed. A queued, `locked` or otherwise in-progress response is `uncertain`. If confirmation is unavailable, the proposal stays `uncertain`, visible to a manager, and blocks any proposal for that change key in the workspace; a manager may Release an `uncertain` proposal more than 24 hours after its dispatch record, settling it `refused (unconfirmed)` without a provider request. Statuses: `pending`, `approving`, `uncertain` are open; `approved` means merged and confirmed; `refused` and `rejected` are settled, and a new proposal is needed after either. The dispatch record is unique per change key and head only while unsettled; a settled dispatch releases the head. A stale `approving` claim (the 2-minute claim window, or the 60-second execution deadline firing) returns to `pending` when no dispatch was recorded and becomes `uncertain` when one was; it never becomes `failed`. Each claim carries a generation, compared inside the dispatch transaction, so a recovered claim's original worker cannot insert a dispatch; a provider response that arrives after reconciliation or Release settled the dispatch is recorded as a note, changes no status and lowers nothing. Reconciliation runs each backstop pass and on a manager's Check now, reading the change at least 10 minutes after the dispatch record: merged at the expected head is `approved`; open (not `locked`) and unmerged is `refused (not_merged)` unless the dispatch recorded a queued or in-progress response, which keeps it `uncertain`; closed unmerged is `refused (closed)`; merged at another head is `refused (merged_elsewhere)`; each settles the dispatch. Approving an `uncertain` proposal is refused. The backstop visits every coordinator holding an open merge proposal, a pending lowering or an active revert watch, whatever its autonomy.
- **AC-COORDINATOR-MERGE-003.5:** The activity log, ledger and proposal outcome shall identify the change, decision and result. The UI shall state that a merge cannot be undone here and offer no Undo. A red pipeline shall be visible to the coordinator so it can propose an ordinary message or move for fixup; it shall not independently push a fix.
- **AC-COORDINATOR-MERGE-003.6:** When `features.coordinatorMerge`, `features.coordinator`, `features.coordinatorPhase2` or `features.coordinatorPhase3` is off, the system shall hide merge controls, create no merge proposal or merge wake and execute no merge; stored data is retained. Provider reads, wakes and reconciliation pause, but the claim recovery of AC-COORDINATOR-MERGE-003.4 still runs as a status write without any provider call: an `approving` claim with no recorded dispatch returns to `pending` and one with a dispatch becomes `uncertain`; a request already in flight records its own result, and the flags are re-read inside the dispatch-record transaction, the last point dispatch can be stopped. While any of these flags is off, automatic evaluation, expiry and stale settlement are skipped; `manager_only` survives a flag cycle and other automatic `pending` proposals are evaluated again when the flags return. The flag defaults off in production and requires the existing coordinator phase flags.

## Out of scope

- Tagging, releases, publishing, branch pushes, provider force or bypass options.
- Automated edits to consuming repositories' instruction files, and enforcement of their text.
- Automatic acceptance of inferred dependency order; inference is advisory until confirmed by a manager.
- Creating merge queue entries; repositories requiring a provider merge queue are unsupported.
