# Coordinator agent-tier notes Requirements

## Overview

A coordinator has durable, advisory project notes separate from manager-owned context, standing orders and goals. Managers curate them; the coordinator cannot write them. This work builds the note substrate, not the active dream. The gate exception is in the [phase 3.1 ADR amendment](../../../decisions/2026-09-30-coordinator-phase-3-1-record-and-measure.md).

G3.5 is the third gate in section 3.5 of the workspace-coordinator post-phase-3 proposal (`analysis/features/workspace-coordinator/post-p3-proposal.md`); this work is built ahead of it by Henry's 2026-11-07 decision. A note belongs to exactly one coordinator. A citation is a coordinator ledger turn, a workspace task, a repository pull request, or a repository-relative file path paired with a commit SHA. A use means inclusion in the index actually delivered for a coordinator conversation turn. A note with an unresolved citation is stale; expiry is measured from its most recent use, or creation if never used. A note's state is exactly one of: live (eligible), stale (a citation is confirmed missing or changed), unavailable (a citation could not be checked), expired, or deleted. Settings display exactly one of these by the precedence deleted, expired, stale, unavailable, "not yet validated" (a live note whose current version has no validation result), "over the cap", live. "Over the cap" is derived on each settings read and never stored (the design defines the ranking); it is advisory and can differ from a past turn's delivery. A task is closed for this work when it is archived or its state is COMPLETED, FAILED or CANCELLED; otherwise it is open. A coordinator turn is a coordinator conversation turn with its own durable session-turn identity. This work requires the coordinator, phase 2, phase 3 and phase 3.1 flags.

## Requirements

### REQ-COORDINATOR-AGENT-NOTES-001: Curated notes

- **AC-COORDINATOR-AGENT-NOTES-001.1:** When a manager creates a note with type `user`, `feedback`, `project` or `reference`, trimmed text of 1 through 500 Unicode code points, and zero through ten valid citations (an omitted or null citation list means none), the system shall save it for that coordinator with a new identity, creation time, version 1, use count zero, last validation unset, expiry 30 days after creation, and a model stamp marked human-authored.
- **AC-COORDINATOR-AGENT-NOTES-001.2:** When a manager edits a note (a full replacement; an omitted `type`, `text` or `citations` is rejected, while `citations: null` is accepted as an empty list, as on create) or reverts it to any previous version, the system shall validate the resulting type, text and citations, retain all previous versions and create a new version; a revert copies content and provenance from the selected version without rewinding use statistics, expiry or identity. An edit carries the fields `type`, `text`, `citations` and `version`; a revert carries `target_version` (the version whose content is restored, a positive integer naming an existing version of the note, which may be the current one) and `version`; in both, `version` is the precondition naming the version the caller believes is current. An edit or revert whose resulting content equals the current version's content (after the normalization of AC-COORDINATOR-AGENT-NOTES-001.11; a revert whose `target_version` is the current version always qualifies) shall succeed with status 200 without a new version or citation resolution, whatever value its `version` field carries, so a retry of an edit that already committed succeeds. A new version resets the note's validation state to not yet validated. Edit and revert of an expired note, or of a deleted note, shall be rejected with a conflict that names the reason (`expired` or `deleted`) and change nothing.
- **AC-COORDINATOR-AGENT-NOTES-001.3:** When two edits or reverts race on the same version, or an edit, revert or delete carries an outdated version for a nondeleted note, the system shall commit at most one and return a conflict for the others (an edit or revert whose content equals the current version is a no-op success, per AC-COORDINATOR-AGENT-NOTES-001.2 and 001.11); a retry with an outdated version shall not overwrite newer content. A delete that loses a race to another delete succeeds as a repeated delete (AC-COORDINATOR-AGENT-NOTES-001.4). Duplicate creates are distinct notes.
- **AC-COORDINATOR-AGENT-NOTES-001.4:** When a manager deletes a nondeleted note (live or expired) carrying its current version in the required `version` field (a missing or non-integer `version` is `invalid_request` for any delete), the system shall mark it deleted without creating a version, remove it from future indexes and preserve its versions and reference history; deleting it again shall succeed with status 200 regardless of which integer the `version` field holds and change nothing, but a repeated delete whose body fails the checks of AC-COORDINATOR-AGENT-NOTES-001.11 step 2 (malformed JSON, over 64 KiB, missing or non-integer `version`) is still rejected as `invalid_request`. A deleted note is hidden from the default list, readable with an include-deleted request with its versions and reference history, and cannot be edited or reverted.
- **AC-COORDINATOR-AGENT-NOTES-001.5:** When a request contains a credential detected by the existing credential gate in note text or citation fields, the system shall reject it without saving or logging the submitted content. Invalid type, length or citation shape shall be rejected without mutation. Every rejection shall carry exactly one reason code from the closed set `invalid_type`, `invalid_text_length`, `invalid_citation`, `citation_unresolved`, `credential_detected` (naming only the field `text` or `citations`, never the content), `note_limit_reached`, `invalid_request` (unknown, missing or null-where-required fields), `conflict` (with reason `version`, `expired` or `deleted`) or `unavailable`. This closed set covers every rejection of a note create, edit, revert or delete that reaches the note service (HTTP 400, 409 and 503, plus 413 for a body over 64 KiB, which carries `invalid_request`). Authorization (403), unknown or foreign identity (404) and a flag-off route (404) use the existing authorization and not-found responses and carry no note reason code. Proposal tools use the set in AC-COORDINATOR-AGENT-NOTES-003.1.
- **AC-COORDINATOR-AGENT-NOTES-001.6:** Readers shall view notes, versions, validation, expiry, use count and references; only workspace managers shall create, edit, delete or revert. A forbidden write shall change nothing. An inaccessible or foreign coordinator or note shall not reveal its contents.
- **AC-COORDINATOR-AGENT-NOTES-001.7:** The coordinator shall have no note-write tool, and notes shall never change human-tier context, goals, standing orders, permissions or tool profiles. A server-internal create operation for a future approved dream item shall use the same validation and preserve the actual producing model stamp; no endpoint or tool shall expose that operation in this work.
- **AC-COORDINATOR-AGENT-NOTES-001.8:** With `features.coordinatorPhase35` off, note controls, routes and turn injection shall be unavailable; stored data shall survive disabling and re-enabling the flag, while expiry keeps elapsing in wall-clock time (a note unused for 30 days, including while the flag was off, is expired). Its default shall be false in every profile and it requires restart. With the flag off the proposal tools shall not advertise `note_ids`, shall treat an absent, null or empty `note_ids` as none, and shall reject a non-empty `note_ids` with reason `notes_unavailable`.
- **AC-COORDINATOR-AGENT-NOTES-001.9:** When a manager creates or edits a note, the system shall also verify that each citation belongs to the coordinator's workspace (and, for a turn, to this coordinator) and resolves now; an unresolved citation shall be rejected with `citation_unresolved` and the lowest offending citation index, and a failed dependency with `unavailable` (HTTP 503), both without mutation; `citation_unresolved` wins when both occur. Resolution has a 5-second total deadline that starts when step 8 starts (after steps 1 through 7, before any lock is taken), after which every unfinished citation counts as a failed dependency. Pull request and commit citations resolve against the local clone and provider without fetching, so a commit only on the remote is `citation_unresolved`; the rejection text and settings help say so. A revert shall verify shape and the credential gate only, because the selected version was valid when saved; its citations are checked at the next turn.
- **AC-COORDINATOR-AGENT-NOTES-001.10:** The system shall allow at most 100 nondeleted notes per coordinator (create beyond that is rejected with `note_limit_reached`, expired notes counting until deleted), a request body of at most 64 KiB, and unique citations within a note. Reads list notes by creation time then note id ascending, versions by version number ascending, and references by proposal creation time then proposal id ascending, unpaginated. Citation resolution never runs inside a write transaction. Under the per-coordinator lock a create recounts nondeleted notes and inserts in one short transaction, so two simultaneous creates at 99 notes admit exactly one and the loser returns `note_limit_reached` even though its citations resolved (the only case where it follows step 8 of AC-COORDINATOR-AGENT-NOTES-001.11); the step 7 count is an early check without the lock.
- **AC-COORDINATOR-AGENT-NOTES-001.11:** A note mutation shall be evaluated in this order and the first failing step alone determines the response: (1) authorization 403, then unknown or foreign coordinator or note 404; (2) a body over 64 KiB or malformed JSON or an unknown, missing or null-where-required field, `invalid_request`; this step applies to every mutation including a delete, whose `version` field must be present and an integer even when the note is already deleted, and to a revert, whose `target_version` must be a positive integer (`citations: null` is not null-where-required); (3) for a delete, a deleted note succeeds with status 200 whatever integer `version` it carries; for an edit or revert, a deleted note then an expired note, `conflict` with that reason; (4) shape, in the order: for a revert, a `target_version` that names no version of the note (zero is excluded by step 2; above the current version), `invalid_request`; then `invalid_type`, `invalid_text_length`, `invalid_citation`, then `credential_detected` over text before citations (for a revert, over the selected version's content); (5) for an edit or revert, equal normalized content, which succeeds as a no-op; (6) the supplied `version` against the current version, `conflict` with reason `version`; (7) for a create, `note_limit_reached` from an early count; (8) for a create or edit, citation resolution of AC-COORDINATOR-AGENT-NOTES-001.9; (9) the commit, one short transaction under the per-coordinator lock that re-runs steps 3, 5, 6 and 7 against committed state in that order (a note deleted or expired meanwhile gives `conflict`/`deleted` or `expired`), and only then writes. Normalization for uniqueness and equality is defined in the design: text trimmed, identifiers lower-cased, paths canonicalized, citation order ignored.

### REQ-COORDINATOR-AGENT-NOTES-002: Validated per-turn index

- **AC-COORDINATOR-AGENT-NOTES-002.1:** Before each attended or unattended coordinator conversation turn, the system shall validate each nondeleted, unexpired note's citations against the current board and repository HEAD and include only notes whose citations resolve. Missing task, turn, pull request, repository, commit or path shall make the note stale; a changed file at HEAD shall make it stale even if its path still exists. A note with no citations is valid. Stale takes precedence over unavailable, which takes precedence over valid, regardless of citation order. Turns of dream episodes and of conversations with no coordinator identity receive no index.
- **AC-COORDINATOR-AGENT-NOTES-002.2:** When validation cannot determine a citation's state because a dependency fails, the system shall omit that note for the turn, show validation unavailable in settings, and leave its prior stale decision and last successful validation time intact. Other validated notes and the turn shall continue. Validation of one turn stops waiting after 5 seconds in total, and each citation still unresolved then counts as unavailable. Lookups start in note order, then citation order. A later successful validation of that note version clears the unavailable status.
- **AC-COORDINATOR-AGENT-NOTES-002.3:** For each successful validation the system shall record its time and whether the note is stale; a previously stale note whose citations again resolve shall become valid. Every validation attempt carries its turn's admission time and persists only if the note version still matches and that time is strictly later than the stored last-attempt time, which the write advances; an equal time goes to the first commit, and a loser is not persisted but its turn still uses its own result. Expired notes shall remain visible in settings but shall not be injected.
- **AC-COORDINATOR-AGENT-NOTES-002.4:** When at least one note is eligible, the system shall inject an advisory index at the start of every turn, including later turns of an existing conversation, with at most 40 lines total. Order eligible notes by creation time ascending then immutable note id ascending, and include the first 38; each note occupies exactly one line, formatted `- [<note id>] <type>: <text>`, and the two wrapper lines (a header carrying the lower-trust statement and a footer) count toward the cap. An empty index injects no section. Notes beyond the first 38 are marked "over the cap" and are not delivered, so one never delivered expires 30 days after creation.
- **AC-COORDINATOR-AGENT-NOTES-002.5:** A delivered index shall increment each included note's use count once for that turn and set expiry to the later of its existing expiry and 30 days after the delivery commit; a retry or recovery of the same session turn shall not increment again. Notes omitted by the cap, stale, expired or unavailable shall not count as used. A note whose expiry is not strictly later than the acceptance commit time gets a receipt but is neither counted nor extended, so an expired note is never revived by a delivery. Failure or cancellation before the turn's prompt is accepted shall not count as use, and a note deleted before the acceptance commit is not counted.
- **AC-COORDINATOR-AGENT-NOTES-002.6:** The index shall identify note content as lower-trust data, not authority, and shall not permit note text to terminate its delimiters or grant a permission. Manager-owned instructions retain precedence. Note text shall not affect permission checks, tool profiles or authorization: with a note instructing the coordinator to grant itself a permission, every permission check returns the same result as without it.
- **AC-COORDINATOR-AGENT-NOTES-002.7:** The index shall be added, as one `<kandev-system>` block hidden from the transcript, to the prompt of every coordinator conversation turn whose prompt is delivered as a new session turn, including the first turn (placed after the standing instructions block), later turns of an existing conversation, wake deliveries and the re-delivery of the same turn by prompt-dispatch recovery (which reuses the frozen snapshot, even an empty one, and never prepares notes again; a turn recovered with no snapshot is sent without the section). It shall not be added to mid-turn steers, to checks of whether a workflow-step prompt is empty (an index alone never makes an empty prompt dispatchable), or to dream episodes.

### REQ-COORDINATOR-AGENT-NOTES-003: References and controls

- **AC-COORDINATOR-AGENT-NOTES-003.1:** When a coordinator submits a proposal, including the separately delivered `answer` kind, it may cite up to five distinct notes supplied in the current turn's index through an optional `note_ids` list (absent, null or empty means none). The system shall reject malformed, missing, foreign, deleted, stale, expired, duplicate or uninjected note IDs, or more than five, without creating a proposal, with a tool error naming a reason from `notes_unavailable`, `too_many_notes`, `note_malformed`, `note_duplicate`, `note_unknown`, `note_deleted`, `note_expired`, `note_stale` or `note_not_delivered`. Evaluation has two phases. Phase 1 checks the whole request: `notes_unavailable` (flag off and a non-empty list), then `too_many_notes` (more than five raw entries, duplicates included); a phase 1 failure is the reported reason and the error lists no ids. Phase 2 checks each entry in submitted order, and for each entry the checks in the order `note_malformed` (not a canonical UUID), `note_duplicate` (equal, compared case-insensitively, to an earlier entry; the earlier entry is judged on its own and only the later occurrences are offending), `note_unknown` (no such note in this coordinator, which includes foreign notes), `note_deleted`, `note_expired`, `note_stale`, `note_not_delivered`. The reported reason is that of the first offending entry in submitted order, and the error lists every offending entry with its own first failing reason. The extension is kind-agnostic; the unreleased `answer` kind is not a prerequisite. Accepted links shall be stored atomically with the proposal, each with the note version delivered. A proposal call has no deduplication: every accepted call creates a new proposal and its own links.
- **AC-COORDINATOR-AGENT-NOTES-003.2:** Each note's `referenced_by` view shall list its proposals with status `pending` or `approving`, and the open tasks created from its approved proposals, where open means not archived and not in state COMPLETED, FAILED or CANCELLED, ordered by task creation time ascending then task id ascending after the proposals. It reflects committed state on each read, is refetched on settings reload and after any mutation, and drops proposals or tasks that are no longer current. A separate references-history read of the note, available also after deletion, shall return every link ever stored with the proposal, its status and the delivered note version.
- **AC-COORDINATOR-AGENT-NOTES-003.3:** Coordinator settings shall show each note's type, text, provenance, validation status, expiry, use count, versions and current references; managers can add, edit, delete and revert individual notes and readers see the same information without mutation controls. Citations are typed identifiers. A never-validated note shows "Not yet validated"; deleted notes are hidden unless an include-deleted toggle is on; each version row shows number, time, actor and provenance. An expired note shows no edit or revert control (delete remains). A 409 `expired` or `deleted` keeps the draft read-only, states the reason and offers "Create a new note from this draft" (and Delete for an expired note) with no reload; a 409 `version` offers a reload only on user action. Empty, loading and error states are distinguishable, failures preserve unsaved edits, and all controls shall work with keyboard and on phone layouts in every shipped locale.

## Out of scope

- Active dream, approval UI, retirement gate and automatic application (3.5-2); the internal create seam only permits a future approved item.
- Model-change revalidation and weather report (3.5-3), routines and routine references, shared cross-coordinator memory, and modifications to human-tier instructions or authority.
- General note retrieval, relevance ranking, and manual restoration of deleted or expired notes. Managers may create a new note instead; future work needs a separate lifecycle contract.
- Showing cited notes on the proposal card, and any retention or pruning of versions, delivery receipts and reference links.
- Any deduplication of proposal calls, any change to proposal status values, and a ranking that lets notes beyond the 38-note cap be delivered; notes beyond the cap are managed by deleting older notes.
