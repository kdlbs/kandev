# Coordinator merge stewardship System Design

## Purpose and boundaries

The coordinator owns the proposal, repository policy and wake records. GitHub and GitLab own provider observations and mutations. The answer-proposals slice ([ADR](../../../decisions/2026-11-07-coordinator-answer-proposals.md)) adds the `answer` kind and policy class; this design assumes only that the proposal-kind registry, tool-profile derivation and executor guard accept one more kind. Merge detail lives in its own table keyed by proposal ID so the shared proposal schema gains only the kind value and statuses. Build starts on that slice's branch and reconciles any schema difference first.

## Observations and wakes

Use workspace-scoped GitHub and GitLab integrations, keyed by change key; never infer authority from a URL alone. Producer: a change observer reads through the existing PR and MR status sync where it already stores state and through the workspace services otherwise. Reads occur on the backstop pass for coordinators with autonomy on, on Queue or settings views, and uncached before dispatch. A successful read is reused for 60 seconds per change key and concurrent reads share one provider call (single flight); a failed read is never cached, Retry bypasses the reuse, the last successful values stay displayed with their time beside the unavailable marker, and a rate-limited, secondary-limited, partial or failed response backs off to the next pass and never clears a condition. Readings follow the Terms in the requirements: for GitHub the pipeline is every check run of every suite plus the combined commit status, with required contexts from branch protection that are unreported counted pending, and empty suites ignored. Provider data is untrusted and rendered as data. The Queue labels an absent pipeline "No checks".

Persist one condition row per (change key, kind) with `state`, `generation`, `head_sha`, `baseline` and `last_observed_at`, where the compared time is the read start, so a concurrent older read is discarded. The first successful observation inserts a baseline row and never wakes; a failed or unavailable read inserts nothing. Reads with equal start times keep the stored row (first writer wins). A changed head that is already red or conflicting clears the old episode and opens a new one in the same transaction, which wakes. A newer observation transitions the row in one transaction that also inserts one wake for every autonomy-on coordinator whose Watches cover a task linked to the change, under the unique (coordinator, task, kind, episode key). Conflict means GitHub `mergeable` false or `mergeable_state` dirty and GitLab `has_conflicts` true (other GitLab not-mergeable statuses are not conflicts). GitLab mergeable is `detailed_merge_status` `mergeable`, falling back to `merge_status` `can_be_merged` only when the detailed field is absent; a conflict clears when `has_conflicts` is false. Detailed statuses map to readings: `not_approved` and `approvals_syncing` to approvals, `discussions_not_resolved` to threads, `ci_must_pass` and `ci_still_running` to pipeline, `draft_status` to draft (all waiting), `checking`, `unchecked`, `preparing` and `locked` to `unavailable:mergeable`, and any other not-mergeable status (for example `need_rebase`, `blocked_status`) to `not_mergeable` only when no earlier-ordered condition explains it. Red clears on green or a changed head, conflict as above or on a changed head, threads at zero unresolved; each is raised again by the next red, conflict, or zero-to-positive threads, bumping `generation`. The episode key is `change key + generation`. Event, Queue-path and backstop reads share this function. Pause and admission delay delivery only, as for every wake; a wake the 200 cap refused is stored by the backstop, which derives missing wakes for each autonomy-on coordinator from open non-baseline rows, so a late-autonomy coordinator also receives open episodes. Wake kinds `change_red`, `change_conflict` and `change_threads` join the closed kind set; the delivery message is bounded text of provider, repository, number, condition and head SHA, as data. Watched non-own cards wake only for these kinds.

## Policy

Store a mapping from workspace repository ID to {policy, selecting manager, automatic_since_revision} on each coordinator, default denied. `withCoordinatorLock` exists today but last write wins; add an expected-policy-revision compare to `PUT` settings, required only when a listed repository differs from the stored one (400 `revision_required`; mismatch 409 `revision_conflict`; checked before the no-change test); an omitted map or repository is unchanged; the whole save is atomic; other saves keep today's behaviour. A repository policy change increments `policy_revision`, which also keys the tool-profile cache; dependency edits do not. Audit before/after in the same transaction. Preserve unrelated eligibility and action settings. Deleted or inaccessible repositories are denied; never transfer a setting to a new repository with the same name. The selecting manager is the execution principal and is revalidated before automatic claim; when invalid the claim refuses `authority`, nothing lowers, settings show automatic as inactive, and another manager saving `automatic` with `replace_principal` replaces the principal as `principal_replaced`, bumping `policy_revision`; while it is valid it cannot be replaced. Settings show an inactive automatic repository as "Automatic inactive: execution manager is no longer authorized" with a "Replace execution manager" control that sends `replace_principal`; a 409 `principal_valid` shows "The execution manager is still authorized". On a stale revision `revision_conflict` wins over `principal_valid`. Strings are localized in all seven locales. Repository policies are ordered by repository display name then repository ID ascending. A system lowering is a value compare under the same lock: it applies only if the stored policy is `automatic` and `automatic_since_revision` equals the one recorded on the dispatch, retries once on contention, bumps the revision, audits once per dispatch, and a stricter or newer manager setting wins. If the retry also fails, the lowering stays pending on the dispatch row, the backstop retries it each pass until it applies or the compare no longer matches, activity shows it, and automatic proposals for that repository are not claimed, stay `pending` and are evaluated again each pass until then; the pending-lowering check also runs inside the dispatch-record transaction under the coordinator lock. A listed `automatic` entry for an already `automatic` repository is a no-op unless it carries `replace_principal`; with the marker it counts as differing for the revision check, bumps `policy_revision`, leaves `automatic_since_revision` unchanged and audits `principal_replaced`, and while the principal is valid it returns 409 `principal_valid` and stores nothing. Repository policy is independent of `raisableClasses`; its automatic claims share the daily budget (counted at dispatch) and unattended admission, and apply to proposals raised in any turn.

## Execution and recovery

**Dependencies.** The settings/Queue manager action replaces a card's complete set; an absent set is empty. Store them per coordinator and task with a `dependency_revision` (first save expects 0), by task ID or canonical change key validated in the workspace. Refuse empty or malformed references, duplicates, self references, a missing revision (400) and stale saves (409) unchanged; audit each change. A task reference resolves only when it has exactly one linked change, otherwise it blocks; a change key no longer linked to any task, a deleted or archived task, and every member of a cycle also block. Manager confirmation writes inferred suggestions; this cycle defines no suggestion producer, so only manager-declared sets exist. The dependency lock is the coordinator lock (`withCoordinatorLock`). The recheck reads the set under it and dispatches only if the revision still equals the one read; if an edit intervened the recheck repeats once with the new set, and a second change leaves the proposal `pending` for the next pass (no refusal reason; for a manager's Approve an activity row records it and a manager approves again). A task reference resolving to the same change key as another entry is a duplicate; a task whose only change is the proposal's is a self reference. Cycles are found within one coordinator's set, over resolved change keys. Predecessors are evaluated sorted by provider, normalized host, repository ID and numeric change number ascending.

**Proposal.** `propose_merge_kandev(task_id, change?, expected_head_sha)` is in the coordinator's tool profile while the flag is on and some repository is not `denied`. It validates in the order `change_unknown`, `policy_denied` (on the resolved change's repository), `predecessor`, `method`, `unavailable`, `head_mismatch` (against a fresh read) and returns `{proposal_id, status, reason?, creation_code?}` immediately (null `proposal_id` and `status` `refused` on a creation refusal; it never waits for dispatch; an automatic proposal is evaluated before the tool returns, so `status` and `reason` reflect that evaluation (`reason` is set when refused or `manager_only`), but dispatch runs in the executor on the next pass), writing an activity row for each refusal; then it applies the dedupe rule of AC-003.2 (return the open one, or settle a `pending` one with a different head `refused (stale_head)` and create anew). The proposal freezes repository ID, change key, head, method and the creating coordinator, whose policy and dependency set govern it; a manager editing another coordinator's set does not affect it, and the owning coordinator is shown. Method comes from provider settings using the GitHub default selection (`pickDefaultMergeMethod`); for GitLab the frozen method is `squash` when the project squash option is always or default on and `merge` otherwise (the frozen method is a label for the squash flag: Kandev passes an empty method plus the squash flag so fast-forward and rebase project methods remain valid, and the `method` recheck compares the squash option and that the project still allows merging); unsupported or unknown refuses. Merge detail is stored in a merge table keyed by proposal ID with a unique partial index on (workspace ID, change key) for open statuses, so concurrent creations across cards and coordinators in a workspace converge on one row.

**Automatic evaluation.** Merge duties (evaluation, settlement, reconciliation, lowering retry, revert scan) run in the backstop step that runs whatever autonomy reads, for every coordinator holding an open merge proposal, a pending lowering or an active revert watch. An automatic merge proposal is evaluated at creation and on each backstop pass with the recheck below and no dispatch (an exception for merge to the create-time-only rule of [pause](../requirements/pause.md)). Waiting reasons (pipeline pending or none, `unavailable:*`, `draft`, `approvals`, `threads`, `predecessor`) keep it `pending`, with an activity row only on a change of reason; other unmet conditions settle it `refused`; Pause or a reached daily limit leaves it `pending` for a manager, marked `manager_only`, and never evaluated automatically again; all met, it is claimed with the automatic principal and dispatched. A proposal records the `automatic` revision at creation. Each pass reads the stored policy: if it is no longer `automatic` at that revision the proposal becomes `manager_only` with reason `policy_changed` (not `authority`), and a manager may still approve it while the policy is not `denied`. Order within a pass: flag and policy, Pause, repository and change conditions; only when all are met, under the coordinator lock, the daily limit (counted at dispatch), phase 3 containment and admission, then the dispatch-record insert, so two proposals cannot pass a one-slot limit. A limit, containment or admission failure marks it `manager_only` with a note ("Daily limit reached", "Not contained", "Not admitted"; "Paused; a manager will decide" for Pause, the string of pause.md; a `paused` result at the dispatch recheck of an automatic attempt gives the same `pending` `manager_only` state, never a refusal). Head change settles `stale_head`; seven days from creation settles `expired`, `manager_only` included; these, `merged_elsewhere`/`closed` and a stored policy of `denied` (`authority`, ahead of `policy_changed`) apply to every pending merge proposal, `requires_approval` included, on each backstop pass and when a manager opens it. While any of the four flags is off none of this runs and `manager_only` is kept. At the dispatch recheck of an automatic attempt a waiting reason returns the claim to `pending` with no dispatch, no daily-limit count and an activity row on a change of reason; any other unmet reason refuses. The execution principal is checked at claim and at the dispatch recheck only, not on waiting passes. "Opens" means the proposal detail read and the Approve action; each runs one uncached provider read for that proposal and list views do not. Notes: `policy_changed` shows "Policy changed; a manager will decide" and a pending lowering shows "Lowering automatic merge policy is pending", localized in all seven locales. A manager's Approve always runs the recheck once and settles `refused` on any unmet condition.

**Execution.** Add a merge kind to the executor and guard, reusing claim and activity mechanisms without editing the answer implementation. Merge overrides the claim recovery of [proposal kinds](proposal-kinds.md#at-most-once): `ReRunsOnStaleClaim` is false, yet a stale `approving` merge claim (2 minutes) or a fired 60-second deadline settles to `pending` when no dispatch record exists and to `uncertain` when one does, never `failed`; this recovery runs with the flag off as a status write. Re-read, uncached, in order: flag and policy, principal, Pause (automatic only), repository, change state, then the conditions of AC-003.3, unavailable failing closed; the first failing one is the reason. Then insert the dispatch record before the request; its uniqueness on (workspace ID, change key, head) applies only while it is unsettled (a partial index), so a rejected, `not_merged` or released head can be proposed again. The dispatch also records the policy `automatic_since_revision`. Extend GitLab `MergeMR` and `MergeMRForAutomation` (`service_mr_automation_auth.go`) with the expected SHA and a method (squash flag); GitHub's `MergePRRequest.ExpectedHeadSHA` exists. Require provider-side expected-head enforcement. Never use a provider's queued or deferred merge: a queued, `locked` or indeterminate response is `uncertain`. Provider rejection settles `refused (provider_rejected)` with the bounded reason, except a response that the expected head no longer matches, which settles `refused (stale_head)` and lowers nothing. A request in flight when the flag turns off records its own result; revoked settings after the recheck cannot stop it.

**Recovery.** `uncertain` is never replayed. The backstop (which also visits autonomy-off coordinators holding an `uncertain` merge proposal) and Check now read the change no sooner than 10 minutes after the dispatch record: merged with the expected head as merge source is `approved` and records the merge commit SHA; open and not `locked` is `refused (not_merged)` (which lowers an automatic dispatch) unless the dispatch recorded a queued or in-progress response, which keeps it `uncertain`; closed unmerged is `refused (closed)`; merged from another head is `refused (merged_elsewhere)`; each settles the dispatch; reads that stay unavailable leave it `uncertain`. More than 24 hours after the dispatch record without confirmation it is flagged for a manager, who cannot approve it but may Release it (`refused (unconfirmed)`, no provider request, no lowering). With the flag off provider reads pause.

**Revert.** For 7 days after a confirmed automatic merge, the backstop lists up to 3 pages of 100 target-branch commits after the merge commit at most every 15 minutes and matches the line `This reverts commit <sha>` against the recorded SHA. Unlistable history shows revert status unknown and lowers nothing; a revert of a revert is not examined; merges a manager approved are not watched.

**Protections.** Provider observations are separate reads, not an atomic snapshot with the merge. Read branch protection for pipeline, approvals and resolved threads per target branch shown in settings, record each as enforced, not enforced or unknown with observation time; missing permission or unsupported capability is unknown. Do not require enforcement to select automatic: the provider stays authoritative for its rules, and Kandev cannot enforce atomically what the provider does not. Rules Kandev does not read (strict up-to-date, signed commits, required merge queue) surface as `provider_rejected`; repositories requiring a merge queue are unsupported.

## Security, UI and observability

Require workspace manager authorization for setting changes, dependency confirmation and approvals. Bind provider operations to workspace credentials and canonical host; do not expose tokens. Show repository policies in settings and change state in Queue, with equivalent phone controls, localized copy and accessible labels. Merge results and irreversible status appear on proposal cards, activity and ledger. Record bounded refusal reasons and provider failures without secrets. The `coordinatorMerge` runtime flag defaults false in production; while off preserve data and prevent dispatch for any claim not yet past the dispatch-record transaction, where the flags and policy are read again; a request already sent records its own result.
