# Plugin Panels in Task Layout Profiles System Design

## Purpose and boundaries

This extension of [task layout profiles](task-layout-profiles.md) owns reusable
plugin-panel discovery, structural eligibility, and portable placement. UI owns
the presentation preference; Plugins retains registration and runtime lifecycle
authority. The split keeps the existing design below its document size limit.

## Requirement mapping

| Requirement | Design section |
| --- | --- |
| `REQ-UI-TASK-LAYOUT-PROFILES-002` | [Plugin layout-profile extension](#plugin-layout-profile-extension) |

## Plugin layout-profile extension

### Discovery and placement

`components/settings/layouts/layout-editor-toolbar.tsx` currently derives
`AddPanelAction` choices solely from `REUSABLE_PANEL_IDS`. Extend that choice
list with `pluginRegistry.getTaskPanels()` and subscribe through
`usePluginRegistry()`. Keep built-ins in their existing order, followed by
registered plugin panels in registry order. Filter every choice using its
full canonical panel ID against the editor's Dockview API, across all groups.
The same combined list determines whether Add panel is disabled.

Use `pluginPanelId(registration.pluginId, registration.id)` for identity and
`resolveTaskPanelTitle(registration)` for display. Do not call the
task-context `visible` predicate in settings: a reusable profile has no
task/session or runtime presentation context. `mobileEnabled` governs phone
task rendering, not a phone user's ability to configure a desktop profile.
Do not invent a fake task or filter the profile catalog against whichever
task happens to be active elsewhere.

Extend `addReusablePanel` in `layout-editor-actions.ts` to resolve either an
existing built-in reusable ID or a currently registered plugin identity.
For plugins use `resolvePluginPanelDefinition`, not an independently assembled
definition. Resolve again at selection time so an option revoked while the
menu is open cannot add stale content. Retain the existing duplicate check,
selected-group/active-group/first-group placement rules, boolean result, and
`state.perform` capture path. Do not use the live task `addPluginPanel` store
action in this isolated editor. Existing Agent removal protection is unchanged.

The controlled, click-driven menu open behavior must remain intact: touch
pointerdown is prevented so opening a menu never also selects its first row.
No new menu primitive or settings save contributor is needed.

### Structural validation

Use the constants and parser in
`lib/state/layout-manager/plugin-panels.ts`. A reusable plugin definition has:

| Field | Invariant |
| --- | --- |
| `id` | Parses through `parsePluginPanelId` and round-trips through `pluginPanelId` |
| `component` | Exactly `PLUGIN_PANEL_COMPONENT` (`plugin-panel`) |
| `tabComponent` | Exactly `PLUGIN_PANEL_TAB_COMPONENT` (`pluginPanelTab`) |
| `params` | Record containing string `pluginId` and `panelKey`, each exactly matching the parsed identity |
| `title` | String as required by the existing `LayoutPanel` shape; never an identity or availability check |

The existing identity parser defines panel-key syntax; this change does not
tighten plugin registration grammar or introduce a plugin-ID allowlist.
Other serializable params remain subject to the existing shape contract; no
task/session-specific params are newly generated by the editor.

`validateReusableLayout` remains registry-independent. Do not use
`isKnownPanelId` or `resolvePluginPanelDefinition` as a profile eligibility
test: both consult live registrations. An unavailable plugin is still a valid
portable reference.

Before `filterLayoutStateByComponents` and session normalization, validate
plugin-intended definitions in the authoritative groups: those with the
`plugin:` prefix, generic plugin component, or generic plugin tab component.
A mismatch must return `invalid-panel` (or the existing unreadable-shape
failure), not disappear as if it were a retired built-in component. This also
prevents a plugin-prefixed ID with a Chat component from being normalized into
Agent. Preserve the existing retirement filter for unrelated retired panels.

Count valid plugin IDs alongside built-in IDs in `validateGroup`, using the
same global duplicate check. Traverse `column.tree` when present; the flat
`groups` projection must not double-count a tree's panels. Retain missing and
duplicate Agent, empty-group, active-tab, and input-immutability behavior.
Keep these checks local to reusable-profile validation unless a shared pure
identity helper removes actual duplication.

### Preview, serialization, and persistence

Keep `LayoutEditor`'s `plugin-panel` placeholder and `pluginPanelTab` editor
tab. Never mount `PluginTaskPanel`, a registration's `Component`, or task
effects in settings. `toSerializedDockview` resolves display titles through
`panelTitle`, but `canonicalPluginPanelTitle` consults the live registry.
Consequently, the existing `fromDockviewApi` fallback to Dockview's displayed
title is not sufficient after a registration disappears in a mounted editor.

`LayoutEditor` retains canonical plugin titles in an editor-owned map keyed by
full panel ID. Seed it from the input draft when applying a profile; for newly
added panels, retain the registration's canonical title before the localized
display can become the only remaining copy. A present registration can refresh
its canonical entry. Loading, failure, removal, and locale changes must not
erase that retained value. Clear/reseed on profile replacement and remove an
entry only when its panel is explicitly removed from the draft.

Capture still uses `fromDockviewApi` for geometry and panel structure, then
restores canonical titles from the retained map when the registry cannot
resolve them. Apply this consistently to authoritative tree leaves and their
flat group projection. An initially unavailable profile seeds the same map
from saved titles; it must not require a previous registration. Mounted preview
titles resolve registered localized copy when available and the retained
canonical fallback when absent; title-only reconciliation must not mark the
profile dirty or change placement/selection. Keep the map transient and
host-owned, outside plugin params, portable schema, and plugin-facing APIs.

`useLayoutSettings.updateLayout`, compatibility/default resolution,
`upsertBuiltInLayoutOverride`, and custom-profile mutations continue to use
the single validator. Persist through `saved_layouts` and the existing
GET/PATCH user-settings API. No backend schema, endpoint, DTO, or plugin API
change is required. Save failures retain the draft and previous baseline;
the returned settings response remains authoritative after success.

Both the declared split tree and its flat group projection must round-trip
with canonical plugin identity/params, tab order, group selection, geometry,
and `LayoutState.rootOrientation`. Missing orientation retains the existing
legacy horizontal default; an explicit `VERTICAL` must not become horizontal.
`isStructuralComponent` already recognizes the generic plugin component, but
structural retention alone does not preserve layout metadata.
The editor resolves saved pinned widths with the same proportional scaling and
caps as task application before loading Dockview, but retains the original source
geometry separately from those constrained preview extents. Tab-only edits
preserve source widths (including incomplete absolute-width geometry), bounds and
nested weights. The preview baseline tracks split topology, group identity/order
and measured extents, not tab order, selection or titles. Applying a profile or
resizing the preview host refreshes that measured baseline without replacing the
source. A genuine sash, size or structural edit adopts the new captured geometry.
Override/custom save/reload and the shared phone settings surface use the same
capture policy. Vertical rows retain their own axis extents and no width pinning.

Task 01 fixes `rewriteReusableChatPanels` in `session-panels.ts` to preserve
unchanged state metadata while replacing columns. Both
`normalizeReusableSessionPanels` and `materializeReusableChatPanel` use it,
including the explicit task-profile application path. Also preserve state
metadata in `serializer.ts`'s `filterEphemeral`, which captures reusable
profiles from the workbench. Rebuild tree-derived flat groups as today.
These metadata fixes are necessary but not sufficient for axis-correct
application. Existing environment-scoped task layouts continue to win over a
newly edited default.

### Root-axis geometry and horizontal pinning

Keep the existing schema: captured `column.width` stores the root child's
split-axis extent, which is a height for a `VERTICAL` root. Task 01 makes
`toSerializedDockview` use height as the vertical root's available axis and
width as its orthogonal extent, including nested tree recursion. Complete
captured root extents scale proportionally along that axis; incomplete
geometry retains the existing explicit/flexible distribution rules. Vertical
rows do not consume horizontal pinned overrides, sidebar preferences, or
min/max width caps, even if an older snapshot carries `pinned: true`.
Capture must not infer horizontal width pinning merely from Files/Changes in
a vertical root child. Preserve panel identity, groups, and placement.

Task 02 makes root-level sidebar/right width policy horizontal-only in
`dockview-store.ts`'s custom/default geometry resolution, `applier.ts`,
`dockview-layout-builders.ts` fixups, environment-switch sizing, and both
`dockview-pinned-enforce.ts` and `dockview-layout-setup.ts` enforcement
boundaries. Read the actual root orientation for live/saved restore paths;
missing orientation keeps the legacy horizontal policy. A vertical row's
height must never be resized from a right/sidebar width target, impose that
target as a group's width cap, or become a persisted manual right width.
Guard setup's automatic target refresh, loose constraints, sash detection,
drag-end persistence, and width tracking as well as its resize enforcement.
Do not record vertical extents in global pinned targets or per-environment
width bookkeeping. Remove obsolete host-imposed horizontal constraints on
orientation transitions without clearing unrelated component constraints.

Existing nested split weights continue to determine their alternating-axis
geometry. Do not introduce a nested-sidebar pinning policy, change the
horizontal safety caps, or add a geometry schema. Task 02 verifies the
non-square live Dockview path through explicit application, fresh default,
Reset Layout, task reload, and container resize, not only a retained enum.

### Plugin-bearing environment switches

Task 02 changes `canUseFastEnvSwitch` in `dockview-env-switch.ts`: reject the
fast path whenever either the captured current layout or the incoming target
contains the generic plugin component. Inspect a saved incoming environment's
serialized panel definitions, or the effective reusable default's authoritative
groups when no saved environment exists. The check is structural and must not
depend on current registry availability. A plugin on only one side still
requires restoration.

Use the existing slow serialized-restore/default-build path to materialize
the target IDs/params, tree, tab order and selected tabs, then apply the
orientation-safe fixups above. Keep outgoing environment capture and incoming
saved-layout precedence. Do not classify plugins as ephemeral, change revocation
policy, automatically reopen panels, or write portable settings during switching.
The fast path is also rejected when the live root orientation differs from the
target's (saved grid orientation, else the effective default's
`rootOrientation`, missing meaning horizontal), or when the target is vertical.
Fast reuse only reapplies horizontal pinned widths; vertical targets need their
own row extents restored even when both roots are vertical. Plugin-free
horizontal reuse and the comparators remain otherwise unchanged; a generalized
comparator redesign is unnecessary.

For a fresh incoming environment, Task 02 carries the effective reusable
default's resolved horizontal targets through the final
`applyLayoutFixups` call. `performBuildDefault` already resolves/applies those
targets; fixups must not replace them with the stock ratio because canonical
Files/Changes groups are present. Reuse the existing resolver and in-memory
geometry path; do not infer the source from arbitrary live split sizes or
manufacture a manual-right-width preference. A plugin-free fast-path switch to
a fresh environment owns the same resolved right target, so the profile's
right ratio does not depend on whether it contains a plugin panel.

At this fresh-default boundary, an actual manual override retains precedence;
otherwise a resolved reusable target wins over the stock automatic target,
with existing caps applied. Keep the global sidebar preference, saved incoming
environment policy, and code-defined preset defaults unchanged. Carry the
resolved target's ownership through scheduled fixups/enforcement and mounted
automatic refresh so a later rAF cannot silently revert to the stock ratio.
Scope that transient geometry to the active environment/build; clear or replace
it when switching source so a previous profile cannot leak into another task.
No new portable setting, persistence tier, or plugin API is introduced.

`layout-manager/pinned-targets.ts` owns one in-memory source-geometry record
for the active environment. Complete saved geometry supplies the unclamped
right share; incomplete geometry supplies the saved absolute right width.
Column bounds and runtime safety caps apply at each current measurement,
never when retaining the source. Cold initialization binds the known
environment before default construction; genuine null-environment staging
remains separate. Default builds, fast fresh switches and explicit custom
application claim ownership; environment switches, preset application and
vertical roots release it. `resolveEnvRightWidth` ranks manual pixels, owned
source geometry, then stock defaults. Final fixups and mounted refresh both
use that resolver, so constraining and later expanding the container cannot
permanently change the reusable share.
Every container synchronization refreshes an owned reusable target from the
new measured width before layout or enforcement, including sidebar-only
changes with a fixed viewport and callbacks after Dockview's own observer has
already resized the grid. Non-owned saved pixel targets keep their existing
container-only policy; viewport refresh is unchanged. Manual pixel widths
retain precedence; vertical roots never enter horizontal target refresh.

For an active horizontal reusable owner, `getOwnedRightColumn` locates the
actual live right root child through the existing tree capture and returns every
group in that child. Settings splits may create generated group IDs, and
workbench reusable capture intentionally drops IDs; neither changes ownership.
Mounted refresh, loose constraints and sash bookkeeping use this membership,
as do proactive state enforcement and final build fixups. Refresh every child
group's cap from the measured container before restoring the column target,
otherwise one narrow-screen cap can constrain the whole branch after expansion.
State enforcement resolves owned source geometry ahead of stale pinned pixels,
with actual manual pixels still first. Canonical group-ID fallback remains
only for the existing non-owned stock/preset policy. No nested-sidebar policy,
portable schema or panel eligibility/lifecycle change is introduced.

Root child count is not evidence of an embedded sidebar: settings Split tab >
Right can produce Agent, Files/Changes and plugin children without any sidebar.
`getRootSidebarWidth` measures only a dedicated sidebar leaf at a horizontal
root, returning zero when absent. Application, fixups, automatic target
resolution and both enforcement boundaries use that same measured reservation;
neither the Agent nor another ordinary child may reduce the right-column cap.
This does not introduce pinning for a nested sidebar.

When the owned right child is between other root children, both adjacent root
sashes resize it. Persist its post-drag width after either boundary, never after
a nested or unrelated sash. Task environments retain those raw manual pixels
through later layout/display changes; null-environment staging remains transient
and does not create a task-scoped manual preference. The ordinary last-column,
foreign-owner and vertical exclusions retain their existing behavior.

Right-pane reveal and maximize exit also resolve the owned source from the
current measured container before applying their retained layouts. The resulting
width map becomes the applied pinned target before scheduled enforcement; a
resize while the right groups are absent must not require another resize event
after restoration. Actual manual pixels still win and remain capped without
rewriting their raw preference. Known and genuinely null environment identities
are distinct owners. Non-owned saved layout pixel maps keep their existing
restore policy. This changes geometry only, not panel eligibility or lifecycle.

Regression coverage uses actual Dockview, real default builders/fixups, both
enforcement boundaries, and mounted automatic refresh. On a measured 1200px
horizontal host, an in-cap saved center/right ratio of 960/240 with canonical
right groups and a plugin must settle at 240, not the stock 360, after SPA
fresh-default switch and scheduled rAF work. Assert measured extents and
unchanged profile/manual-width storage, not only the initial build/map or a
mocked resize call. Include override/custom-default variants, stock preset,
real manual-width and saved-environment controls.

Consumer integration uses actual Dockview, capture/serialization, and the real
`layoutStructuresMatch`/`savedLayoutMatchesLive` modules, not the existing
mocked comparator decisions. Cover Notes to Prompt History with the same
component skeleton on a fresh incoming task, return to a saved different-plugin
environment, and same plugin IDs with different root/nested placement, tab order
and selection. Include plugin-to-plugin-free and plugin-free-to-plugin switches.
Desktop browser proof uses in-app task navigation without full page reload.


### Availability and lifecycle

Registry changes update the settings choices without removing preview panels
or rewriting saved profiles. Settings does not mount
`useCloseRevokedPluginPanels`. A saved unavailable plugin remains editable as
a generic placeholder.

The task workbench retains its current lifecycle authority: loading/failed
generations preserve panel identities; definitive removal or a ready
generation omitting a panel closes the live tab. This behavior can alter live
environment state, but cannot PATCH or rewrite the portable profile. Re-enabling
and explicitly reapplying the profile restores its declared placement.
No automatic runtime reopening or placement-recovery mechanism is added.

### Responsive interaction and evidence

Desktop settings keeps its existing preview, contextual controls, and
floating Add panel/Save changes actions. Phone entry is the shipped settings
index link to `/settings/preferences/layouts`; the same editor manipulates
desktop profiles. The current responsive Radix menu provides a short
bottom-sheet choice below 640px, with internal scrolling for longer lists,
safe-area treatment, and touch-sized rows. The settings page remains the
vertical scroll owner outside that menu. No phone task-layout override is
persisted, and no mobile-only catalog is created.

Use the existing `mobile-layout-profiles.spec.ts` touch-menu flow and shared
Radix mobile menu as exemplars. Verify 44px touch hit areas, no horizontal
document overflow, deferred touch selection, and shared profile persistence;
keyboard selection remains available through normal menu semantics.

Focused tests cover structural validity with an empty/changing registry,
malformed definitions before sanitization, cross-tree duplicates, save/reload,
and placeholder-only preview. Title regressions exercise both initialization
orders: open/add while registered in a non-English or pseudo locale, revoke
without unmounting, edit another tab, save and reload while unavailable; and
open an initially unavailable saved profile, edit, save and reload. Assert the
exact canonical stored title, identity/params/tree, fallback display, and
unchanged dirty state on registration-only transitions.
Orientation regressions use a non-square host (for example 1400 by 700) and a
`VERTICAL` root with unequal root/nested sizes, non-default selected tabs, and
a Files/Changes/plugin root child carrying a historical pinned flag. Across
validation, override/custom persistence, Agent materialization, application,
fresh default, Reset Layout, task reload, and container resize, assert actual
root-axis proportions, nested widths, tree order, plugin placement, and
selection within Dockview rounding. Exercise both enforcement boundaries and
sash persistence: dragging a vertical root sash must not overwrite the stored
manual right width. Include explicit HORIZONTAL and omitted-orientation
controls to preserve horizontal caps, manual widths, and legacy defaults.
Managed desktop/mobile Playwright tests use the packaged plugin fixture.
Separate disposable-instance browser smoke uses the real Prompt History
package, proves actual content in saved placement, and records package version,
host revision, isolation, and teardown. The fixture is not real-package proof.
