# Orchestrator

`internal/orchestration` owns the complete Orchestrator product: workspace coordination, central assistant capabilities, conversation APIs, instructions, memory, attention and managed work. It has no dependency on `internal/office`. Core run dispatch, runtime authentication and execution profiles are shared infrastructure. `workspace_orchestrators` registers core persona profiles; `orchestration_roles` stores behavioral templates. Registered orchestrators use ordinary task execution profiles, with `DirectProfile` resolved server-side. Do not apply legacy Office task profile pins to `orchestration_managed` tasks. Gate all Orchestrator capabilities together with `features.orchestration`; there is no separate Personal Assistant rollout switch. See `docs/decisions/2026-09-18-orchestrator-product-boundary.md` and the workspace-orchestrators spec/tests.

Core Automations may deliver to a workspace orchestrator through the injected `automation.OrchestratorTarget` interface. Start trigger producers only after the Orchestration queue is ready. A `dispatched` automation run confirms prompt delivery, not completion of requested work. Store its chat reference in `conversation_task_id`, never `task_id`: automation cleanup owns generated tasks but must not delete shared conversations.

Personal assistant privacy is owned by `orchestration_conversations.owner_user_id`, not the mutable default binding. Switching/deleting a binding or unregistering a persona never clears ownership. Configuration/reimport, native task/session reads, legacy Office compatibility and runtime reads/launches must preserve this boundary even with the feature disabled. Private conversations without a current binding require reselection before new turns; automation targets need durable owner authority (currently unsupported for private assistants). See ADR `2026-09-16-private-conversation-ownership`.
